## 一、这个工具要解决什么问题

先说清楚它**不是**什么，避免以后自己想歪：

| 它不是 | 因为 |
|---|---|
| ❌ 网站后台 / CMS | 博客是静态站（ADR-003），**没有服务器、没有数据库**，不存在"在网页上点发布就上线"这回事 |
| ❌ 线上编辑器 | 内容从仓库里的 `.md` 文件来，工具只是**替你操作这些文件** |
| ❌ 博客功能的一部分 | 它**不参与网站运行** —— 删掉这个文件夹，博客照样跑。它跟 `site/` 是「使用者」与「被使用者」的关系 |

**它是什么**：一个跑在你自己电脑上的**本地小管理器**。你（阿然）是唯一用户，它的职责是把你原本要手动做的一串动作（跑命令、改文件、改错格式再重来）压缩成点几下按钮。

### 用户是谁：只服务一个人

这条决定了后面所有取舍。它不是给别人用的工具，所以：

| 因为是「只给自己用」 | 所以可以 |
|---|---|
| 不用做登录、权限、多用户 | 省掉一整层复杂度 |
| 不用考虑联网、部署、别人怎么装 | 只跑本机 `localhost`，不对外暴露端口 |
| 不用做「兼容各种环境」 | 硬编码你的路径、你的分类清单都行 |

> ⚠️ **但有一条不能省**：**这个工具唯一的用户就是站点内容的权威来源**。
> 也就是说，它改的文件就是最终上线的内容 —— **删除、覆盖这类动作必须可回退**（见第六节）。

## 二、它跟你现有的东西怎么摆

新文件夹 `博客管理工具/` 与 `site/`、`搭建设计和过程/` **平级**，都属于 `D:\file\myblogweb` 仓库。

```text
D:\file\myblogweb\                     ← 仓库根（git 管这一层）
├── 搭建设计和过程/                     ← 文档：设计与过程记录【不参与运行】
│   └── 设计方案/……                    现有设计文档（本次不改）
│
├── site/                              ← 代码：网站本体【网站要的东西】
│   ├── src/content/posts/*.md         ← ★ 工具操作的目标就是这里
│   ├── package.json                   ← 工具会调用它的 npm 脚本
│   └── dist/                          ← 构建产物（工具不碰）
│
├── 博客管理工具/                        ← 【本次新增】工具本体
│   ├── 技术架构.md                     ← 就是本文
│   └── （后续）源码
│
├── .workbuddy/                        ← 工具内部数据【已排除出仓库】
│   └── tmp/                           ← 删除文章的备份放这里
└── .gitignore
```

### 选址理由（和现有原则一致）

`目录与命名规范.md` 的第一原则是 **「文档与代码分开」**。那么新工具为什么**不**塞进 `site/`？

| 方案 | 问题 |
|---|---|
| 塞进 `site/` | 会跟 Astro 项目混在一起 —— `site/` 是"网站本身"，工具是"管理网站的软件"。混了以后清理依赖、上线打包都会互相牵连 |
| 塞进 `搭建设计和过程/` | 那个文件夹明确定义为**纯文档、不参与运行**。放代码进去破坏这条边界 |
| **平级新开一个**（✅ 选定） | 边界干净：删掉工具，网站和文档都不受影响；工具坏了，网站照常访问 |

> **一句话**：`site/` 回答"网站长什么样"，`博客管理工具/` 回答"怎么方便地维护网站"。两件事，两个文件夹。

## 三、整体架构

### 一张图

```text
┌─────────────────────────────────────────────────────────────┐
│  浏览器（你看到的界面）                                        │
│  地址 http://localhost:4321 (博客) / http://localhost:5678 (工具) │
└───────────────┬─────────────────────────┬───────────────────┘
                │ ① 直接访问               │ ② 点按钮 → 发请求
                ▼                         ▼
┌───────────────────────────┐  ┌──────────────────────────────┐
│  Astro 开发服务器          │  │  博客管理工具（本地服务）      │
│  npm run dev              │  │  一个 Node 进程，监听 127.0.0.1│
│  端口 4321                │  │  端口 5678                    │
│                           │  │                              │
│  改文件 → 自动刷新页面     │  │  ┌────────────────────────┐  │
└───────────▲───────────────┘  │  │ 网页界面（前端）        │  │
            │                  │  │ 列表 / 编辑表单 / 按钮  │  │
            │ ④ Astro 侦测到    │  └───────────┬────────────┘  │
            │    文件变化        │              │ ③ 后端读写       │
            │    自动重载        │              ▼                │
            │                  │  ┌────────────────────────┐  │
            │                  │  │ 文件操作层（后端）      │  │
            │                  │  │ 读/写/删 .md 文件       │  │
            │                  │  └───────────┬────────────┘  │
            └──────────────────┼──────────────┘                │
                               └──────────────┼────────────────┘
                                              ▼
                       ┌──────────────────────────────────────┐
                       │  site/src/content/posts/*.md         │
                       │  （文章的唯一真相来源）                │
                       └──────────────────────────────────────┘
```

**读图要点**：工具**从不直接操作浏览器里的博客**。它只做一件事 —— **读写 `src/content/posts/` 里的 `.md` 文件**。写完之后，Astro 自己的热更新机制（步骤 ④）会把页面刷新出来。

### 这个设计的三个直接好处

| 好处 | 为什么 |
|---|---|
| **工具坏了不影响博客** | 两者是独立进程，工具只是"帮你写文件的另一个人"。它崩了，你还能手动改文件 |
| **不需要给 Astro 打补丁** | 没有插件、没有改配置。工具用的是最朴素的方式：写文件 |
| **不会产生"两套内容"** | 文件只有一份，在 `src/content/posts/`。工具不是数据库，不存副本 |

## 四、技术选型

### 选定：Node.js + 一个本地 HTTP 服务 + 浏览器界面

理由链条（每一环都指向你已定的东西）：

1. **必须用 Node** —— 你本机已经有（v24.15.0），而且 `npm run dev` 本身就要 Node。**引入第二种运行时**（比如 Python）等于让你多装一个环境，而工具的主要职责只是"起 npm 命令 + 读写文件"，Node 完全够
2. **必须是「本地服务 + 浏览器」** —— 这是你选的 A 方案。关键好处：**界面归界面，能随时改**。改样式不用重新打包、不用重启，刷新浏览器就行
3. **不用任何前端框架** —— 界面就是几页 HTML + 一点原生 JavaScript。理由见下方取舍

### 备选方案与否决理由

| 方案 | 长什么样 | 否决理由 |
|---|---|---|
| **A. 本地服务 + 浏览器**（✅ 选定） | 跑个 Node 服务，浏览器开 `localhost:5678` | —— |
| B. 桌面软件（如 Electron / Tauri） | 双击 exe 弹窗 | **体积暴涨**（Electron 动辄上百 MB）。为了一个"自己用的文章管理器"扛一个浏览器内核，投入产出不成比例 |
| C. 纯命令行脚本 | `blog new`、`blog edit` | **与你的习惯直接冲突** —— 需求文档里"写起来省事"优先级很高，而你明确不喜欢敲命令 |
| D. VSCode 插件 | 在编辑器里点 | 把工具绑死在一个编辑器上；且插件开发调试麻烦，改一行要看半天 |
| E. 装现成的 CMS（如 Decap CMS 等） | 别人写好的网页后台 | **与 ADR-003 冲突** —— 这类工具通常需要 Git 远端或服务端托管，会把你"暂不接远程仓库"（ADR-002）的前提打破；且引入一堆你不认识的依赖 |

### 依赖策略：能不加就不加

这是**只给自己用的工具**，所以可以反常规地"抠门"：

| 依赖 | 用不用 | 说明 |
|---|---|---|
| Node 内置模块（`http` / `fs` / `path` / `child_process`） | ✅ 用 | **零安装**，Node 自带 |
| 前端框架（Vue / React） | ❌ 不用 | 界面只有"列表页 + 编辑页"两屏，原生 JS 足够。加框架 = 多一层构建步骤 + 多一堆依赖 |
| Markdown 解析库 | ❌ 先不用 | 预览可以先靠 Astro 自己（改完文件页面就刷新了）。真需要再做 |
| YAML 解析库 | ⚠️ 待定 | frontmatter 是 YAML。可以先用**纯文本逐行处理**（我们的字段都是扁平的，没有嵌套），不行再加 |
| 代码格式化 / 打包工具 | ❌ 不用 | 没有构建步骤，源码直接跑 |

> **为什么这条值得单列**：你的项目已经踩过 npm 装依赖的坑（BUG-002：esbuild 安装脚本失败后挂起 23 分钟）。
> 工具的依赖越少，**"放半年回来还能跑"的概率越高** —— 这直接对着成功标准第 5 条「半年后还愿意写」。

## 五、功能设计

### 5.1 三组能力

| # | 能力 | 用户动作 | 工具在背后做什么 |
|---|---|---|---|
| 1 | **一键打开博客** | 双击启动文件 | 起 Astro 开发服务器 → 等它可访问 → 自动打开浏览器到 `localhost:4321` |
| 2 | **上传文章**（新增） | 填表单 / 导入 `.md` → 点保存 | 拼出 frontmatter → 生成文件名 → 写入 `src/content/posts/` |
| 3 | **修改 / 删除文章** | 列表里点某一篇 → 改 → 保存；或点删除 | 改：重写该文件。删：**先备份**再删 |

### 5.2 「文章」这个对象长什么样

工具必须理解文章的结构 —— 它由**两半**组成：

```text
---                          ← 这三横线之间是 frontmatter（元数据）
title: 标题
description: 一句话摘要
pubDate: 2026-09-20
updatedDate: 2026-09-25      ← 选填
category: 开发工具
tags: [Git, Windows]         ← 选填
draft: false
---                          ← 三横线结束，下面是正文
## 正文标题
正文内容……
```

**工具的责任就是把这两半拆开、分别让你编辑、再合回去。**

| 一半 | 谁生成 | 怎么填 |
|---|---|---|
| frontmatter | **工具自动拼** | 你在表单里填字段（日期给日历、分类给下拉框），工具负责拼成正确格式 |
| 正文 | **你写** | 大文本框里直接写 Markdown；或从 Obsidian 导入整篇 |

> ⚠️ **这里有个必须守住的点**：frontmatter 的格式错一个字，Astro 构建就会失败
> （`架构设计.md` 实测过：`pubDate` 写成文字 → 构建 exit 1）。
> **所以「输出格式正确的 frontmatter」是这个工具最重要的正确性要求** —— 比界面好不好看重要得多。

### 5.3 新增文章：完整流程

```text
点「新建文章」
     ↓
填表单：标题 / 摘要 / 发布日期 / 分类 / 标签 / 是否草稿
     ↓
写正文（两种方式，你选的 C 方案，两个都能走）
     ├─ 直接在工具里的文本框写 Markdown
     └─ 或点「导入」选一个 Obsidian 里的 .md 文件（只取正文部分）
     ↓
文件名怎么来？ ← 见下方「命名规则」
     ↓
点保存 → 工具把 frontmatter + 正文拼成一个 .md 文件
     ↓
写入 site/src/content/posts/<文件名>.md
     ↓
Astro 侦测到文件变化 → 浏览器里的博客自动出现这篇
```

### 5.4 文件命名规则（**这条不能省**）

你的规范（`目录与命名规范.md`）写死了：**文章文件名必须英文 kebab-case**，因为文件名会变成 URL 的一部分（`/posts/<文件名>`），中文会变成一长串百分号编码，很难看也很难分享。

但**你是用中文写标题的**。所以工具要负责"翻译"这一步：

| 环节 | 谁做 | 例子 |
|---|---|---|
| 你填的标题 | 你 | `npm install 卡死 23 分钟：一次 esbuild 脚本导致的假死` |
| 生成候选文件名 | **工具** | `npm-install-hang-esbuild` |
| 最终确认 | **你**（工具填好默认值，可改） | ✅ 保留 / 或改成你更喜欢的关键词 |

**为什么让你确认一下，而不是全自动**：你的规范里写明「文件名要能被搜索命中」—— **这个判断只有你知道**（哪几个词是别人会搜的）。工具猜得出来大概，但把握关键词的该是你。工具做的是**把"起英文名"这件事的难度从"从零想"降成"改一下"**。

> 这条也顺手解决了"文件名撞车"：如果 `src/content/posts/` 里已经有同名文件，工具会提示你，不覆盖。

### 5.5 修改文章

| 动作 | 工具行为 |
|---|---|
| 打开一篇 | 拆出 frontmatter → 填进表单；正文 → 填进文本框 |
| 改正文 | 保存时重写正文部分，**frontmatter 按表单当前值重写** |
| 改标题 | 保存时**不动文件名**，只改 `title` 字段 |
| 保存时 | **自动把 `updatedDate` 设成今天**（你的需求：技术内容要标更新时间） |
| 改了文件名？ | **本期不做重命名**。理由：URL 是"以后改起来贵"的东西（ADR-006），改名 = 换 URL = 旧链接失效。真需要时人工处理，工具不主动提供这个按钮 |

> **⚠️ 关于「改标题不自动改文件名」，可能反直觉，所以单独解释**：
> 直觉上"标题变了文件名该跟着变"，但那样会**悄悄换掉文章的 URL**。
> 现在还没上线（没人收藏过链接），代价是 0；但**工具一旦养成"改名"的习惯，上线后的某次改标题就会造成死链**。
> 所以定为：**改名是显式操作，不是保存的副作用。**

### 5.6 删除文章（**最危险的动作，单独设计**）

```text
点「删除」
     ↓
弹出确认：「确定删除《标题》吗？将从 <完整路径> 移除」
     ↓
你点确定
     ↓
① 先把这篇 .md 复制到 .workbuddy/tmp/deleted-posts/（带时间戳）
     ↓
② 确认备份成功后，才删原文件
     ↓
③ 界面提示：已删除，备份在 <路径>
```

**为什么这么啰嗦**：这是全套工具里**唯一无法挽回的操作**。写文章错了能改，删错了就得重写。

| 设计点 | 理由 |
|---|---|
| **先备份再删** | 你的项目已经踩过「删除没删干净」的坑（BUG-002 里 `Remove-Item` 静默残留）。这里的思路相反：**不追求"删得干净"，追求"删错了能回来"** |
| **备份放 `.workbuddy/tmp/`** | 这个目录已被 `.gitignore` 整块忽略（BUG-001 的教训），备份不会污染仓库、不会误传 |
| **不做「回收站」界面** | 本期不做"撤销删除"的按钮。备份只是**兜底**，要恢复就手动从 `tmp/` 拷回来 |
| **不做批量删除** | 只删单篇。批量删除把"一次点错"的代价从 1 篇放大成 N 篇，不符合"只给自己用、求稳"的取向 |

## 六、几个关键设计决定（汇总）

| # | 事项 | 决定 | 主要理由 |
|---|---|---|---|
| 1 | 工具形态 | **本地服务 + 浏览器界面** | 界面改起来灵活；不用扛一个浏览器内核 |
| 2 | 工具位置 | **`博客管理工具/`，与 `site/` 平级** | 保持"文档与代码分开"的边界，删工具不影响网站 |
| 3 | 内容来源 | **工具内直接写 + 可导入 Obsidian 的 .md** | 保留你的 Obsidian 工作流，也不强迫你每次都走外部工具 |
| 4 | frontmatter | **表单填，工具拼格式** | 格式错 = 构建失败。表单从源头消灭这类错误 |
| 5 | 文件名 | **工具生成英文 kebab-case 候选，你确认** | 规范要求文件名参与搜索命中，关键词判断权归你 |
| 6 | 修改标题 | **不自动改文件名** | 改名 = 换 URL = 死链风险，要显式做 |
| 7 | 删除 | **先备份到 `.workbuddy/tmp/` 再删** | 唯一不可逆的动作，必须留退路 |
| 8 | 依赖 | **尽量用 Node 内置，不引框架** | 依赖越少，"放半年还能跑"越有保障 |
| 9 | 端口 | **工具用 `127.0.0.1`，不对外** | 只给自己用，不需要局域网访问，减少暴露面 |
| 10 | 与 Astro 的关系 | **只读写文件，不碰它的配置，不装插件** | 耦合越浅，一方坏掉另一方还能用 |

## 七、风险与已知限制（诚实记录）

| 风险 | 影响 | 怎么应对 |
|---|---|---|
| **工具与 Astro 的端口/进程打架** | 重复启动会报端口占用 | 启动前先检测 4321 是否已被占用；已占用则不再启动，直接打开浏览器 |
| **本机 npm 路径特殊** | PATH 里 WorkBuddy 的 node 抢先且没有 npm | 工具内部**写死完整路径** `C:\Program Files\nodejs\npm.cmd`（这个坑 `架构设计.md` 已经记过） |
| **frontmatter 里含 `---` 或特殊字符** | 文件被拆错，内容错乱 | 保存前校验：正文里出现行首三横线要在界面提示 |
| **文章很长时，浏览器文本框会卡** | 编辑体验下降 | 本期接受。真卡了再考虑换编辑器组件 |
| **工具本身没有版本控制保护** | 工具的错操作可能覆盖文章 | 双保险：① 删除先备份；② 仓库有 Git，文章改动可 `git diff` 对比（ADR-002） |
| **`.md` 被外部改动（你在 Obsidian 里直接改站点文件）** | 工具的"内存状态"可能与磁盘不一致 | 工具**每次操作前重新读磁盘**，不缓存文章内容 —— 保证看到的永远是真实文件 |
| **图片仍然是外部依赖** | 图床挂了图片全裂 | 这与工具无关（图片走 PicGo 图床，见 `架构设计.md`）。工具只管文字 |

> **最后一条特别注意**：本工具**不处理图片**。
> 因为你的 Obsidian 插件在上传时就已经把图片换成网络链接了，工具只需要原样搬运文本。
> 什么时候需要重新考虑：如果哪天真要往仓库里放图片，再单独设计。
