# 本章速览

- **需求分析的双重身份**：既要细化基础需求，又要建立各类模型（桥接"需求"与"设计"）。
- **易混**：用例图（表达"谁做什么"）≠ 活动图（表达"按什么顺序做"）。

---

# 1. 需求分析与建模的定位

**需求分析要确定的三个"什么"**：

- 确定软件的**操作特性**；
- 指明软件和其他系统元素之间的**接口**；
- 规定软件必须满足的**约束**。

**软件工程师（分析师/建模师）的两项工作**：

- **细化**在前期需求工程任务中建立的基础需求；
- 建立描述**用户场景、功能活动、问题类及其关系、系统和类行为、数据流变换**的模型。

> **桥接作用**：需求模型是"问题域（用户语言）"通向"设计模型（实现语言）"的**桥梁**——它既不是纯粹的自然语言需求描述，也还不是设计蓝图。

# 2. 需求建模的六条经验原则

1. 模型应关注在**问题域或业务域内可见的需求**，抽象的级别应该相对高一些；
2. 需求模型的每个元素都应能**增加对软件需求的整体理解**，并提出对信息域、功能和系统行为的深入理解；
3. 关于**基础结构和其他非功能**的模型应推延到**设计阶段**再考虑；
4. **最小化**整个系统内的关联；
5. 确认需求模型为**所有利益相关者**都带来价值；
6. 尽可能**保持模型简洁**。

# 3. 需求模型（分析模型）的元素

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261105213939566.png)

| 元素类别 | 建模对象 | 产物 |
|---|---|---|
| **基于场景的元素** | 用户如何使用系统 | 用例文本、用例图、活动图、泳道图 |
| **基于类的元素** | 对象、属性、操作、关系、协作 | 类图、分析包、CRC 模型、协作图 |
| **行为元素** | 系统如何响应事件/刺激 | 状态图、顺序图 |
| **面向数据流的元素** | 数据的变换过程 | 数据流图、控制流图、处理叙述 |

# 4. 基于场景的建模：用例

> 场景模型只帮助定义两件事：系统**之外**存在什么（参与者）、系统**应完成**什么（用例）。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261105213959539.png)

## 4.1 写用例前的四个问题

1. 我们应该**写什么**？
2. 我们应该**写多少**？
3. 我们编写说明应该**多详细**？
4. 我们如何**组织**说明？

**写什么**——起始与导出阶段提供了开始编写用例所需的信息：

- 运用需求收集会议、QFD 和其他需求工程机制；
- 确定利益相关者；定义问题的范围；说明整体的运行目标；
- 建立优先级顺序；概述所有已知的功能需求；
- 描述系统将处理的信息（对象）；
- 开始开发用例时，**列出特定参与者执行的功能活动**。

> **SafeHome 示例**：住宅监视子系统确定了由参与者"房主"执行的 7 项功能——选择要查看的摄像机、提供所有摄像机的缩略视图、在窗口中显示摄像机视图、控制镜头的转动与缩放、可选择地记录输出、回放输出、通过 Internet 访问监视功能。

**写多少**——与相关利益人进一步会话后，团队为每一个**功能说明**开发用例：

- 通常以**非正式、叙述性**的方式表达；
- 若要求更正式，则以类似结构化格式**重写**同一用例。

## 4.2 用例的三个基本概念

| 概念 | 含义 |
|---|---|
| **场景** | 描述了系统的一个"**使用线程**" |
| **参与者（Actor）** | 系统运行时**人或设备扮演的角色** |
| **角色多样性** | 用户在给定场景中**可以扮演许多不同的角色** |

## 4.3 开发用例要回答的问题

- 参与者完成的**主要任务和功能**是什么？
- 参与者将**获取、产生或改变**哪些系统信息？
- 参与者必须**通知**系统有关外部环境的改变吗？
- 参与者希望**从系统获取**什么信息？
- 参与者希望得知会有意料之外的变更吗？

## 4.4 一个完整用例的模板结构（SafeHome：ACS-DCV）

| 栏目 | 内容要点 |
|---|---|
| **用例名/编号** | 通过互联网访问摄像头监视——显示摄像头视图（ACS-DCV） |
| **迭代/更新** | 迭代 2，V.Raman 1 月 14 日 |
| **主要参与者** | 房主 |
| **情境目标** | 从任何远程地点通过互联网查看遍布房间的摄像头输出 |
| **前提条件** | 系统必须完整配置；必须获得正确的身份证号和密码 |
| **起动** | 房主在离家时决定查看房屋内部 |
| **主成功场景** | 登录网站 → 输入身份证号 → 输入两个密码（各≥8 字符）→ 系统显示功能按钮 → 选"监视" → 选"选取摄像头" → 显示平面图 → 选摄像头图标 → 选"视图" → 显示视图窗口 → 每秒一帧输出 |

# 5. 活动图与泳道图

## 5.1 活动图

- 活动图用于描述**从活动到活动的流**，可为系统的**动态方面**建模，也可用来描述**用例脚本**；
- 在活动图中，一个活动结束后**立即进入**下一个活动（而状态图中状态的变迁可能需要事件的触发）；
- **跃迁**：控制流从一个动作/活动状态传递到下一个动作/活动状态，用简单的**有向线条**表示；
- **分叉（fork）**：将单一控制流分成两个或多个**并发**控制流，**一个输入、多个输出**，分叉路径相关的活动是并行的；
- **联结（join）**：两个或多个并发控制流的**同步**，**多个输入、一个输出**，联结上各路径相关的活动是并行的。

> ⚠️ 活动图描述**发生了什么**，但**没有说明该活动由谁完成**——这正是泳道图要解决的问题。

## 5.2 泳道图

- **泳道**决定各个活动由哪个类（或哪个参与者）来完成；
- 泳道用**矩形框**表示，属于某个泳道的活动放在该矩形框中，将**对象名放在矩形框的顶部**，表示泳道中的活动由谁负责；
- 作用：让建模人员表示用例所描述的活动流，同时**指示哪个参与者或分析类**负责活动矩形所描述的活动（当一个用例涉及多个参与者时尤其必要）。

# 6. 数据建模

数据建模的四项工作：

- 检查**数据对象的独立处理**；
- 注意力集中在**数据域**；
- 创建**客户级抽象的模型**；
- 指出**数据对象之间的相互联系**。

> 数据建模的产物是**实体—关系（ER）** 层面的描述：有哪些数据对象、对象有哪些属性、对象之间是什么关系。它是后面"基于类建模"的原料。

# 7. 基于类的建模

## 7.1 基于类建模要表示什么

- 系统操作的**对象**；
- 应用于对象之间能有效控制的**操作**（也称方法或服务）；
- 对象间的**关系**（某种层级）；
- 定义出现在类之间的**协作**。

> **基于类模型的元素**：类和对象、属性、操作、**CRC 模型**、协作图、包。

## 7.2 CRC 模型

> **CRC（类—职责—协作者）建模**提供了一种简单方法，可以识别和组织与系统或产品需求相关的类。

CRC 模型实际上是**表示类的标准索引卡的集合**。每张卡片分三部分：

| 位置 | 内容 |
|---|---|
| 卡片**顶部** | **类名**（Class） |
| 卡片主体**左侧** | 类的**职责**（Responsibility） |
| 卡片主体**右侧** | 类的**协作者**（Collaborator） |

**SafeHome 的 FloorPlan 类示例**：

| 类 | FloorPlan（住宅平面图） |
|---|---|
| **职责** | 定义住宅平面图的名称/类型（defines floor plan name/type） |
| | 管理住宅平面图的布局（manages floor plan positioning） |
| | 缩放显示住宅平面（scales floor plan for display） |
| | 合并墙、门和窗（incorporates walls, doors and windows） |
| | 显示摄像头的位置（shows position of video cameras） |
| **协作者** | Wall（墙）、Camera（摄像头） |

> 记忆点：**一张卡片三个格子——类名、职责、协作者**；职责用"动词开头"描述，协作者写"它需要谁配合"。

## 7.3 类的三种类型

| 类型 | 别名 | 作用 | 示例 |
|---|---|---|---|
| **实体类** | 模型类 / 业务类 | 从**问题说明中直接提取**出来，表示业务概念 | FloorPlan、Sensor |
| **边界类** | —— | 创建**用户可见**、使用软件时交互的接口 | 交互屏幕、打印的报表 |
| **控制类** | —— | 自始至终管理"**工作单元**" | 见下 |

**控制类具体管理**：

- 实体类的**创建或更新**；
- 当边界类从实体对象获取信息后的**实例化**；
- 对象集合间的**复杂通信**；
- 对象间或用户与应用系统间**交换数据的确认**。
