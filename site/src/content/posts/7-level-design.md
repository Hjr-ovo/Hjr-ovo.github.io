# 本章速览

- **必知**：构件与传统模块在**内聚、耦合**上的分类；四种算法表示工具的优缺点与适用场合。
- **易混**：`ISP`（接口分离）≠ `LSP`（里氏替换）；决策表 ≠ 判定树（本章只讲决策表）。

# 1. 什么是构件

> **OMG 统一建模语言规范的定义**：构件是"**系统模块化的、可部署的和可替换的部件，该部件封装了实现并暴露一组接口**"。

三种理解视角：

| 视角 | 说明 |
|---|---|
| **OMG / 通用视角** | 模块化、可部署、可替换的部件；封装实现、暴露接口 |
| **OO 观点** | 构件包含**一组协作的类** |
| **传统观点** | 一个构件包含**处理逻辑**、实现处理逻辑所需的**内部数据结构**，以及能保证构件被调用和实现数据传递的**接口** |

# 2. 基本设计原则

## 2.1 面向对象四原则（"SOLID"的核心四条）

| 缩写 | 原则 | 一句话表述 | 通俗解释 |
|---|---|---|---|
| **OCP** | 开闭原则（Open-Closed） | 模块/构件应该**对外延具有开放性，对修改具有封闭性** | 加功能靠"加新代码"，不改老代码 |
| **LSP** | Liskov 替换原则 | "**子类可以替换它们的基类**"——子类对象必须可以替换基类对象 | 子类型不能破坏父类型的契约 |
| **DIP** | 依赖倒置原则 | "**依赖于抽象，而非具体实现**" | 高层与低层都依赖抽象；抽象不依赖细节 |
| **ISP** | 接口分离原则 | "**多个客户专用接口比一个通用接口要好**" | 别让客户被迫依赖它用不到的方法 |

**LSP 的严格表述**：

> "若对于类型 S 的任一对象 o1，均有类型 T 的对象 o2 存在，使得在 T 定义的所有程序 P 中，用 o1 替换 o2 之后，**程序的行为不变**，则 S 是 T 的子类型。"

**DIP 的两条与启发式规则**：

- a. **高层模块不应该依赖于低层模块**，二者都应该依赖于抽象；
- b. **抽象不应该依赖于细节**，细节应该依赖于抽象；
- 启发式规则：程序中**所有的依赖关系应该终止于抽象类或者接口**；
- 原因：应用程序中编写的大多数具体类都是**不稳定的**，把它们隐藏在**抽象接口**后面，可以**隔离它们的不稳定性**。

![开闭原则（OCP）——通过接口扩展而非修改源码](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s04.png)

> OCP 的经典做法：定义 `Sensor` 接口（read / enable / disable / test），新增 `HeatSensor`、`SmokeSensor`、`MotionDetector` 只需实现接口，**不必修改已有代码**。

## 2.2 打包组织的三条原则

| 缩写 | 原则 | 一句话表述 | 解决的问题 |
|---|---|---|---|
| **REP** | 发布复用等价性原则 | **复用的粒度就是发布的粒度** | 类要打包管理、同时升级 |
| **CCP** | 共同封装原则 | **一同变更的类应该合在一起** | 变更影响局部化 |
| **CRP** | 共同复用原则 | **不能一起复用的类不能被分到一组** | 避免"被迫复用一堆用不到的东西" |

> 记忆提示：前四条（OCP/LSP/DIP/ISP）管"**类怎么设计**"，后三条（REP/CCP/CRP）管"**类怎么打包**"。

# 3. 构件的 UML 表示

构件具有**两组接口**：

- **提供的接口**（provided interface）——它能给其他构件提供什么服务；
- **需要的接口**（required interface）——它需要从其他构件得到什么服务。

> 接口用"棒棒糖/插座"符号表示：提供的接口画成棒棒糖，需要的接口画成半圆插座。**这正是"可替换"的前提**：只要接口匹配，构件就能被替换。

# 4. 构件级设计中的内聚与耦合

## 4.1 内聚性

| 观点 | 理解 |
|---|---|
| **传统观点** | 模块的**专一性** |
| **OO 观点** | 内聚性意味着构件或类**只封装那些相互关联密切、且与构件或类自身有密切关系的属性和操作** |

**内聚的分类**（由强到弱）：功能的、分层的、通信的、有序的、过程的、暂时的、实用的。

## 4.2 耦合性

| 观点 | 理解 |
|---|---|
| **传统观点** | 构件之间彼此联系、构件和外部世界联系程度的一种度量 |
| **OO 观点** | 类之间彼此联系程度的一种**定性**度量 |

**耦合的分类**（由强到弱）：内容、共用、控制、标记、数据；另有**历程调用**、**类型使用**、**包含或导入**、**外部**等与实现技术相关的耦合形式。

## 4.3 内聚与耦合的关系（与第 5 章一致）

- 与其他模块**强耦合**的模块意味着**弱内聚**；**强内聚**的模块意味着与其他模块间**松散耦合**；
- **设计目标：力争强内聚、弱耦合**。

![内聚与耦合——设计目标：强内聚、弱耦合](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s14.png)

# 5. 算法设计：如何把过程细节表达清楚

> **算法设计模型**：以**细节的层次**表示算法，**它能对质量进行评审**。

可选的表示形式：

- **图解**（流程图、盒图/N-S 图）；
- **伪代码**（如 PDL）；
- **编程语言**；
- **决策表**。

## 5.1 流程图（Flowchart）

程序流程图的**标准符号**：起止框（圆角矩形）、处理框（矩形）、判断框（菱形）、输入输出框（平行四边形）、流程线（箭头）、连接符（圆）。可表达顺序、选择（IF、IF-ELSE）、循环（WHILE、DO-UNTIL）、CASE 等结构。

**例题：托运货物运费计算**

> 设货物重量 x、客户信息 y，输入 x、y 后计算运费。要求：若 `0 < x ≤ 5`，用公式 1 计算，并循环 3 次完成"记账"和"输出"操作后结束；若 `5 < x ≤ 15`，用公式 2 计算，同样循环 3 次；若 `15 < x ≤ 50`，用公式 3……（条件 1/2/3 依次判断，其余情况用公式 4）

![运费计算例题——程序流程图](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s18.png)

![运费计算例题——PFD 图](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s19.png)

## 5.2 盒图（N-S 图 / Box Diagram）

- 用**嵌套的矩形框**表达控制结构：顺序（上下拼接）、选择（IF 框）、循环（DO-WHILE / DO-UNTIL 框）、CASE 框；
- **没有箭头**，因此**不允许随意转移控制**——这正是它的优点。

![N-S 盒图](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s20.png)

**N-S 图小结（四点优点）**：

1. 每个构件具有明确的**功能域**；
2. **控制转移必须遵守结构化设计要求**；
3. 易于确定**局部数据和（或）全局数据的数据域**；
4. 易于表达**嵌套关系和模块的层次结构**。

**与流程图的对比**：

| 维度 | 流程图 | N-S 盒图 |
|---|---|---|
| 控制转移 | 可用箭头任意跳转（易破坏结构化） | 无箭头，**强制结构化** |
| 表达嵌套 | 嵌套层次不直观 | 嵌套关系**一眼可见** |
| 可维护性 | 修改易引起"面条式"混乱 | 局部修改影响范围明确 |

## 5.3 PDL（程序设计语言 / 伪代码）

> **PDL** 是一种用于描述功能模块的**算法设计和加工细节**的语言，也称**伪代码（Pseudo code）**。

**构成**：**PDL = 关键词 + 自然语言**。

**运费计算例题的 PDL 表达**：

```
条件1 { 公式1；call sub； }
条件2 { 公式2；call sub； }
else if 条件3 { 公式3；call sub； }
else { 公式4；call sub； }
do { 记账；输出； }
```

![PDL 示例](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s23.png)

> PDL 的优点：可以用自然语言补足细节，**便于评审**，且**与具体编程语言无关**。

## 5.4 决策表（Decision Table）

**定义**：一种描述程序执行逻辑的**表格化工具**，可以把**动作和条件**翻译成表格。表格**很难被误解**，并能够作为某个**表驱动算法**的机器可识别的输入。

**四个组成部分**：

| 位置 | 内容 |
|---|---|
| **左上部** | 列出所有的**条件** |
| **左下部** | 列出所有可能的**动作** |
| 右半部 | 构成一个**矩阵**：表示条件的组合，以及特定条件组合对应的动作 |
| 右半部的**每一列** | 可解释为**一条处理规则** |

![决策表的结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s25.png)

**设计决策表的步骤**：

1. 列出该模块相关的**所有动作**；
2. 列出执行该模块时的**所有条件**（或所做的决策）；
3. 将特定的**条件组合**与特定的**动作**相关联，**消除不可能的条件组合**；
4. **定义规则**——指出一组条件应对应哪个或哪些动作。

![决策表示例](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_07_s27.png)

## 5.5 四种表示工具对比

| 工具 | 形式 | 优点 | 缺点/适用 |
|---|---|---|---|
| **流程图** | 图形 | 直观、符号标准、人人能看懂 | 允许任意跳转，易破坏结构化 |
| **N-S 盒图** | 图形 | 强制结构化、嵌套清晰 | 修改时局部重画成本高；不便于表达复杂判断组合 |
| **PDL** | 文本（伪代码） | 与语言无关、易评审、易维护 | 不够直观，需读者具备一定基础 |
| **决策表** | 表格 | 条件/动作组合一目了然、难误解、可作表驱动输入 | 条件很多时表格膨胀 |

> 选择建议：**逻辑判断组合复杂** → 决策表；**强调控制结构规范** → N-S 图；**需要评审算法细节** → PDL；**需要与人沟通流程** → 流程图。
