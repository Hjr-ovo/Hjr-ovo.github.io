# 本章速览

- **一句话**：需求分析的任务是**借助当前系统的逻辑模型，导出目标系统的逻辑模型**，解决"做什么"的问题。
- **易混**：需求 ≠ 功能；"做什么" ≠ "怎么做"。

---

# 1. 需求分析在软件工程中的位置

## 1.1 需求分析的任务

需求分析要完成三件事：

- 确定软件的**操作特性**；
- 指明软件和其他系统元素之间的**接口**；
- 规定软件必须满足的**约束**。

由此，软件工程师（有时称分析师或建模师）要做的是：

- **细化**前期需求工程任务中建立的基础需求；
- 建立描述**用户场景、功能活动、问题类及它们之间的关系、系统和类行为以及数据流变换**的模型。

## 1.2 "理解需求"的实质

> 软件开发是要实现目标系统的**物理模型**。需求分析的任务，就是借助于**当前系统的逻辑模型**，导出**目标系统的逻辑模型**，解决目标系统"**做什么**"的问题。

理解这张图的四个概念对：

| 概念 | 含义 |
|---|---|
| **当前系统的物理模型** | 现在实际是怎么运转的（含具体的人、设备、实现方式） |
| **当前系统的逻辑模型** | 抽象掉实现手段后，现在系统在"逻辑上"做什么（**模型化 / 抽象化**得到） |
| **目标系统的逻辑模型** | 新系统在逻辑上应当做什么 |
| **目标系统的物理模型** | 新系统最终的具体实现（**具体化 / 实例化**得到） |

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104190002392.png)


> 一句话记忆：**"怎么做"是设计阶段的事，"做什么"才是需求阶段的事。**

# 2. 需求的类型

| 类型 | 定义 | 典型内容 |
|---|---|---|
| **功能性需求** | 描述系统**应该做什么**，即为用户和其他系统完成的功能、提供的服务 | 业务功能、输入输出处理、权限与角色 |
| **非功能性需求** | 必须遵循的**标准、外部界面的细节、实现的约束条件、质量属性**等 | 性能、可靠性、安全、可移植性、可用性…… |

> **关键结论**：非功能需求**限定了选择解决问题方案的范围**，如运行平台、实现技术、编程语言和工具等。
> ——这就是为什么"非功能需求"常常比功能需求更"致命"：它决定了方案空间。

## 非功能性需求的分类

课件的分类维度包括：

- **效率需求**、**可靠性需求**、**可移植性需求**；
- **互操作性需求**、**道德需求**、**立法需求**；
- **可用性需求**、**安全性需求**、**隐私需求**；
- **交付需求**、**现实需求**、**标准需求**；
- **空间需求**、**性能需求**、**产品需求**、**机构需求**。

# 3. 需求工程的七项任务

| # | 任务 | 核心动作 |
|---|---|---|
| 1 | **起始（Inception）** | 询问一系列问题以建立：对问题的基本理解、需要解决方案的人、所期望解决方案的性质；达成项目利益相关者与开发人员之间的**初步交流合作** |
| 2 | **导出（Elicitation）** | **引出**所有利益相关者的需求 |
| 3 | **精化（Elaboration）** | 创建一个**分析模型**，用以说明软件的数据、功能和行为等需求 |
| 4 | **协商（Negotiation）** | 对开发者和客户来说都是**现实的**、达成**一致的可交付系统** |
| 5 | **规格说明（Specification）** | 可以是以下一项或任意组合：一份写好的**文档** / 一套**模型** / 一个形式化的**数学模型** / 一组**使用场景（用例）** / 一个**原型** |
| 6 | **确认（Validation）** | 一种**审查机制**，即找出：内容或解释上的错误、可能需要进一步解释澄清的地方、丢失的信息、不一致性（建造大型产品或系统时的**主要问题**）、冲突的需求或不可实现的需求 |
| 7 | **需求管理（Requirements Management）** | 对需求变更、需求状态、需求跟踪进行管理 |

> 记忆口诀：**起、导、精、协、规、确、管**（7 个字概括 7 项任务）。

# 4. 需求模型（分析模型）的元素

需求模型由**四类元素**构成，每一类都对应一种建模视角与一组 UML 图：

| 元素类别 | 关注点 | 典型建模产物 |
|---|---|---|
| **基于场景的元素** | 用户如何使用系统（使用线程） | 用例文本、用例图、活动图、泳道图 |
| **基于类的元素** | 系统操作的对象、属性、操作、关系 | 类图、分析包、CRC 模型、协作图 |
| **行为元素** | 系统如何响应外部事件（状态与交互） | 状态图、顺序图 |
| **面向数据流的元素** | 数据在系统中的变换 | 数据流图、控制流图、处理叙述 |

# 5. 用例与用例建模

## 5.1 场景与参与者

- 一个**场景**描述了系统的一个"**使用线程**"；
- **参与者（Actor）**代表了系统运行时**人或设备扮演的角色**；
- 用户在给定场景中**可以扮演许多不同的角色**。

> 用例图只帮助定义两件事：系统**之外**存在什么（参与者）、系统**应完成**什么（用例）。

## 5.2 编写用例时的四个问题

1. 我们应该**写什么**？
2. 我们应该**写多少**？
3. 我们编写说明应该**多详细**？
4. 我们如何**组织**说明？

**写什么**——起始和导出阶段提供了开始编写用例所需的信息：

- 运用需求收集会议、QFD 及其他需求工程机制；
- 确定利益相关者；
- 定义问题的范围；
- 说明整体的运行目标；
- 建立优先级顺序；
- 概述所有已知的功能需求；
- 描述系统将处理的信息（对象）；
- 开始开发用例时，**列出特定参与者执行的功能活动**。

**写多少**——在与相关利益人进一步会话后，团队为每一个**功能说明**开发用例：

- 通常以**非正式的叙述性**方式表达；
- 若要求更正式，则以类似结构化的格式**重写**相同的用例。

## 5.3 开发用例要回答的问题

- 参与者完成的**主要任务和功能**是什么？
- 参与者将**获取、产生或改变**哪些系统信息？
- 参与者必须**通知**系统有关外部环境的改变吗？
- 参与者希望**从系统获取**什么信息？
- 参与者希望得知会有意料之外的变更吗？

## 5.4 用例模板的构成（以 SafeHome 为例）

> **用例**：通过互联网访问摄像头监视——显示摄像头视图（**ACS-DCV**）
> **迭代**：2 ｜ **最新更新**：V.Raman 1 月 14 日

| 要素 | SafeHome 实例内容 |
|---|---|
| **主要参与者** | 房主 |
| **情境目标** | 从任何远程地点通过互联网查看遍布房间的摄像头输出 |
| **前提条件** | 必须完整配置系统；必须获得正确的用户身份证号和密码 |
| **起动（触发器）** | 房主在远离家的时候决定查看房屋内部 |
| **场景（主成功流）** | ① 登录 SafeHome 网站 → ② 输入用户身份证号 → ③ 输入两个密码（各至少 8 个字符）→ ④ 系统显示所有主要功能按钮 → ⑤ 选择"监视" → ⑥ 选择"选取摄像头" → ⑦ 系统显示房屋平面图 → ⑧ 选择某摄像头图标 → ⑨ 选择"视图" → ⑩ 系统显示该摄像头编号确定的视图窗口 → ⑪ 以每秒一帧显示视频输出 |
| **异常（备选流）** | ① 身份证号/密码不正确 → 参看"确认身份证号和密码"；② 未配置监视功能 → 显示错误消息，参看"配置监视功能"；③ 选择"查看所有摄像头的缩略视图快照" → 参看同名用例；④ 平面图不可用/未配置 → 参看"配置平面设计图"；⑤ 遇到报警条件 → 参看"遇到报警条件" |
| **优先级** | 必须在基础功能之后实现，**中等优先级** |
| **何时可用** | 第三个增量 |
| **使用频率** | 中等频度 |
| **使用方式** | 通过基于 PC 的浏览器和互联网连接到 SafeHome 网站 |
| **次要参与者及方式** | 系统管理员（基于 PC 的系统）、摄像头（无线连接） |
| **未解决的问题** | ① 有何机制防止 SafeHome 雇员未授权使用该功能？② 足够安全吗？（黑客入侵将使最主要的个人隐私受侵）③ 给定摄像头视图所需带宽下，系统响应可否接受？④ 高带宽连接下能否做到比每秒一帧更快？ |

# 6. 其他常用建模图（本章提及）

| 图 | 用途 |
|---|---|
| **活动图** | 描述从活动到活动的**流**，为系统动态方面建模，可用于描述用例脚本 |
| **类图** | 描述类及其属性、操作与关系（如 SafeHome 的 Sensor 类：type、name/id、characteristics、area、location、enable()、disable()、identify()、reconfigure()） |
| **状态图** | 描述状态、状态变量、状态活动及状态之间的迁移（如"读指令"状态：System status = "ready"、Entry/subsystems ready、Do: poll/read/interpret user input） |
