# 本章速览

- **必知**：构件与对象的四点区别；体系结构分析与设计的六个步骤；垂直分块与水平分块。

---

# 1. 为什么体系结构重要

三点理由：

1. 软件体系结构的表示有助于对系统开发感兴趣的各方（**利益相关者**）开展**交流**；
2. 体系结构突出了**早期的设计决策**——这些决策对随后所有软件工程工作有深远影响，对系统作为可运行实体的最后成功起重要作用；
3. 体系结构"**构建了一个相对小的、容易理解的模型，该模型描述了系统如何构成以及其构件如何一起工作**"。

> **结论**：对于大规模的复杂软件系统，**总体的系统结构设计和规格说明**，比起对计算的算法和数据结构的选择，已经变得**明显重要得多**。

---

# 2. 软件体系结构（SA）的定义

**软件体系结构（SA）**：
- 是一个关于**系统形式和结构的综合框架**，包括系统构件和构件的整合；
- 从**较高的层次**考虑组成系统的构件、构件之间的连接，以及由构件与构件交互形成的**拓扑结构**；
- 这些要素应满足一定的**限制**、遵循一定的**设计规则**，能够在一定的环境下**演化**；
- 反映系统开发中具有**重要影响的设计决策**，便于各种人员的交流，反映**多种关注**，据此开发的系统能完成既定的功能和性能需求。

**核心公式**：

**体系结构 = 构件 + 连接件 + 拓扑结构 + 约束 + 质量**
Architecture = Components + Connectors + Topology + Constraints + Performance

# 3. 构件与连接

## 3.1 什么是构件

- "**构件**"是具有某种功能的**可复用的软件结构单元**，表示系统中主要的**计算元素和数据存储**，具有提供的**接口描述**；
- 构件是一个**抽象的概念**——任何在系统运行中承担一定功能、发挥一定作用的软件体，都可看作是构件。

![构件与接口](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s04.png)

## 3.2 构件 vs. 对象（四点区别，易考）

| 比较维度 | 构件（Component） | 对象（Object） |
|---|---|---|
| **抽象级别** | 是**设计概念** | 是**实现技术** |
| **规模** | 可以小（一个对象）也可以大（一系列对象或一个完整应用） | 一般**较小** |
| **数据封装程度** | 不允许直接操作构件中的数据，数据**真正被封装** | 通过**公共接口**部分操作，数据**可能被访问** |
| **复用性质** | 基于**功能**的复用（**组装**） | 基于**技术**的复用（**继承**） |

## 3.3 连接（Connection）

> **连接**：构件间建立和维持**行为关联与信息传递**的途径。

连接需要**两方面的支持**：

| 支持 | 简称 | 说明 |
|---|---|---|
| 连接发生和维持的**机制** | **机制**（mechanism） | 实现连接的**物质基础** |
| 连接正确、无二义、无冲突进行的**保证** | **协议**（protocol） | 连接正确有效进行**信息交换的规则** |

# 4. 体系结构风格

## 4.1 风格由什么构成

每种风格描述一种**系统类别**，包括四个要素：

1. 完成系统需要的某种功能的**一组构件**（如数据库、计算模块）；
2. 能使构件间实现"**通信、合作和协调**"的**一组连接件**；
3. 定义构件如何集成为系统的**约束**；
4. **语义模型**——使设计者能通过分析系统组成的已知属性来理解系统的整体性质。

## 4.2 主要风格清单（必背）

- **以数据为中心的体系结构**（仓库）
- **数据流体系结构**（管道—过滤器）
- **调用和返回体系结构**（主程序—子过程、分层）
- **面向对象体系结构**
- **层次体系结构**
- 其他：**客户机—服务器**（C/S）、**模型—视图—控制器（MVC）**

![主要软件体系结构风格总览](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s08.png)

## 4.3 五种主要风格详解

### （1）以数据为中心的体系结构（仓库风格）

- **构件**：中央数据存储（数据库/黑板）+ 若干独立处理构件；
- **连接件**：各处理构件与中央数据之间的访问通道；
- **特点**：数据是"中心"，构件之间**不直接通信**；
- **优点**：易扩充新构件（数据格式不变即可接入）；数据集成性好；
- **缺点**：中央数据结构的**格式变更**会影响所有构件；控制流分散、难以管理。

![以数据为中心的体系结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s09.png)

### （2）数据流体系结构（管道—过滤器）

- **构件**：一系列**过滤器**（变换处理）；
- **连接件**：**管道**，在过滤器之间单向传递数据；
- **特点**：数据依次流经各处理阶段；
- **优点**：可复用（过滤器可重组）、易理解、支持并发；
- **缺点**：不适用于交互式系统；数据格式必须在阶段间统一。

![数据流体系结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s10.png)

### （3）调用和返回体系结构

- 包括**主程序—子过程**结构、**分层**结构等；
- **构件**：程序模块/过程；
- **连接件**：**调用（call）与返回（return）** 机制；
- **特点**：控制流自上而下、单向进入、逐层返回；
- **优点**：结构清晰、易调试与维护；**缺点**：耦合偏强，复用小粒度模块较难。

![调用和返回体系结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s11.png)

### （4）面向对象体系结构

- 系统被看作**对象的集合**，每个对象都有自己的功能集合；
- **数据及作用在数据上的操作被封装成抽象数据类型（ADT）**；
- 只通过**接口**与外界交互，内部设计决策被封装起来；
- **构件**：**类和对象**；**连接件**：对象之间通过**函数调用、消息传递**实现交互。

### （5）层次体系结构

- 系统按**抽象层次**组织，每一层为上层提供服务、调用下层服务；
- **特点**：层间通过**定义良好的接口**交互，层内实现可替换；
- **优点**：易分层理解、易替换与复用、支持渐进式开发；
- **缺点**：层间调用带来**性能损耗**；层次的划分有时不自然。

![层次体系结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s13.png)

# 5. 构件结构示例：SafeHome

体系结构设计要产出**构件层次结构**。以 SafeHome 为例，顶层构件分解为：

| 构件 | 职责 |
|---|---|
| **SafeHome Executive（执行者）** | 总体控制与调度 |
| **Function selection（功能选择）** | 功能菜单与选择 |
| **External Communication Management（外部通信管理）** | 与外部世界的通信 |
| **Security Surveillance（安全监视）** | 安全监视主功能 |
| **Home management（住宅管理）** | 住宅设备管理 |
| **GUI（图形用户界面）** | 用户界面 |
| **Internet Interface（Internet 接口）** | 网络访问接口 |
| **Control panel processing（控制面板处理）** | 控制面板输入处理 |
| **Detector management（探测器管理）** | 探测器状态管理 |
| **Alarm processing（警报处理器）** | 报警事件处理 |

构件结构确定后，还需要进一步**细化**——把每个构件展开为子构件与接口（如 communication 子结构）。

# 6. 分析体系结构设计（六个步骤）

1. **收集场景**；
2. **引出需求、约束和环境描述**；
3. **描述**那些已被选择用于解决场景和需求的**体系结构风格/模式**——用三种视图刻画：**模块视图、过程视图、数据流视图**；
4. 通过**单独地考虑每个属性**来评估质量属性；
5. 针对特定的体系结构风格，确定**质量属性对各种体系结构属性的敏感性**；
6. 使用第 5 步的**敏感性分析**鉴定候选体系结构（即第 3 步开发的那些）。

> 记忆线索：**场景 → 需求约束 → 风格 → 质量属性 → 敏感性 → 定候选**。

# 7. 体系结构的分割

体系结构按要求的"**水平**"和"**垂直**"两个方向分割。

## 7.1 垂直分块（vertical partitioning）

- 为每个**主要功能**定义**单独的模块层次分支**；
- 使用**控制模块**协调各功能之间的通信。

> 类比：按业务功能切"竖条"——功能 1、功能 2、功能 3 各自一棵子树。

## 7.2 水平分块：分解（horizontal partitioning）

- 设计这样的决策，使**决策者和工作者是分层的**；
- **决策模块**应该驻留在该体系结构的**顶部**。

> 类比：按"管理层次"切"横条"——上层决策、下层执行。

## 7.3 架构设计方法的两个方向

| 方向 | 手段 | 结果 |
|---|---|---|
| **垂直方向** | **功能分解** | 得到**块**（模块层次分支） |
| **水平方向** | **服务分层** | 得到**层** |

![架构设计方法：垂直分块与水平分层](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_06_s20.png)

## 7.4 为什么要分割体系结构

- 导致软件**更容易测试**；
- 导致软件**更容易维护**；
- 导致**较少的负作用传播**；
- 导致软件**更容易扩展**。
