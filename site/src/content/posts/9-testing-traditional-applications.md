# 本章速览

- **易混**：白盒 = **结构**测试 = **逻辑驱动**；黑盒 = **功能**测试 = **数据驱动**。

---

# 1. 两种测试视角

任何工程化产品都可用两种方式之一测试：

| 视角 | 做法 |
|---|---|
| **外部视角**（黑盒） | 了解产品**要完成的指定功能**，执行测试以显示每个功能可操作，同时查找各功能中的错误 |
| **内部视角**（白盒） | 了解产品的**内部工作情况**，执行测试以确保"**所有的齿轮吻合**"——即内部操作依据规格说明执行，且对所有内部结构已充分测试 |

| 类型 | 别名 | 依据 | 别名来源 |
|---|---|---|---|
| **白盒测试** | **结构测试** / **逻辑驱动测试** | 程序的内部逻辑结构 | 由"逻辑"驱动用例设计 |
| **黑盒测试** | **功能测试** / **数据驱动测试** | 规格说明中的功能 | 由"数据（输入）"驱动用例设计 |

![黑盒测试——只见输入与输出，不见内部结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s04.png)

# 2. 白盒测试

## 2.1 基本路径测试法

> **定义**：在程序**控制流图**的基础上，通过分析程序的**环路复杂性**，导出**基本可执行路径集合**，从而设计测试用例。

**四个步骤**：

1. 以设计或源码为基础，画出相应的**流图**；
2. 确定所得流图的**环复杂性**；
3. 确定**线性独立路径的基本集合**；
4. 准备**测试用例**，强制执行基本集合中的每条路径。

![基本路径测试法概述](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s05.png)

## 2.2 控制流图的符号

| 符号 | 含义 |
|---|---|
| **◯** | 控制流图的一个**结点**（代表一条或多条语句） |
| **⟶** | **边**，表示控制流的方向 |
| **◇** | **判定结点 / 分支结点**（结点里含条件，所以有两条出边） |
| **⬚** | **区域**（region）：由边和结点所限定的范围 |

![程序流程图与控制流图的对应](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s07.png)

![由程序导出的控制流图](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s08.png)

## 2.3 环形复杂性（圈复杂度）V(G)

> **环复杂性**以图论为基础，可通过以下**三种方法之一**计算：

| 方法 | 公式/说法 |
|---|---|
| ① **区域法** | **区域的数量**与环复杂性相对应 |
| ② **边点法** | **V(G) = E − N + 2**，E 为流图的边数，N 为流图的结点数 |
| ③ **判定结点法** | **V(G) = P + 1**，P 为包含在流图 G 中的**判定结点数** |

> **V(G) 的意义**：它提供了组成**基本集的独立路径数目的上界**，并由此得出**覆盖所有程序语句所需测试数量的上界**。

![环路复杂度的计算](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s13.png)

## 2.4 独立路径

> **独立路径**：一条路径，**至少包含一条在定义该路径之前不曾用过的边**（至少引入程序的一个新处理语句集合或一个新功能条件）。

**示例**（对应下图的流图）：

- 路径 1：1-11
- 路径 2：1-2-3-4-5-10-1-11
- 路径 3：1-2-3-6-8-9-10-1-11
- 路径 4：1-2-3-6-7-9-10-1-11

> 对以上路径的遍历，就是**至少一次地执行了程序中的所有语句**。

## 2.5 完整例题：Sort 函数的基本路径测试

**第 1 步：根据代码画出控制流图**

```c
void Sort(int iRecordNum, int iType)
{
    int x = 0;
    int y = 0;
    while (iRecordNum-- > 0)
    {
        if (0 == iType) { x = y + 2; break; }
        else
            if (1 == iType) x = y + 10;
            else            x = y + 20;
    }
}
```

![第 1 步：根据代码画出程序控制流图](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s12.png)

**第 2 步：计算环路复杂度**

| 算法 | 计算过程 | 结果 |
|---|---|---|
| 边点法 | V(G) = **10 条边 − 8 个结点 + 2** | **4** |
| 判定结点法 | V(G) = **3 个判定结点 + 1** | **4** |
| 区域法 | 流图中**区域的数量** | **4** |

![第 2 步：计算环路复杂度](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s14.png)

**第 3 步：确定独立路径集合（共 4 条）**

- 路径 1：`4-14`
- 路径 2：`4-6-7-14`
- 路径 3：`4-6-9-10-13-4-14`
- 路径 4：`4-6-9-12-13-4-14`

![第 3 步：确定基本路径集合](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s15.png)

**第 4 步：设计测试用例**

| 用例 | iRecordNum | iType | 覆盖路径 | 说明 |
|---|---|---|---|---|
| TC1 | 0（或负数） | 任意 | 路径 1（4-14） | 循环体一次也不执行 |
| TC2 | 1 | 0 | 路径 2（4-6-7-14） | 进入 if 分支并 break |
| TC3 | 1 | 1 | 路径 3（4-6-9-10-13-4-14） | 走内层 if 的 then 分支 |
| TC4 | 1 | 2 | 路径 4（4-6-9-12-13-4-14） | 走内层 if 的 else 分支 |

> ⚠️ 考试提示：**V(G) = 4 就意味着至少要 4 个用例**才能覆盖全部独立路径。答题时"流图 → V(G) → 路径 → 用例"四步要写全。

## 2.6 图矩阵（Graph Matrix）

- 图矩阵是一种**方阵**，其大小（行与列的数量）**等于流图的结点数**；
- 每行、每列都对应于已标识的结点，矩阵中的项对应于**结点间的连接（边）**；
- 通过为每个矩阵项加入**连接权值**，图矩阵就成为测试期间**评估程序控制结构**的强有力工具。

## 2.7 控制结构测试

| 方法 | 说明 |
|---|---|
| **条件测试** | 通过检查程序模块中**包含的逻辑条件**进行测试用例设计 |
| **数据流测试** | 根据**变量的定义和使用位置**来选择程序测试路径 |

## 2.8 循环测试

按循环结构分四类，各有不同的测试策略：

| 类型 | 测试要点 |
|---|---|
| **简单循环** | 跳过循环、循环 1 次、典型次数、最大次数、最大次数 ±1 |
| **嵌套循环** | 由内向外逐层测试，固定外层参数 |
| **串接循环（Concatenated）** | 各循环独立时按简单循环处理；有依赖时按嵌套循环处理 |
| **非结构循环（Unstructured）** | 尽量重构为结构化后再测（否则无法充分测试） |

![循环测试的四类结构](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s20.png)

# 3. 黑盒测试

## 3.1 黑盒测试要回答的问题

- 如何测试功能的**有效性**？
- 如何测试系统的**行为和性能**？
- 哪种类型的**输入**会产生好的测试用例？
- 系统是否对**特定的输入值**特别敏感？
- 如何分离**数据类的边界**？
- 系统能承受什么样的**数据速率和数据量**？
- 特定类型的**数据组合**会对系统运行产生什么影响？

![黑盒测试——依据需求而非代码](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s21.png)

## 3.2 等价类划分

> **思路**：把输入域划分为若干**等价类**，每一类中取一个代表值测试即可——因为同一类中的输入对错误的暴露能力等价。

| 类型 | 定义 |
|---|---|
| **有效等价类** | 对于程序的规格说明来说，是**合理的、有意义的**输入数据构成的集合 |
| **无效等价类** | 对于程序的规格说明来说，是**不合理的、无意义的**输入数据构成的集合 |

> **设计原则**：设计测试用例时，要**同时考虑**有效等价类和无效等价类。

**例**：规格说明"…… 项数可以从 1 到 999 ……"

- 有效等价类：`1 ≤ 项数 ≤ 999`；
- 两个无效等价类：`项数 < 1` 或 `项数 > 999`。

**设计测试用例的三个步骤**：

1. **形成等价类表**，每一等价类规定一个**唯一的编号**；
2. 设计一个测试用例，使其**尽可能多地覆盖尚未覆盖的有效等价类**，重复此步直到所有有效等价类均被覆盖；
3. 设计**新**测试用例，使其**只覆盖一个无效等价类**，重复此步直到所有无效等价类均被覆盖。

> 差别记忆：**有效等价类可以"合并覆盖"，无效等价类必须"一个用例打一个"**——因为一个用例同时触发两个无效条件，就无法判断到底是哪个条件被拦住。

## 3.3 等价类划分完整例题：报表日期检查

> **题目**：某报表处理系统要求用户输入处理报表的日期，日期限制在 **2001 年 1 月至 2005 年 12 月**；日期不在此范围内则显示输入错误信息。系统日期规定由**年、月的 6 位数字字符**组成，前四位代表年，后两位代表月。请用等价类划分法设计测试用例。

**第一步：等价类划分**

| 输入条件 | 有效等价类 | 无效等价类 |
|---|---|---|
| **报表日期的类型及长度** | 6 位数字字符 (1) | 有非数字字符 (4) |
| | | 少于 6 个数字字符 (5) |
| | | 多于 6 个数字字符 (6) |
| **年份范围** | 在 2001～2005 之间 (2) | 小于 2001 (7) |
| | | 大于 2005 (8) |
| **月份范围** | 在 1～12 之间 (3) | 小于 1 (9) |
| | | 大于 12 (10) |

**第二步：为有效等价类设计测试用例**（一个用例覆盖 1、2、3）

| 测试数据 | 期望结果 | 覆盖范围 |
|---|---|---|
| `200105` | 输入有效 | 等价类 (1)(2)(3) |

**第三步：为每一个无效等价类至少设计一个测试用例**

| 测试数据 | 期望结果 | 覆盖范围 |
|---|---|---|
| `20015` | 输入无效 | 等价类 (5) 少于 6 位 |
| `200005` | 输入无效 | 等价类 (7) 年份小于 2001 |
| `200100` | 输入无效 | 等价类 (9) 月份小于 1 |
| （其余类似：`20010A` → (4)；`2001005` → (6)；`200605` → (8)；`200113` → (10)） | 输入无效 | 对应各无效等价类 |

## 3.4 边界值分析

> **定位**：边界值分析也是一种**黑盒测试方法**，是**对等价类划分方法的补充**。

**为什么有效**：长期的测试经验表明，**大量的错误发生在输入或输出范围的边界上**，而不是在输入范围的内部。因此针对各种边界情况设计测试用例，可以查出更多的错误。

**经典例子（三角形）**：输入三边长 A、B、C，须满足 `A>0、B>0、C>0、A+B>C、A+C>B、B+C>A` 才能构成三角形。若把六个不等式中的任何一个 **`>` 错写成 `≥`**，就不能构成三角形——问题恰出现在**容易被疏忽的边界附近**。

**边界的定义与取值原则**：

- 边界指相对于输入等价类和输出等价类而言，**稍高于其边界值及稍低于其边界值**的一些特定情况；
- 应选取**正好等于、刚刚大于、刚刚小于**边界的值作为测试数据，**而不是**选取等价类中的典型值或任意值。

> 与等价类的分工：**等价类负责"分区域"，边界值负责"打边缘"**。两者常配合使用。

## 3.5 对比测试（Back-to-Back Testing）

- 仅在**软件的可靠性是绝对关键**的情况下使用（如与人相关的系统）；
- 由**独立的软件工程团队**使用**相同的规格说明独立开发**应用系统的多个版本；
- 可以使用**相同的测试数据**测试每一个版本，以确保所有版本有确定的输出；
- 然后**并行执行**所有版本，**实时比较结果**，以确保一致性。

## 3.6 正交数组测试

- 适用条件：**输入参数的数量不多**，且**每个参数可取的值有明确的界定**；
- 做法：用**正交表**（如 L9 正交数组）在参数取值组合中**科学抽样**，用少量用例覆盖主要组合（"一次一个输入项"无法发现参数交互问题，全组合又太多）。

![正交数组测试（L9 正交表）](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_09_s34.png)

## 3.7 基于模型的测试

1. 分析软件已有的**行为模型**或创建一个行为模型（行为模型指明软件如何响应外部事件或刺激）；
2. **遍历行为模型**，标明促使软件状态之间进行转换的**输入**（输入将触发事件，使转换发生）；
3. 评估行为模型，标注软件在状态之间转换时所**期望的输出**；
4. **运行测试用例**；
5. 比较**实际结果与期望结果**，并根据需要进行调整。

# 4. 白盒 vs 黑盒（对比总结）

| 维度 | 白盒测试 | 黑盒测试 |
|---|---|---|
| **别称** | 结构测试、逻辑驱动测试 | 功能测试、数据驱动测试 |
| **依据** | 程序的内部结构与逻辑 | 需求/规格说明 |
| **关注** | 语句、分支、路径是否被覆盖 | 输入输出是否符合规格 |
| **典型方法** | 基本路径测试、条件测试、数据流测试、循环测试、图矩阵 | 等价类划分、边界值分析、对比测试、正交数组测试、基于模型的测试 |
| **主要指标** | 环路复杂度 V(G)、覆盖率 | 有效/无效等价类覆盖率、边界覆盖 |
| **盲区** | 无法发现"需求本身错了"、遗漏路径 | 无法知道内部哪些代码未被覆盖 |

> **结论**：两者互补——**黑盒保证"做对了事"，白盒保证"事做对了"**；实际项目中先黑盒（按需求设计用例）再白盒（补覆盖率）。
