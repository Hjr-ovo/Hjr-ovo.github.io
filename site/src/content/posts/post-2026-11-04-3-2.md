# 本章速览

- **三层台阶**：软件生命周期（分几个时期/阶段）→ 软件过程（一系列活动）→ 过程模型（活动的组织方式）。
- **易混**：增量 ≠ 演化；螺旋 = 瀑布 + 原型 + 风险分析。

# 1. 软件生命周期

## 1.1 定义

> **软件生命周期**：是指一个软件项目被提出并着手实施开始，到该软件报废或停止使用为止的**一段时间**。

## 1.2 三个时期

| 时期         | 基本任务                                                       | 负责人             |
| ---------- | ---------------------------------------------------------- | --------------- |
| **软件定义时期** | 确定总目标；研究可行性；分析确定客户需求；估算资源与成本；制定工程进度表（此时期工作统称**系统分析**）      | 系统分析员           |
| **软件开发时期** | 具体设计和实现前一时期定义的软件，由 4 个阶段组成：总体设计（概要/结构设计）、详细设计、编码与单元测试、综合测试 | 系统设计员、编程人员、测试人员 |
| **软件维护时期** | 对交付使用的系统进行升级和后期维护管理                                        | 系统维护员           |

> 其中：**前两个设计阶段 = 系统设计**，**后两个阶段 = 系统实现**。

## 1.3 六个阶段的具体任务

**（1）可行性研究与计划**

- 确定要开发软件系统的总目标；
- 给出功能、性能、可靠性及接口等方面的要求；
- 完成该任务的可行性研究；
- 估计可利用的资源（硬件、软件、人力等）、成本、效益、开发进度；
- 制定实施计划，连同可行性研究报告提交管理部门审查。

**（2）需求分析和定义**

- 对用户提出的要求进行分析并给出详细定义；
- 编写软件需求说明书（或系统功能说明书）及初步的系统用户手册；
- 提交管理机构评审。

> 本阶段的建模落点：概念设计 → 逻辑设计 → 物理设计；UML 分析建模（基于类的建模、面向流的建模、状态图、顺序图），对应 Data model / Function model / Behavior model。

**（3）软件设计**

- **概要设计**——把各项需求转换成软件的**体系结构**；结构中每个组成部分都是意义明确的模块，每个模块都和某些需求相对应；体系结构描述了构成要素及其之间的关系；
- **详细设计**——对每个模块要完成的工作进行具体描述，为源程序编写打下基础；
- 编写设计说明书，提交评审。

**（4）系统实现——编码**

- 把软件设计转换成计算机可接受的程序代码，即写成某种程序设计语言表示的"源程序清单"；
- 写出的程序应当**结构良好、清晰易读**，且与设计相一致。

**（5）测试阶段**

| 测试 | 目的 |
|---|---|
| **单元测试** | 查找各模块在功能和结构上存在的问题并加以纠正 |
| **集成测试** | 将已测试过的模块按一定顺序组装起来 |
| **确认测试** | 按规定的各项需求逐项进行有效性测试，决定软件是否合格、能否交付用户 |

**（6）运行/维护**

| 维护类型 | 触发原因 |
|---|---|
| **改正性维护** | 运行中发现了软件中的错误需要修正 |
| **适应性维护** | 为适应变化了的软件工作环境需做适当变更 |
| **完善性维护** | 为增强软件的功能需做变更 |

# 2. 软件过程与过程框架

## 2.1 什么是软件过程

> **软件过程**定义了软件生产的一系列**活动**，这些活动贯穿于软件开发的整个过程。

## 2.2 过程框架（五个框架活动）

| 框架活动 | 子活动 |
|---|---|
| **沟通 Communication** | 项目启动、需求获取 |
| **策划 Planning** | 估算、进度计划、项目跟踪 |
| **建模 Modeling** | 分析（requirements analysis）、设计（design） |
| **构建 Construction** | 代码生成（code generation）、测试（testing） |
| **部署 Deployment** | 交付、支持、反馈 |

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121308939.png)


## 2.3 过程流

过程流描述框架活动在时间上的**组织方式**（线性、迭代、并行、演化……），不同过程流就对应不同的过程模型——这是理解第 4 节的关键线索。

# 3. 过程评估与改进

## 3.1 四种主要方法

| 方法 | 定位与要点 |
|---|---|
| **CMMI 标准评估方法**（用于过程改进） | 提供**五步**过程评估模型：启动、诊断、建立、执行、学习 |
| **CMM 评估**（用于组织内部改进） | 采用 SEI 的 CMM 作为评估依据，提供诊断方法，分析开发机构相对**成熟度** |
| **SPICE**（ISO/IEC 15504） | 定义软件过程评估的一系列要求，帮助组织建立**客观评价体系**，评估已定义软件过程的有效性 |
| **ISO 9001:2000** | 通用标准，任何希望提高产品/系统/服务整体质量的组织都可采用，可直接应用于软件组织 |

## 3.2 CMM 与 CMMI 的关系

- **CMM**（Capability Maturity Model，能力成熟度模型）：卡耐基梅隆大学**软件工程研究院（SEI）**受美国国防部委托制定的软件过程改良、评估模型，也称 SEI SW-CMM。
- CMM 的成功促使其他学科相继开发类似模型（系统工程、需求工程、人力资源、集成产品开发、软件采购等）。
- **CMMI**（CMM Integration，能力成熟度模型集成）：美国国防部的设想——把现在所有的、以及将被发展出来的各种能力成熟度模型**集成到一个框架**中。该框架有两个功能：① 软件采购方法的改革；② 建立一种从集成产品与过程发展角度出发、包含健全系统开发原则的过程改进。**就软件而言，CMMI 是 SW-CMM 的修订本。**
- CMMI 是目前世界公认的软件产品进入国际市场的**通行证**，不仅是对产品质量的认证，更是一种软件过程改善的途径。

## 3.3 CMMI 的五个能力等级

| 级别 | 名称 | 核心特征 |
|---|---|---|
| 1 | **已执行级** Performed | 过程能完成必要工作，但成功依赖个人努力 |
| 2 | **已管理级** Managed | 过程有计划、有监控、有制度，项目级可重复 |
| 3 | **已定义级** Defined | 组织级标准过程，项目按裁剪后的标准过程执行 |
| 4 | **已定量管理级** Quantitatively Managed | 用统计与量化手段管理过程性能 |
| 5 | **已优化级** Optimized | 持续改进，主动识别并消除过程缺陷 |

> **执行 → 管理 → 定义 → 定量 → 优化**，逐级递进，不可跳跃。

# 4. 过程模型

## 4.1 瀑布模型（The Waterfall Model）

线性顺序模型的代表，阶段严格串行：可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码与模块测试 → 集成与系统测试 → 交付与维护。

**三个基本观点（特点）**：

1. **阶段间的顺序性和依赖性**——前一阶段完成并评审通过后，才能进入下一阶段；
2. **推迟实现的观点**——尽量晚地进入编码，把问题留在前面阶段解决；
3. **质量保证的观点**——以文档和评审作为各阶段的质量闸门。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121345731.png)


| 优点                        | 缺点                         |
| ------------------------- | -------------------------- |
| 通过设置**里程碑**，明确每阶段的任务与目标   | **缺乏灵活性**，不能适应用户需求的改变      |
| 可为每阶段制定开发计划、进行成本预算、组织开发力量 | 开始阶段的**小错误被逐级放大**，可能导致产品报废 |
| 通过**阶段评审**，将开发过程纳入正确轨道    | **返回上一级**的开发需要十分高昂的代价      |
| 强迫开发人员采用**规范化**的方法        | 随规模与复杂性增加，产品成功机率大幅下降       |

> 适用：需求明确、稳定、技术成熟的项目。

## 4.2 V 模型

瀑布模型的变体，把"分解"（左侧：需求→设计→编码）与"验证"（右侧：单元→集成→系统→验收测试）按层级一一对应，强调**测试与开发阶段的对应关系**，测试计划应尽早编写。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121358075.png)


## 4.3 演化模型：原型开发

先快速构造一个可运行的原型，通过用户试用澄清模糊需求，再据此开发正式产品。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121406408.png)


**优点**

- 开发者与用户充分交流，可澄清模糊需求，需求定义比其他模型好得多；
- 开发过程与用户培训过程同步；
- 为用户需求的改变提供了充分余地；
- 开发风险低、产品柔性好、开发费用低、时间短；系统易维护，对用户更友好。

**缺点**

- 在不熟悉的领域中开发人员不易分清主次，原型不切题；
- 产品原型在一定程度上**限制了开发人员的创新**；
- 随更改次数增多，次要部分越来越大，**"淹没"了主要部分**；
- 原型过快收敛于需求集合，忽略了一些基本点；
- 资源规划和管理较困难，随时更新文档也带来麻烦；
- 只注意原型是否满意，**忽略了原型环境与用户环境的差异**。

## 4.4 演化模型：螺旋

1988 年 **Barry Boehm** 正式发表，把**瀑布模型与快速原型模型结合起来，强调风险分析**，特别适合大型复杂系统。每一轮螺旋包含四象限：制定计划 → 风险分析 → 实施工程 → 客户评估。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121451544.png)


**优点**

- 支持用户需求的动态变化，具有良好可扩充性与可修改性；也支持可维护性——每次维护只是沿螺旋继续多走一两个周期；
- 原型易于用户与开发人员共同理解需求，可作为继续开发的基础，方便用户参与关键决策；
- 为项目管理人员及时调整管理决策提供方便，从而降低开发风险；
- 支持需求不明确、特别是大型软件系统的开发，并支持面向规格说明、面向过程、面向对象等多种开发方法。

**缺点**

- 若每次迭代效率不高、迭代次数过多，将**增加成本并推迟提交时间**；
- 需要相当丰富的**风险评估经验和专门知识**，要求开发队伍水平较高。

> 记忆要点：螺旋 = 瀑布的**系统性** + 原型的**迭代性** + 独有的**风险分析**。它是"风险驱动"的模型。

## 4.5 演化模型：协同（Concurrent）

用状态图描述工程活动：任一活动或任务处于 **none（非活动状态）→ Under development（正在开发）→ Under review（正在评审）→ Under revision（正在修改）→ Baselined（已建立基线）→ Done（完成状态）** 之一，多团队可并行推进并随时查看状态。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121424079.png)


**优点**：① 可用于所有类型的软件开发，尤其多个团队共同参与一个工程时，对 C/S 结构更有效；② 可随时查阅到开发的状态。

## 4.6 增量模型

融合了**线性顺序（瀑布）模型的基本成分**和**原型的迭代特征**，采用随日程时间进展而**交错的线性序列**——每一个线性序列产生软件的一个可发布的"**增量**"。

> 适用：迫切需要为用户先提供一套功能有限的产品，在后续产品中再细化或拓展。

**优点**

1. 人员分配灵活——开始不必投入大量人力，核心产品受欢迎时可加人做下一个增量；
2. 配备人员无法在期限内完成产品时，提供"先推出核心产品"的途径，先发布部分功能，对客户起"镇静剂"作用；
3. 能占据一定的市场；
4. 早期获得投资回报，较易维护；
5. 能有效规避风险。

**缺点**

1. 各构件逐渐并入已有体系结构，加入构件**必须不破坏已构造好的部分**——要求软件具备开放式的体系结构；
2. 需求变化不可避免时，增量模型的灵活性虽优于瀑布与快速原型，但**很容易退化为边做边改模型**，使软件过程控制失去整体性。

## 4.7 RAD 模型

RAD 是一个**线性顺序**的软件开发模型，是线性顺序模型的"**高速**"变种，强调极短的开发周期。通过**基于构件的建造方法**获得快速开发，使开发组能在很短时间内（如 **60～90 天**）创建出"功能完善的系统"。

## 4.8 喷泉模型（Fountain Model，面向对象）

**特点**

- 软件系统可维护性较好；
- 各阶段**相互重叠**，表明面向对象开发方法各阶段间的**交叉和无缝过渡**；
- 具有**增量开发**特性——分析一点、设计一点、实现一点、测试一点，使相关功能随之加入演化的系统；
- 很自然地**支持软部件的重用**。

![image.png](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/20261104121433719.png)


## 4.9 其他过程模型与统一过程（UP）

| 模型/方法 | 要点 |
|---|---|
| **基于构件的开发** | 使软件复用成为可能，是一项发展目标 |
| **形式化方法** | 强调需求的**数学规范说明** |
| **面向方面的软件开发（AOSD）** | 为定义、说明、设计和构建"方面"提供过程与方法 |
| **统一过程（UP）** | "**用例驱动、以架构为核心、迭代并且增量**"，与 UML 紧密结合 |

UP 的起始阶段：通过与客户和最终用户协作，定义软件的基本业务需求（用例），提出系统的大致框架（主要功能），并制定开发计划以保证项目具有迭代和增量特性。

# 5. 各模型对比

| 模型 | 过程结构 | 最大特点 | 主要风险/缺点 | 适用场景 |
|---|---|---|---|---|
| **瀑布** | 线性顺序 | 阶段清晰、文档与评审严格 | 不灵活、返工代价高 | 需求明确稳定 |
| **V 模型** | 线性 + 测试对应 | 测试与开发层级一一对应 | 同上 | 强调验证与确认 |
| **原型** | 迭代（快速） | 澄清模糊需求 | 易被原型束缚、忽略环境差异 | 需求不清、用户参与度高 |
| **螺旋** | 迭代（风险驱动） | 每轮含**风险分析** | 需风险评估经验、成本高 | 大型复杂、高风险项目 |
| **增量** | 交错线性序列 | 分增量交付、早期回报 | 要求开放体系结构、易退化为边做边改 | 需尽早投放市场 |
| **RAD** | 线性（高速） | 基于构件、周期极短（60～90 天） | 依赖可复用构件与人员素质 | 中小规模、构件可复用 |
| **喷泉** | 阶段重叠 | 面向对象、无缝过渡、支持重用 | 阶段界限模糊、管理难度大 | OO 项目 |
| **协同** | 并行状态驱动 | 多团队并行、状态可视 | 协调成本高 | 多团队、C/S 结构 |
