> **这篇文章是示例数据**，用于验证站点排版效果。
> 内容以本站的技术选型为背景，但经过简化，**不要当作 Astro 教程使用**。

## 环境

- Astro 7.3.3
- Node.js v24.15.0
- Windows 11

## 静态站的本质

动态站每次有人访问，服务器现场查数据库、拼 HTML 再返回。
静态站反过来：**在构建时就把所有 HTML 生成好**，访问时只是把文件递出去。

```text
构建时（一次）                     访问时（每次）
Markdown  →  HTML 文件    →   把现成的 HTML 直接返回
```

好处是快、便宜、不需要服务端；代价是**内容更新必须重新构建**。

## 一次构建的完整链路

以本站为例，跑 `npm run build` 之后发生的事：

### 第一步：扫描内容目录

```text
src/content/posts/*.md
```

Astro 把这些文件当成一个「内容集合」，逐个读取 frontmatter 和正文。

### 第二步：校验 frontmatter

这一步是关键 —— 字段类型不对会**直接报错并中断构建**：

```text
posts → xxx data does not match collection schema.
pubDate: Expected type "date", received "object"
```

比起悄悄忽略、等到线上页面渲染出奇怪结果，构建时就失败要好得多。

### 第三步：生成路由

`pages/` 下的每个文件对应一个网址：

| 源文件 | 生成的网址 |
|---|---|
| `pages/index.astro` | `/` |
| `pages/posts/[...slug].astro` | 由 `getStaticPaths()` 决定，一篇文章一条 |

### 第四步：渲染

Markdown 转 HTML，代码块交给语法高亮器着色，套上布局模板。

### 第五步：输出到 `dist/`

产物是一堆静态文件，可以直接扔到任何能托管静态资源的地方。

## 一个容易搞混的地方

| 目录 | 性质 | 要不要进 Git |
|---|---|---|
| `src/` | 源码 | **要** |
| `public/` | 源码（原样拷贝到网站根目录） | **要** |
| `dist/` | 构建产物 | **不要** |

`public/` 最容易被误当成产物 —— 它其实是**手写的源文件**，
构建时只是被原样搬过去，不参与任何处理。

## 小结

1. 静态站把「渲染」从访问时提前到构建时
2. 构建时能做校验，所以错误暴露得早
3. `public/` 是源码不是产物，这一点反直觉但很重要
