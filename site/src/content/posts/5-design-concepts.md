# 本章速览

- **重点**：**信息隐蔽**、**模块化**、**功能独立（内聚 / 耦合）**——这三个概念贯穿后面所有设计章节。
- **易混**：设计 ≠ 编码；内聚是"模块内部"，耦合是"模块之间"。

---

# 1. 什么是好的软件设计

Lotus 1-2-3 创始人 **Mitch Kapor** 在《Dr. Dobbs》杂志发表"**软件设计宣言**"，认为良好的软件设计应该展示三点：

| 品质                  | 含义                      |
| ------------------- | ----------------------- |
| **坚固（Solid）**       | 程序应该展示出**不含任何妨碍其功能的缺陷** |
| **适用（Suitable）**    | 程序应该**符合开发的目标**         |
| **愉悦（Pleasurable）** | **使用程序的体验应是愉快的**        |

> 记忆：**坚固（对质量）+ 适用（对目标）+ 愉悦（对用户）**。

**设计的定义**：将用户需求准确地转化为软件设计模型或文档的方法。

---

# 2. 软件设计在软件工程中的位置

设计处在"需求 → 设计 → 构建"的中间位置，要回答两个问题：

- **"做到什么程度？"（To what degree?）**——即质量目标；
- **"如何达到这个程度？"（How to reach the degree?）**——即设计方法与模型。

![软件设计在软件工程中的位置](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s03.png)

## 从分析模型到设计模型

**分析模型的四类元素 → 设计模型的四种设计**：

| 分析模型元素 | 对应设计 |
|---|---|
| 面向流的元素（数据流图、控制流图、处理叙述） | **构件级设计**（Component-Level Design） |
| 基于场景的元素（用例文本、用例图、活动图、泳道图） | **体系结构设计**（Architectural Design） |
| 基于类的元素（类图、分析包、CRC 模型、协作图） | **数据/类设计**（Data/Class Design） |
| 行为元素（状态图、顺序图） | **接口设计**（Interface Design） |

> 一句话：**分析模型是"问题"的模型，设计模型是"解"的模型**，四类分析元素各自演化成一种设计。

---

# 3. 设计与质量（三条硬性要求）

1. 设计必须实现所有包含在需求模型中的**明确需求**，而且必须满足利益相关者期望的所有**隐含需求**；
2. 对那些生成代码、进行测试以及随后维护软件的人而言，设计必须是**可读的、可理解的指南**；
3. 设计必须提供软件的**全貌**，从实现的角度说明**数据域、功能域和行为域**。

---

# 4. 设计原则（Davis 十条）

1. 设计过程中不要有"**井蛙之见**"；
2. 设计应**起源于分析模型**；
3. 设计**不要白费力气做重复工作**；
4. 在软件和真实世界的问题之间，设计应能"**最小化知识距离**"；
5. 设计应表现出**一致性和集成性**；
6. 设计结构应**适应变化**；
7. 即使遇到数据、事件或操作条件异常时，设计结构应能**温和处理**；
8. **设计不是编码，编码不是设计**；
9. **创建设计时就应对其质量进行评估**，而不是创建之后；
10. **评审设计**以最小化概念上的（语义的）错误。

# 5. 设计的十一个基本概念

| 概念        | 要点                  |
| --------- | ------------------- |
| **抽象**    | 数据、过程、控制三个层面的抽象     |
| **体系结构**  | 软件的**整个结构**         |
| **模式**    | 已证实的解决方案的"**精髓**"   |
| **关注点分离** | 复杂问题被分解为若干块后更容易处理   |
| **模块化**   | 数据和功能的**划分**        |
| **信息隐蔽**  | 控制**接口**，隐藏实现细节     |
| **功能独立**  | **专一的功能**和**低耦合**   |
| **求精**    | 所有抽象**精化**的细节（逐步细化） |
| **方面**    | 一种理解"全部需求如何影响设计"的机制 |
| **重构**    | 一种**简化设计的重新组织**技术   |
| **设计类**   | 提供设计细节，使分析类得以实现     |

（另：面向对象设计概念见课件附录 II，含继承、消息、多态等。）

---

# 6. 关注点分离

- 任何复杂问题，如果被分解为可以**独立解决和（或）优化**的若干块，该复杂问题就能更容易地被处理；
- 一个**关注点**是一个特征或行为，被指定为软件需求模型的一部分；
- 通过将关注点分割为更小的关注点，解决问题所需的**工作量和时间**都会减少。

---

# 7. 模块化

> "**模块化是软件的单一属性，它使程序能被智能化地管理**"（Myer, 1978）

- 软件工程师**难以掌握单块软件**（由单独模块构成的大程序）；
- 原因：其**控制路径的数量、引用的跨度、变量的数量和整体的复杂度**，使得理解这样的软件几乎不可能；
- 几乎所有情况下，为了更容易理解，都应将设计**划分成许多模块**，由此**构建软件所需的成本也随之降低**。

> 注意：模块并非"越多越好"——模块划分有成本（接口、集成），存在**最优模块数**；过度细分反而抬高总成本。

---

# 8. 信息隐蔽

**基本思想**：模块应该对外**隐藏**其内部的设计决策，只通过受控接口与外界通信。

需要隐藏的**典型设计决策**：

- 算法（algorithm）；
- 数据结构（data structure）；
- 外部接口的细节（details of external interface）；
- 资源分配策略（resource allocation policy）。

![信息隐蔽——隐藏具体的设计决策](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s10.png)

**为什么要信息隐蔽**：

- 减少"**负效应**"的可能性；
- **限制全局影响局部的设计决策**；
- 强调通过**控制接口**通信；
- **不提倡使用全局数据**；
- 导致**封装**——高质量设计的属性；
- 最终导致**高质量软件**。

# 9. 功能独立：内聚与耦合（重点）

> **功能独立**：通过开发具有"**专一**"功能和"**避免**与其他模块过多交互"的模块来实现。它是**模块独立程度**的度量，由两个定性标准衡量：**内聚性**与**耦合性**。

![模块独立程度的两个度量标准](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s13.png)

## 9.1 内聚性（Cohesion）

> **内聚性**显示了某个模块**相关功能的强度**。一个内聚的模块执行一个独立的任务，与程序的其他部分只需要很少的交互——**理想情况下只完成一件事情**。

模块内部元素在功能上相互关联的强度。按由强到弱（由高到低）：

| 等级  | 名称           | 说明                            |
| --- | ------------ | ----------------------------- |
| 最高  | **功能内聚**     | 模块内所有元素共同完成**单一功能**，缺一不可      |
| ↓   | **分层内聚**     | 模块内元素按层次组织，上层使用下层             |
| ↓   | **通信内聚**     | 模块内元素操作**同一数据结构**             |
| ↓   | **顺序（有序）内聚** | 模块内处理元素**顺序执行**，前一个的输出是后一个的输入 |
| ↓   | **过程内聚**     | 元素按**特定次序**执行（但不共享数据）         |
| ↓   | **时间内聚（暂时）** | 元素因**在同一时间段**执行而聚集（如初始化模块）    |
| 最低  | **实用内聚（偶然）** | 元素之间**没有实质关系**，只是被凑在一起        |

> **设计目标：高内聚**——模块在软件过程中完成单一的任务。

## 9.2 耦合性（Coupling）

> **耦合性**显示了**模块间的相互依赖性**，是程序结构中各模块之间相互关联的度量。它取决于：模块之间**接口的复杂程度**、**调用模块的方式**，以及**通过接口传递的信息**。

按由强到弱（由高到低）：

| 等级  | 名称           | 说明                              |
| --- | ------------ | ------------------------------- |
| 最强  | **内容耦合**     | 一个模块直接**访问/修改另一个模块的内部数据**或代码    |
| ↓   | **共用（公共）耦合** | 多个模块共享**全局数据**                  |
| ↓   | **控制耦合**     | 一个模块向另一个模块传递**控制信息**（开关量）       |
| ↓   | **标记耦合**     | 通过**参数（记录/结构）** 传递，且被调模块只用其中一部分 |
| 最弱  | **数据耦合**     | 只通过**简单数据参数**交换信息               |

其他耦合形式（课件列出）：**历程调用耦合**（routine call，模块间通过调用相联系）、**类型使用耦合**（type use，一个构件使用另一个构件定义的数据类型）、**包含或导入耦合**（inclusion/import，通过 include/import 引入）、**外部耦合**（external，受外部环境强加的约束）。

![耦合的类型](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s14.png)

## 9.3 内聚与耦合的关系

- 二者**密切相关**：与其他模块**强耦合**的模块意味着**弱内聚**；**强内聚**的模块意味着与其他模块间**松散耦合**；
- 二者都是模块独立性的**定性标准**，都反映模块独立性的良好程度；
- 但**耦合是直接的主导因素**，内聚则辅助耦合共同对模块独立性进行衡量。

> **设计总目标：力争强内聚、弱耦合。**（记这八个字就够了）

# 10. 重构

> **定义（Fowler）**：重构是使用这样一种方式改变软件系统的过程——**不改变代码（设计）的外部行为，而是改进其内部结构**。

重构时检查现有设计的以下不足：

- **冗余性**；
- **没有使用的设计元素**；
- **低效的或不必要的算法**；
- **拙劣的或不恰当的数据结构**；
- 其他设计不足——修改这些不足以获得更好的设计。

# 11. 面向对象设计概念

| 概念 | 要点 |
|---|---|
| **设计类** | 提供设计细节，使分析类得以实现；分为**实体类、边界类、控制类** |
| **继承** | 超类的所有特点**立即被所有子类继承** |
| **消息** | 刺激接收对象产生某种行为 |
| **多态** | 一种可以**显著减少扩展已存在设计**的特性 |

# 12. 软件设计的元素与设计模型的维度

![软件设计的元素](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s19.png)

**设计模型的维度**（数据 / 体系结构 / 接口 / 构件）：

| 维度 | 涉及元素 |
|---|---|
| **数据设计** | CRC 模型、协作图、数据流图、控制流图、处理叙述 |
| **体系结构设计** | 子系统、协作图、构件图、设计类、活动图、顺序图（接口元素、构件级元素、部署级元素） |
| **接口设计** | 导航设计、图形用户界面设计 |
| **构件级设计** | 设计类、活动图、顺序图等 |

![设计模型的维度](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s20.png)

**从工程管理角度看，软件设计包括**：

| 阶段 | 内容 |
|---|---|
| **概要设计** | 将软件需求转化为**数据结构和软件的体系结构** |
| **详细设计**（即构件设计） | 通过对软件结构表示进行**细化**，得到软件的详细数据结构和算法 |

![概要设计与详细设计](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_05_s21.png)

> 补充一句常考的话：**从技术角度**看，软件设计分为**数据设计、体系结构设计、接口设计、构件级（过程）设计**四种——这正是"设计模型的维度"。
