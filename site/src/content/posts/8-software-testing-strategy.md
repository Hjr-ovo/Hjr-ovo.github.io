# 本章速览

- **重点**：**集成测试的四种策略**（自顶向下 / 自底向上 / 混合增量 / 三明治）及其优缺点；回归测试与冒烟测试的用途。
- **必知**：单元测试要测什么；调试与测试的区别；调试的四种技术。

---

# 1. 什么是软件测试

> **定义**：测试是在**交付产品给最终用户之前**，带着**特定的目的**在**运行程序的过程**中发现错误。

三个限定词都是考点：**交付前**（时机）、**有目的**（不是盲试）、**运行程序**（动态，区别于静态评审）。

---

# 2. 策略性方法（五点）

1. 为完成有效的测试，应该进行**有效的技术评审**——通过评审，**许多错误可以在测试开始之前排除**；
2. 测试**开始于构件层**，然后向外"**延伸**"到整个基于计算机系统的集成；
3. **不同的测试技术**适用于不同的软件工程方法和不同的时间点；
4. 测试由**软件开发人员和**（对大型项目而言）**独立的测试组**执行；
5. 测试和**调试是不同的活动**，但任何测试策略都必须包括调试。

# 3. 测试的四个层次

| 层次 | 测试对象 | 回答的问题 |
|---|---|---|
| **单元测试** | 单个构件/模块 | 这个模块自己对不对？ |
| **集成测试** | 组装后的模块集合 | 模块拼起来能不能协同工作？ |
| **确认测试**（Validation） | 整个软件 | 是否满足**需求**？ |
| **系统测试**（System） | 软件 + 其他系统元素 | 放进真实系统环境能否正常工作？ |

![软件测试过程](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s05.png)

> 图中所示的三类测试（确认测试、系统测试、验收测试）**可能交叉与前后互换**，并非绝对串行。

## 3.1 "小的测试"与"大的测试"

- 测试策略是"先**小**后**大**"：从构件开始，逐步扩展到集成；
- **传统软件**：最初关注**模块（构件）**，随后关注**集成模块**；
- **面向对象软件**：关注点从"单独模块"变化到一个**包含属性和操作、并暗含沟通与协作的面向对象类**。

## 3.2 制定测试策略要考虑的八个问题

1. 早在测试之前，就要以**量化的方式规定产品需求**；
2. **明确地陈述测试目标**；
3. 了解软件的用户，并为**每类用户建立用户描述**；
4. 指定强调"**快速周期测试**"的测试计划；
5. 建立能够**测试自身**的"健壮"软件；
6. 测试之前，利用有效的**正式技术评审**作为过滤器；
7. 实施正式技术评审以**评估测试策略和测试用例本身**；
8. 为测试过程建立一种**持续的改进方法**。

# 4. 单元测试

单元测试聚焦于软件设计的最小单位——**构件（模块）**，重点检查四类内容：

| 检查项 | 说明 |
|---|---|
| **模块接口** | 参数传递、调用方式是否正确 |
| **局部数据结构**（local data structures） | 变量定义、初始化、作用域 |
| **独立路径**（independent paths） | 各条执行路径都要走到 |
| **边界条件**（boundary conditions） | 边界值、极限值、异常输入 |
| **错误处理路径**（error handling paths） | 出错时能否正确响应 |

![单元测试的环境（驱动模块与桩模块）](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s08.png)

![单元测试要检查的内容](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s09.png)

> **重要概念**：单元测试需要**驱动模块（driver）** 模拟主程序调用被测模块，需要**桩模块（stub）** 模拟被测模块所调用的下层模块。

# 5. 集成测试策略（重点）

![集成测试的常见策略](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s10.png)

## 5.1 自顶向下集成（Top-Down Integration）

- 从**主控模块（顶层）**开始，沿控制层次向下集成；
- 顶层模块用**桩模块（stub）** 测试，然后**一次替换一个桩模块**，采用"**深度优先**"方式；
- 当集成新的模块时，**重新运行某些测试子集**（回归测试）。

| 优点 | 缺点 |
|---|---|
| 早期验证主要控制逻辑 | 需要大量**桩模块** |
| 能在早期发现上层设计缺陷 | 底层模块的测试被推迟，底层问题暴露晚 |

![自顶向下集成](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s11.png)

## 5.2 自底向上集成（Bottom-Up Integration）

- 从**最底层（工作模块）**开始，把**工作模块分组为"簇（build）"** 进行集成与测试；
- 用**驱动模块（driver）** 替代上层调用，**一次替换一个驱动模块**，采用"深度优先"方式。

| 优点 | 缺点 |
|---|---|
| 不需要桩模块，**驱动模块好写** | 直到最后才能验证**主控逻辑** |
| 底层模块测试充分，问题早暴露 | 需要一个"骨架"程序才能跑起来 |

![自底向上集成](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s12.png)

## 5.3 混合增量式测试

> 把**自顶向下**与**自底向上**两种方式结合起来进行集成和测试，**兼具两者优点、摒弃其缺点**。

两种常见方式：

1. **衍变的自顶向下增量式测试**：强化对**输入/输出模块**和**引入新算法模块**的测试，先自底向上集成为功能相对完整且相对独立的**子系统**，然后由主模块开始**自顶向下**进行增量式测试；
2. **自底向上—自顶向下的增量式测试**：对含**读操作**的子系统**自底向上**直至根节点模块进行集成与测试，对含**写操作**的子系统做**自顶向下**的集成与测试。

## 5.4 三明治测试（Sandwich Testing）

混合增量式的典型形态：**上层用桩模块自顶向下测**，**下层工作模块按簇自底向上集成**，中间汇合——形似三明治。

![三明治测试](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s14.png)

## 5.5 四种集成策略对比

| 策略 | 起点 | 辅助模块 | 主要优点 | 主要缺点 |
|---|---|---|---|---|
| **自顶向下** | 顶层主控模块 | 桩模块 | 早验证控制逻辑 | 桩模块多、底层问题暴露晚 |
| **自底向上** | 底层工作模块 | 驱动模块 | 驱动好写、底层测充分 | 主控逻辑验证晚 |
| **混合增量** | 双向 | 桩 + 驱动 | 兼顾两者优点 | 组织管理复杂 |
| **三明治** | 上下同时 | 桩 + 驱动 | 上下并行、周期短 | 中间层汇合处易出问题 |

# 6. 回归测试（Regression Testing）

> **定义**：回归测试**重新执行已测试过的某些子集**，以确保变更**没有传播不期望的副作用**。

- 无论什么时候修正软件，软件配置的某些方面（**程序、文档或支持数据**）也会发生变更；
- 回归测试有助于保证变更（由于测试或其他原因）**不引入无意识行为或额外的错误**；
- 实施方式：**手工**重新执行所有测试用例的子集，或利用**捕捉/回放工具自动**进行。

---

# 7. 冒烟测试（Smoke Testing）

- 是**为生产软件创建"每日构建"** 的一种常见方法；
- **三个步骤**：
  1. 将已转换为代码的软件构件集成到"**构建**"中去——一个构建包括**所有数据文件、库、可复用的模块**以及实现一个或多个产品功能所需的工程化构件；
  2. 设计一系列测试以**暴露影响构建正确完成其功能的错误**——目的是发现极有可能造成项目延迟的"**业务阻塞**"错误；
  3. **每天**将该构建与其他构建及整个软件产品（以其当前形式）集成起来进行冒烟测试——这种集成方法可以是自顶向下，也可以自底向上。

> 一句话区分：**回归测试防"改坏了"；冒烟测试防"今天根本跑不起来"。**

---

# 8. 高阶测试

| 类型 | 关注点 / 做法 |
|---|---|
| **确认测试** | 关注点是**软件需求** |
| **系统测试** | 关注点是**系统集成** |
| **α / β 测试** | 关注点是**客户使用**（α 在开发者现场由用户测；β 在用户现场由用户测） |
| **恢复测试** | 通过各种方式**强制地使软件发生故障**，并验证其能适当恢复 |
| **安全测试** | 验证建立在系统内的**保护机制**是否能够实际保护系统不受非法入侵 |
| **压力测试** | 以**非正常的数量、频率或容量**方式执行系统 |
| **性能测试** | 用来测试软件在**集成环境中的运行性能** |

---

# 9. 调试：一个诊断过程

> **测试与调试的区别**：测试是**发现**错误的活动，调试是**定位并修正**错误的活动。测试策略必须包含调试。

![调试过程（诊断模型）](https://raw.githubusercontent.com/Hjr-ovo/Picture-host/main/picture/Chapter_08_s18.png)

**四种常用调试技术**：

| 技术 | 思路 | 适用 |
|---|---|---|
| **蛮干法（测试法）** | 靠打印语句、内存转储等大量信息"淹没"问题 | 最后手段，效率低 |
| **回溯法** | 从出错处沿控制流**反向追踪**到源头 | 程序规模小、路径清晰 |
| **归纳法** | 从**症状与线索**出发归纳假设，再验证 | 中等规模、线索较多 |
| **排除法** | 逐个**排除**可疑原因，二分缩小范围 | 原因域可枚举 |
