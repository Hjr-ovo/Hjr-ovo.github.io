## 环境

- 任意支持 HTTP/1.1 的浏览器
- 一个能返回 `Cache-Control` 与 `ETag` 的静态资源服务

## 两种缓存策略

浏览器拿到响应后，缓存是否可用分两条路径：

| 策略 | 判断依据 | 是否发请求 |
|---|---|---|
| 强缓存 | `Cache-Control: max-age` / `Expires` | **不发**，直接用本地副本 |
| 协商缓存 | `ETag` / `Last-Modified` | 发请求，服务端可能返回 304 |

## 判断流程

```text
浏览器要请求某资源
      │
      ├─ 本地有缓存？
      │     └─ 无 → 直接请求
      │
      └─ 有 → 强缓存还在有效期内？
            ├─ 是 → 直接用本地副本（不发请求）
            └─ 否 → 带 If-None-Match 发协商请求
                  ├─ 服务端返回 304 → 用本地副本，只更新头部
                  └─ 服务端返回 200 → 用新内容替换缓存
```

## 关键点

`Cache-Control` 可以叠加多个指令：

```http
Cache-Control: public, max-age=3600, must-revalidate
```

- `max-age` 决定强缓存的有效期（秒）
- `no-cache` 不是「不缓存」，而是「**每次都要协商**」—— 这是最容易记反的一个
- `no-store` 才是真正的不缓存

## 一个常见误区

很多人以为 `ETag` 是给强缓存用的。实际上：

```text
Cache-Control  -> 决定「要不要发请求」
ETag           -> 决定「发了请求之后，能不能只用头部不用正文」
```

两者解决的是不同层次的问题，不是二选一。

## 小结

1. 先看强缓存有没有过期，没过期就不发请求
2. 过期了发协商请求，靠 `ETag` 判断内容是否真的变了
3. `no-cache` 与 `no-store` 含义完全不同，别记混
