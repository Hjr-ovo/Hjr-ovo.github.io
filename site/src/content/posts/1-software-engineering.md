# 1. 软件与软件产品

## 1.1 三个层次的概念

从"独唱 → 小合唱 → 合唱 → 万人大合唱"，规模与协作复杂度逐级上升，对应三个概念：

| 概念 | 含义 | 特征 |
|---|---|---|
| **程序** | 为解决某问题而设计的指令序列 | 规模小、个人可完成 |
| **软件** | 程序 + 数据 + 相关文档 | 需多人协作、有完整生命周期 |
| **软件产品** | 面向市场/客户的软件，含包装、培训、售后 | 有商业属性，需持续维护与升级 |

## 1.2 软件 = 指令 + 数据 + 文档

> **定义**：软件是计算机系统中与硬件相互依存的另一部分，包括**程序、数据**及其**文档**的完整集合。

拆开看是三部分：

1. **指令的集合（计算机程序）**——通过执行这些指令满足预期的特征、功能和性能需求；
2. **数据结构**——使程序可以合理地利用信息；
3. **文档描述**——描述程序的操作与使用。

> "软件就是程序"是最典型的错误认识。

## 1.3 软件的七个特点

1. 软件是**设计开发**的，不是传统意义上的生产制造；
2. 软件**不会"磨损"**（但会因频繁变更而退化）；
3. 虽然工业界向基于构件的构造模式发展，但**大多数软件仍是按顾客需求定制的**；
4. 软件是**逻辑实体**，具有抽象性——形态不可见，必须通过观察、分析、思考、判断来了解其功能、性能和其他特性；
5. 软件是人脑思维的产物，其**生产过程与硬件不同**（带来开发过程质量控制与产品保护问题）；
6. 软件的开发和运行**受计算机系统限制**（由此产生软件移植问题）；
7. 软件开发技术相对落后，**手工开发方式仍占统治地位**，开发效率低；软件复杂性越来越高，出现"软件复杂性与软件技术发展不相适应"的现象。

此外，相当多的软件工作涉及**社会因素**（机构、体制、管理方式、人的观念与心理），直接影响软件工作成败。

## 1.4 软件的分类

课件从**六个维度**切分软件，考试常问"软件按功能/按工作方式分为哪几类"。

**按功能**（最常用）：

| 类别 | 说明 | 举例 |
|---|---|---|
| **系统软件** | 管理计算机资源、为应用提供运行环境 | 操作系统、编译程序、数据库管理系统 |
| **支撑软件** | 支撑软件开发与维护的工具性软件 | 编辑器、调试器、CASE 工具 |
| **应用软件** | 面向特定业务问题的软件 | 报表系统、教务系统、CAD |

其余五个维度：按**规模**、按**工作方式**（实时处理 / 分时 / 交互式 / 批处理）、按**服务对象**、按**使用频度**、按**失效影响**。

# 2. 软件为什么必须变更

软件必须持续演化，原因有四：

- 进行**适应性调整**，以满足新的计算环境和技术的需求；
- **升级**以实现新的商业需求；
- **扩展**使之具有与更多现代系统和数据库的互操作能力；
- **改建**使之能适应多样化的网络环境。

> 关键逻辑：正因为"变更"是常态，一次性交付的瀑布式做法才不够用——这为第 2 章的演化模型、增量模型、敏捷方法埋下伏笔。

# 3. 软件危机

## 3.1 背景与定义

20 世纪 60 年代末 70 年代初，西方工业发达国家经历了一场"软件危机"。一方面软件十分复杂、价格昂贵、供需差日益增大；另一方面软件开发常受挫、质量差、进度与完成日期很少能按时实现、研制过程难以管理，即**软件的研制往往失去控制**。

> **定义（软件危机）**：落后的软件生产方式无法满足迅速增长的计算机软件需求，从而导致软件开发与维护过程中出现一系列严重问题的现象。

## 3.2 表现

1. 对软件开发的**成本和进度估计不准确**；
2. 开发的软件**不能满足用户要求**；
3. 软件产品的**质量不可靠**；
4. 软件常常**不可维护**；
5. 软件通常**没有适当的文档资料**；
6. 软件成本在计算机系统总成本中的**比例逐年上升**；
7. 软件**开发生产率低**。

## 3.3 产生的原因

| 分类 | 原因 | 具体表现 |
|---|---|---|
| **客观**（软件本身特点） | 缺乏"可见性" | 管理和控制软件开发过程相当困难 |
| | 规模庞大 | 需多人分工合作；如何保证各自成果合起来构成高质量大系统，不仅涉及技术，更需严格科学的管理 |
| **主观**（方法不正确） | 忽视软件需求分析的重要性 | —— |
| | 错误认为"软件开发 = 程序编写" | —— |
| | 轻视软件维护 | 统计表明维护费用占软件总费用的 **55%～70%** |

## 3.4 解决途径

- **组织管理**：采用工程项目管理方法；
- **技术措施**：软件开发技术与方法 + 软件工具。

> 这两条正是"软件工程"诞生的两个支点——管理 + 技术。

# 4. 软件工程

## 4.1 IEEE 定义

> **软件工程是**：① 将系统化的、规范的、可量化的方法应用于软件的开发、运行和维护，即将**工程化方法**应用于软件；② 对①中所述方法的**研究**。

## 4.2 软件工程是一种层次化技术

自下而上三个层次 + 一个贯穿始终的基石：

| 层次 | 内容 |
|---|---|
| **工具**（最上层） | 对过程和方法提供自动化或半自动化的支撑 |
| **方法** | 回答"如何做"：需求分析、设计、编码、测试的技术方法 |
| **过程** | 回答"什么时候做、做什么"：把方法与工具粘合起来的骨架 |
| **质量关注**（基石） | 贯穿全部层次的根本目标——a "quality" focus |

## 4.3 通用框架活动

| 框架活动 | 关键动作 |
|---|---|
| **沟通** | 与客户/利益相关者交流，明确需求与约束 |
| **策划** | 制定计划、估算工作量与进度、识别风险 |
| **建模** | ① 需求分析（理解要做什么）② 设计（决定怎么做） |
| **构建** | ① 代码生成 ② 测试 |
| **部署** | 交付用户、获得反馈、进入维护 |

> 五步可循环迭代，是"普适性活动"之上的框架骨架。

## 4.4 Hooker 的七条一般原则

1. 存在价值（系统首先要对使用者有存在意义）
2. 保持简洁
3. 保持愿景
4. 关注使用者
5. 面向未来
6. 计划复用
7. 认真思考

# 5. 软件神话与常见误解

## 5.1 软件神话

- 神话影响**管理者、客户（及其他非技术性利益相关者）和从业人员**；
- 之所以被认为可信，是因为它们**有时包含真实的部分**；
- 但神话**不可避免地导致错误决策**；
- 正确做法：按照正确理解软件工程的方式，**从实际出发**解决问题。

## 5.2 常见误解与对应的现实

| 角色 | 误解（Myth） | 现实（Reality） |
|---|---|---|
| **管理** | M1：已有一本关于软件生产的标准和过程的书，这还不能让我们学到需要的知识吗？ | R1：相比最新的大型主机、工作站和 PC，仅靠"标准手册"会使高质量软件开发**花费更多** |
| | M2：如果项目进度落后，可以加入更多程序员赶进度 | R2：软件开发机制与手工作业不同，**给延期项目加人只会让它更延期** |
| | M3：把软件项目外包出去我们就轻松了 | R3：若组织管理方不懂得如何内部管理和控制软件项目，**外包也无济于事** |
| **客户** | M1：对目标的一般陈述就足以开始编程，细节今后再补 | R1：**前期糟糕的需求定义是软件失败的主要原因** |
| | M2：需求一旦确定就不该再变 | R2：需求确实不断变化，但**变化产生的影响取决于变化提出的时间**（越晚代价越大） |
| **实践者** | M1：编程完毕并成功运行，工作就结束了 | R1："越早开始写代码，花费的时间越长"；工业数据显示 **60%～80%** 的精力耗费在首次交付给用户之后 |
| | M2：程序运行之前无法评估质量 | R2：最有效的质量保证机制应在项目**正式开始启动时**就介入（可通过技术评审体现） |
| | M3：唯一可交付的成果是可运行的程序 | R3：可运行程序只是软件配置的一部分，还包含文档、数据等 |
| | M4：软件工程会让我们创建大量不必要的文档，使进度变慢 | R4：软件工程**不是创建文档，而是创建质量**；更好的质量减少返工，返工减少让项目更早交付；文档是提高沟通与质量所必需的 |
