## 20:15 重构 · 文章管家界面重做：三列布局 + 拖拽打标签

用户要求：中间**始终**显示全部文章（每篇一个小格子）、入库改成悬浮窗、标签和分类点开时
从左侧栏右边弹出第二列、两列宽度都能拖且要记住、标签 ⇄ 文章可以互相拖。

**布局从「两列 + 切页面」改成「三列 + 悬浮窗」**：

```
side(可拖) │ drawer(可拖，点标签/分类才出现) │ main(文章格子墙，常驻)
```

以前 `show(view)` 会把中间整块换掉（列表 / 编辑 / 入库三选一），现在中间只有文章墙，
入库和编辑都是盖在上面的 `.modal`。这一条是这次改版的根本，其余都是它的推论。

| 改动 | 具体做法 |
|---|---|
| 骨架 | `.app` 从 `grid-template-columns: 188px 1fr` 改成 flex；宽度写进 `--side-w` / `--drawer-w` |
| 拖宽 | 两个 6px 透明把手，`mousedown` 记录起点、`mousemove` 改 CSS 变量、`mouseup` 存 localStorage；双击复位 |
| 抽屉 | 默认宽度取 `layout.drawer \|\| layout.side`——没单独调过就**自动等于左栏** |
| 自动重排 | 文章墙用 `repeat(auto-fill, minmax(248px, 1fr))`，抽屉一开主区变窄，列数自己从 4 掉到 3 |
| 编辑窗 | 从「整页」改成 `.modal`，左元数据 / 右正文两栏（≤1100px 摞成一列） |
| 入库窗 | 同样改成 `.modal`，空态只有拖拽区，拖进文件后展开诊断 |

**新增接口 `POST /api/posts/:slug/terms`**（`{kind, name, action}`）：走和保存同一条
`patchMeta` 通道，所以加一个标签只改那一行。实测加标签 `git diff --numstat` = `1 1`；
重复添加返回 `changed:false` 且**不写文件**；删最后一个分类返回 422（分类是必填项）。

**拖拽双向**：抽屉项和卡片都 `draggable="true"`，`dragstart` 把内容记进 `state.drag`，
`dragover` 时给落点加 `.drop-ok`（淡绿底 + 描边），`drop` 调同一个 `addTerm()`。
另加一个「点抽屉项 → 同类文章保持、其余淡到 0.28」的筛选，**不隐藏不重排**，
这样「中间永远是全部文章」这条没破。

**踩到一个坑**：`openDrawer()` 里原本写了 `if (!layout.drawer) layout.drawer = layout.side`，
等于在第一次展开的瞬间把宽度**固化**成当时的左栏宽度。后果是之后把左栏拖宽，抽屉不跟。
改成完全不碰 `layout.drawer`，宽度交给 `applyLayout()` 现算。合成 MouseEvent 测出来的：
修之前拖左栏到 250 再拖抽屉，结果 258（188+70）；修之后起点正确跟着 250 走。

**验证手段**（HTML5 拖放没法用鼠标坐标模拟，所以合成事件）：

| 测什么 | 怎么测 | 结果 |
|---|---|---|
| 标签 → 文章 | 临时页里 `dispatchEvent(new DragEvent(...))` 走 dragstart/dragover/drop | 卡片拿到 `.drop-ok`，`addTerm` 被调用并弹「已有该标签」 |
| 文章 → 抽屉 | 同上，方向反过来 | 抽屉项拿到 `.drop-ok`，同样走通 |
| 点抽屉项 | `MouseEvent('click')` | 项变 `selected`、grid 加 `filtering`、卡片加 `match`、标题跟着改 |
| 拖宽 + 记忆 | 合成 mousedown/mousemove/mouseup | 188→250 生效并存档；拖到 100 被夹在下限 150 |
| 多文章重排 | 临时造 5 篇再删 | 默认 4 列，抽屉打开变 3 列 |

## 19:18 新增 · 文章管家桌面快捷方式 + 专属图标

## 18:10 样式 · 标题整体加重，正文 h2 挂一根绿条

**为什么改**：四级标题原本一律 `font-weight: 500`，层级全靠字号差（1.65 / 1.3 / 1.1 / 1rem）。
中文在 500 下看着发虚，长文扫读时标题和加粗正文混在一起，抓不住章节边界。

**改法**（`site/src/styles/global.css`）：

| 层级 | 之前 | 现在 |
|---|---|---|
| h1 | 1.65rem / 500 | **1.85rem / 700**（窄屏 ≤480px 1.65rem） |
| h2 | 1.3rem / 500 | **1.45rem / 700 ＋ 左侧 3px 绿竖条** |
| h3 | 1.1rem / 500 | **1.2rem / 600** |
| h4 | 1rem / 500（继承） | **1.05rem / 600** |

另统一加 `color: var(--ink)`、`letter-spacing: -0.01em`（中英混排收紧一点，看着更实）。

**h2 绿条的三个讲究**：

- **只给 `.post-body` 里的 h2**。「相关文章」「关于页章节」也是 h2，但它们有自己的字号覆盖，
  属于辅助标题 —— 跟着长绿条会让页面到处是竖条，反而失去指示意义。
- `padding-left: 0.8rem` + `margin-left: calc(-0.8rem - 3px)`：绿条挂在正文左侧留白里，
  标题文字的左缘与段落**严格对齐**。少减这 3px 边框宽度，标题会整体右偏 3px。
- 颜色用 `var(--accent)`，深色模式自动变亮绿 `#6ed3ad`，不用单写一份。

竖条而不是下划线 / 大色块：竖条几乎不占纵向空间，长文里十几二十个 h2 也不会把页面切碎；
而且它和文章卡片 hover 时冒出的绿条是同一套视觉语言。

**验证**：
- 文章页截图：h1 明显加重；h2 绿条落在正文左缘外侧、文字与段落对齐；h3 只靠字重字号区分，不抢戏
- 横向溢出实测（临时页面把 5 个页面塞进 320 / 360 / 400 / 480 / 640 / 768 / 1024 / 1280 / 1440
  共 9 档 iframe，量 `scrollWidth - clientWidth`）：**45 组全部 0 溢出**，
  负 margin 没有顶破 `.wrap` 的 `1.25rem` 内边距（12.8 + 3 < 20px）
- `npm run build` exit=0

## 17:50 样式 · 滚动条补上「白天版」，顺带修掉跟随系统配色的漏配

**现象**：白天模式下滚动条是深色的，跟暖白纸页面完全不是一路。

**根因有两层**：

1. **`color-scheme` 只配了一半**。深色块里写了 `color-scheme: dark`，但 `:root` 从来没写过
   `color-scheme: light`。head 里又有 `<meta name="color-scheme" content="light dark">`，
   根元素没显式声明时它会**跟随操作系统的配色**渲染原生控件 —— 系统是深色的话，
   即使用户手动切回白天，滚动条、input、select 仍然保持深色。
   （这是当初做深色模式时留下的口子：只想着「切深色要跟着变」，漏了「切浅色也要跟着变」。）
2. 滚动条本身**没有任何自定义样式**，全靠浏览器默认。就算颜色对了，也是灰白轨道 + 浅灰滑块，
   跟这套「暖白纸 + 墨绿」的配色也不搭。

**改法**（只动 `site/src/styles/global.css`）：

| 改动 | 说明 |
|---|---|
| `:root` 补 `color-scheme: light` | 原生控件改为跟随**本站主题**，不再跟随系统 |
| 新增 `--scroll-thumb` / `--scroll-thumb-hover` | 浅色 `#d3d0c3` / `#b3b0a2`，深色 `#3b3e37` / `#4f534a` |
| `::-webkit-scrollbar` | 宽 10px、轨道透明、滑块圆角；`2px solid transparent` 描边 + `background-clip: padding-box` 做出两侧留白，视觉宽 6px |
| Firefox 分支 | `@supports (-moz-appearance: none)` 里写 `scrollbar-width: thin` + `scrollbar-color` |
| `.toc` 侧栏 | 滚动条收细到 6px（描边同步减到 1px，否则 6−4 只剩 2px 的滑块） |

**两个坑记一下**：

- **`scrollbar-width` / `scrollbar-color` 不能无条件写**：Chrome 121+ 也实现了这两个属性，
  无条件写会让它改用原生细滚动条，把伪元素那套圆角、内缩全盖掉。所以只用 `@supports`
  圈给 Firefox —— 判据用 `-moz-appearance`，Chrome/Safari 不认这个属性，`@supports` 返回 false。
- **深浅两套滚动条不能写两份规则**：颜色全走变量，深色块只覆盖变量值。写两份的话下次改配色
  必然漏一边 —— 这正是这次踩的坑的重演。

**验证**：dev 编译产物里确认规则都在（`color-scheme: light`、`::-webkit-scrollbar` 四个伪元素、
`scrollbar-width: thin`、深浅两套 `--scroll-thumb`）；`[data-theme='dark']` 写在 `:root` 之后，
同特异性后者胜，深色仍然正确覆盖。生产构建 `dist/_astro/BaseLayout.*.css` 里同样齐全，
`color-scheme:light` 在前、`color-scheme:dark` 在后。

**顺手挖出一个老问题（比滚动条本身严重）**：提交时发现 `博客后台工具/` **还在磁盘上**。
10-30 那次删除时，工具的 server 进程（`node src/server.mjs`，监听 `127.0.0.1:5678`）占着目录，
Windows 下删不干净 —— 但 git 那边已记录了删除，所以 `git status` 一直干干净净，看不出异常。
这次 `git add -A` 把这 16 个文件、7270 行一股脑塞进了提交。
处理：停掉那个残留进程 → 目录移到 `.workbuddy/tmp/backend-tool-20261031/` → 用 `--amend`
把提交剥干净（HEAD 里工具目录文件数已为 0）。

**教训**：**「`git status` 干净」不等于「文件真的没了」**。删目录之后要 `ls` 一眼确认；
另外 `git add -A` 会把工作区里所有未跟踪的东西一起收进来，动完大目录后最好先看一眼
`git status` 再提交。

全挂在四级标题下，之前一条都不进目录。读者滚到那一带时目录里没有对应行，只剩上级「1.3 办法二」
还亮着，等于失去了定位作用 —— 而这正是用户提需求的直接原因。

**滚动跟随的实现要点**：`keepVisible()` 只在「active 状态真的发生变化」时触发，且判断
「当前项与侧栏中心的距离 < 侧栏高的 30%」就跳过，否则每次切换都微调、看着像抖。
只在 `toc.scrollHeight > toc.clientHeight` 时才滚，否则会带着整个页面跳。

### 二、Obsidian 格式适配（`site/src/utils/remark-obsidian.mjs`）

| 写法 | 处理 |
|---|---|
| `==高亮==` | → `<mark>`，**支持跨节点**（`==**粗体**==`、`` ==带 `代码` 的== `` 都能正确包住） |
| 正文出现 h1 | 全文标题整体降一级（`#`→`##`…），让章节回到目录 |
| frontmatter `date` / `explain` | 校验前映射成 `pubDate` / `description`（`content.config.ts` 的 `z.preprocess`） |

**为什么放 remark 阶段**：同 code-tabs —— Shiki 高亮跑在自定义 rehype 插件之前，
到 rehype 时文本结构已固化成 HTML 字符串，没法再跨节点配对。

**安全的边界**（都实测过）：
- 代码块里的 `==`（Java 的 `a == b`）**不会**被误转 —— code 节点是 value 型，不是文本节点
- 等号没配对（只出现一次）时原样吐出，不吞内容
- frontmatter 只在正式字段缺失时才用别名兜底，两边都写时以正式字段为准
- `categories` 仍然必填（不给默认值）：机器猜不出文章该归哪一类，漏写应当报错而不是悄悄归入「未分类」

**已知限制**：正文段落里写 `==` 比较运算符会被当成高亮（无法与荧光笔区分）。
技术文章的运算符一般写在代码块内，影响很小；真要写在正文里，用反引号包一下即可。
