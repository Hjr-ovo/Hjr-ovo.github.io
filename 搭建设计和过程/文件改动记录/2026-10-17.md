## 17:36 修改 · 首页只显示最近 10 篇 + 新增「全部文章」归档页

**改了什么**：`pages/index.astro` 引入常量 `RECENT_COUNT = 10`，只渲染前 10 篇；
多出来的篇数存进 `restCount`，>0 时底部渲染 `.more-posts`（描边胶囊链接「查看更多历史文章」
+ 小字「还有 N 篇更早的文章」），链接指向新页 `/posts/`。
新增 `pages/posts/index.astro`：全部文章按**年份**分组（每行 = 月-日 + 标题 + 分类胶囊），
`<title>` 写「全部文章」，页头注明「共 N 篇」。`global.css` 补 `.more-*` 与 `.archive-*` 样式。

**为什么**：首页一次性铺开所有文章，文章一多就成了无限长列表，读者滚不到底也看不出「有没有更早的」。

设计上的几个取舍：
- **用独立归档页，不用「加载更多」**：加载更多要么把所有文章都塞进首页 HTML（首页最重、访问量最大），
  要么上客户端请求。归档页则是纯静态、有固定地址、能收藏能分享，和自己运维的成本一致。
- **只在超过 10 篇时才显示按钮**：文章不够 10 篇时渲染一个点了也没用的按钮更糟。
  实测当前 6 篇，按钮确实不出现。
- **年份是分隔符不是内容**：小字灰色 + 一条细线。每行只写「09-22」，因为年份已经写在上面的分组标题里，
  再重复一遍「2026 年」纯属噪音。
- **`monthDay()` 用 UTC 取值**：`pubDate` 是 `z.coerce.date()` 解析的 UTC 零点，
  用本地 `getMonth()` 在负时区会退一天，`getUTCMonth()` 才稳。

**改了什么**：新增 `pages/about.astro`（`/about/`）—— 身份区（头像 + 昵称 + 一句话定位）、

`BaseLayout.astro` 导航末尾加「关于」；`global.css` 补关于页样式
（头像圆形区、三块统计卡片、圆点列表、描边胶囊——和标签的实心胶囊区分开）。

文章数 / 分类数 / 标签数**构建时从文章集合现算**，不手写。

**为什么**：陌生读者点进一个技术博客，第一反应是「这是谁写的、值不值得读」。关于页就是回答
这两个问题的地方，也是唯一能放「我为什么写这个站」的位置。

三个设计决定：
- **文案单独放 `data/about.ts`**：用户明确要求「以后自己也能改」。文字抽出来之后，改一句话
  只改那个文件里的中文，不用碰 HTML 标签；排版和文案彻底分开。
- **统计数字自动算**：手写「6 篇文章」这种数字，等文章加到 7 篇就会对不上，而且没人会记得回来改。
- **隐私口径**：只写技术身份，**不写真实姓名、学校名**（2026-10-17 用户定）。
  联系方式先只放 GitHub；同日 17:23 补上不含姓名拼音的 gmail（见上一条卡片）。

## 16:42 新增 · 文章页显示阅读时长 + 文末「相关文章」

**改了什么**：新增 `utils/reading-time.ts` —— 按 Markdown 原文估算阅读时间：先把围栏代码块、
行内代码、图片、链接地址、HTML 标签剥掉，再分别数汉字（350 字/分钟）、英文词（200 词/分钟）
和代码行（50 行/分钟），取整且**最少显示 1 分钟**；文章页日期后面接一句「约 X 分钟读完」。
新增 `utils/related-posts.ts` —— 相关文章按「标签重合 ×3 + 同分类 ×2」打分，分数为 0 的不进推荐，
同分按发布时间新的在前，取 3 篇；文章页 `<Content />` 之后渲染 `<aside class="related">`。
`global.css` 补相关文章区块样式（细线分隔、小字灰色标题、条目之间紧凑排布）。

**为什么**：技术文长短差很多，读者需要先知道「要不要现在读」。相关文章则是给读完的人一条
继续走的路 —— 一个人踩过的坑往往连着好几个坑。

两处刻意的设计：
- 阅读时长里**代码单独计速**。把代码按普通文字算，一篇满是命令行的文章会被算成「3 分钟读完」，
  实际读起来远不止；反过来全按字数糊过去，纯代码片段又会被高估。
- 相关文章算不出交集时**退回「继续阅读」列最新 3 篇，标题跟着换**。原因是本站现在只有 1 篇真实
  文章，它的标签（npm / Windows / 踩坑）和分类（开发工具）跟其他文章零重合；按严格规则，
  读者在这篇文末会撞到一堵墙。换个名头列最新文章，既不冒充「相关」，也保证有路可走。

## 13:41 新增 · 深色模式

**改了什么**：`global.css` 把颜色全部收进 CSS 变量，新增派生变量
（`--line-strong` / `--chip-bg` / `--table-head-bg` / `--placeholder` / `--shadow-card` /
`--shadow-card-hover`），把散落在规则里的 6 处写死颜色换掉（`#bcd9cd`、`#f1efe8`、`#f7f6f1`、
`#a5a39c`、两处 `rgba()` 阴影）；新增 `[data-theme='dark']` 一组覆盖值（暖调深灰，不是纯黑）
并加 `color-scheme: dark` 让滚动条等原生控件跟着变。
`BaseLayout.astro` 在 `<head>` 里加 `is:inline` 内联脚本，首屏绘制前就定好主题
（存过 localStorage 就听用户的，没存过就看系统偏好）；页头导航末尾加 `.theme-toggle` 按钮
（月亮 / 太阳两个 SVG 都渲染，用 CSS 按当前主题显示其中一个）。
`astro.config.mjs` 的 Shiki 改成双主题 `['github-light', 'github-dark']`，代码块靠
`--shiki-dark` 变量在深色下换色。

**为什么**：晚上看白底页面刺眼。工程上的关键在于**先变量化再加深色** —— 只要有一条规则写死
了 `#f1efe8`，深色下就会留一块白斑，而且这种问题很难靠肉眼扫出来。

两个必须注意的点：
- 内联脚本**不能**写成普通 `<script>`。Astro 会把普通脚本打包成模块并延后执行，那时首屏已经
  画完了，会先看到白底再闪成深色。必须 `is:inline` 原样塞进 `<head>`。
- 深色下的强调色要**提亮**（`#0f6e56` → `#6ed3ad`），原来的墨绿放在深底上几乎看不见。

深浅两套配色的对比度用 WCAG 公式核对过（正文 / 次要文字 / 强调色 / 代码底色），
全部达到 AA 以上。

## 13:10 修改 · 搜索支持「标题 / 标签 / 正文」三个范围，可勾选组合

**改了什么**：`pages/search.astro` 重写搜索逻辑，搜索框下加一排胶囊选项（标题 / 标签 / 正文，
默认全选），勾选状态实时触发重搜，地址栏同步 `?q=关键词&in=title,tag`；
`global.css` 补胶囊选项、命中徽标、标题高亮样式。数据上多了一份**构建时内联的轻量索引**
（`getCollection('posts')` 取 title / description / tags / category / date，塞进
`<script type="application/json" id="post-index">`），标题与标签的匹配就靠它。

**为什么**：原来只有一个搜索框，正文、标题、标签混在一起搜，读者分不清「为什么这篇会出现」。
现在按范围搜，结果卡片上还会标出命中来源（徽标「标题」「标签」「正文」）。

关键约束：**标题和标签本来就不在 PageFind 索引里** —— 标题是 `data-pagefind-meta`（元数据不参与
全文检索），标签行是 `data-pagefind-ignore`（当初特意排除，免得标签词污染摘要）。所以这两个范围
只能另起一份索引自己匹配；文章就几十上百篇，内联 JSON 完全够用，还比全文检索更准。
正文仍走 PageFind，两路结果按 URL 去重合并，排序固定为 **标题命中 > 标签命中 > 正文命中**
（正文内部保留 PageFind 的相关度顺序）。
副产品：开发模式没有 PageFind 索引时，「正文」不可用但标题 / 标签照常能搜，状态栏会如实说明。

## 11:52 新增 · 站内搜索：构建时用 PageFind 生成索引

**改了什么**：新增 `pages/search.astro`（搜索框 + 结果列表，复用首页卡片样式，命中词绿色高亮，
支持 `?q=` 直接打开某次搜索）；`site/package.json` 的 build 改成
`astro build && pagefind --site dist`，并加 `pagefind` 到 devDependencies；
导航加「搜索」；`global.css` 补搜索框 / 状态文字 / 摘要高亮样式；
文章页给 `<article>` 加 `data-pagefind-body`、标题加 `data-pagefind-meta="title"`、

顺带清掉 `redirects.json` 里 10-07 测试改名留下的两条假重定向（测试分类甲 / 测试标签甲）。

**为什么**：需求「成功标准」第 4 条要求「内容找得到」，「想要有」里站内搜索是最实用的一项。
选 PageFind 是因为它构建时扫 `dist/` 生成静态索引、纯客户端、不需要服务端，
和「不自己租服务器」的边界一致；中文能自动识别（构建日志 `Discovered 1 language: zh-cn`）。
索引只收文章正文，分类/标签/首页这些导航页不参与，避免搜出「一篇文章的列表页」。

**改了什么**：新增 `components/TableOfContents.astro` —— 数据直接取 `render()` 返回的

窄屏刻意不把目录摞到正文上方：读者会先看到一屏目录、看不到标题，比没有目录更糟。
