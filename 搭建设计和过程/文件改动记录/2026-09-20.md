## 15:50 修改 · 修复弹窗被 CSS 顶穿（BUG-009）

**改了什么**：

- `博客管理工具/public/style.css` —— 文件最前面新增一条全局兜底规则
  `[hidden] { display: none !important; }`，并写了注释说明为什么必须有（防后人误删）
- `搭建设计和过程/bug修复记录/2026-09-20.md` —— 新增 BUG-009 卡片
- `搭建设计和过程/bug修复记录/经验教训.md` —— 新增 **L-007 / L-008 / L-009**
- `搭建设计和过程/bug修复记录/README.md` —— 索引与 bug 一览补 BUG-009

**为什么**：用户截图反馈「双击后怎么是这个样子，中间的这个点击不改、只改标题、顺便改成新的都没有用」——
打开工具后改名弹窗**自己就浮在页面上**，且弹窗里写着「标题从『』变成了『』」**两头都是空的**。

定位出的根因，**一条规则解释全部三个怪现象**：

**HTML 的 `hidden` 属性不是特殊开关，它只是浏览器默认样式表里的一条 `[hidden] { display: none }`，优先级很低。**
我手写的 `.modal { display: flex }` 特异性相同却是作者样式，**作者样式优先于浏览器默认样式** → `hidden` 形同虚设。

| 你看到的现象 | 真正的原因 |
|---|---|
| 弹窗一打开就在 | `.modal` 的 `display:flex` 盖过了 `hidden` |
| 里面字段全空 | `askRename()` 里才填字段，而它**从没被调用过** |
| 两个按钮都没反应 | `onclick` 也是在 `askRename()` 里才绑的 |

**一个佐证**：写脚本审计了 HTML 里全部 11 个带 `hidden` 的元素，**正好 2 个破损**（`modal` 与 `rename-modal`，
都带 `.modal` 类）；其余 9 个的类都没声明 `display`，所以一直正常 —— 这解释了为什么只有弹窗出问题。

**提交**：`——`

**验证结果**：用**真实 Chromium** 实测（不是靠推理）

- 反向复现：注入去掉该规则的 CSS → 两个弹窗实测 `display: flex`、文案两头皆空 → **与截图完全一致**
- 修好后：弹窗默认 `display: none`；程序主动显示时变 `flex`，关掉又回 `none`
- 走完真实流程：进编辑器时仍隐藏 → 改标题 → 保存 → 弹窗**这才出现**，文案为
  `标题从「npm install 卡死 23 分钟：…」变成「…（改）」`，点「不改，只改标题」正常关闭
- 测试后标题已改回原样，端口与浏览器进程全部清理

**一个值得记的踩坑**：一开始用 jsdom 测，报告「13 项全过」—— 但 **jsdom 内置了 `[hidden] {display:none}` 默认样式，
把 bug 掩盖了**，修复前后都显示 `none`，属于假阳性。改用真实浏览器并加了「撤掉修复确认能变红」这一步才算验证到位。

## 15:30 修改 · 修复双击 启动.bat 一闪而过（BUG-008）

**改了什么**：

- `博客管理工具/启动.bat` —— **行尾统一改成 CRLF**（原先是我用 Node 以 `\n` 写出的，纯 LF 55 行 / CRLF 0 行）；**所有 `REM` 注释改成纯 ASCII**，中文只保留在 `echo` 行里；`title` 也从中文改为 `Blog Tool`；「找不到 node」的提示文案写得更明确
- `搭建设计和过程/bug修复记录/2026-09-20.md` —— 新增 BUG-008 卡片（两层根因分开写：行尾错位 + 中文注释）
- `搭建设计和过程/bug修复记录/经验教训.md` —— 新增 **L-005**（程序生成的 bat 必须 CRLF + ASCII 注释）与 **L-006**（脚本内容对但双击不工作先查行尾编码）；顺带把该文件的规律清单**从表格改成列表**（原先全库早已统一为不用表格，只有这里漏了）
- `搭建设计和过程/bug修复记录/README.md` —— 索引与 bug 一览各补 BUG-008

**为什么**：用户双击 `启动.bat` 后反馈「黑窗口一闪而过就没了」。定位出**两层叠加**的根因：

1. **行尾是 LF 不是 CRLF** —— cmd.exe 要求 CRLF，行尾不对时逐行解析错位，`set "NODE_EXE=..."` 没生效（变量成空 → 展开出 `""`）、`cd /d "%~dp0"` 也没生效，脚本带着空值继续跑，最后 node 调用失败（rc=9009）
2. **`chcp 65001` + 中文 `REM` 注释** —— 切到 UTF-8 代码页后，cmd.exe 解析某些多字节序列会**吞掉 `REM ` 前缀**，把注释当命令执行。踩中的字符是全角括号 `（）` 与全角等号 `＝`，共 5 行

两层叠加的效果就是「一闪而过、零反馈」——连兜底的 `pause` 都被跳过，报错根本看不见。

**定位手法（值得记）**：报错一闪而过抓不到 → 写诊断脚本把每一步 `echo [N] ... >> file` 落盘再读，发现 `cd` 明明写了却没生效；再用 `[System.IO.File]::ReadAllBytes` 直接读字节，一眼看出 `0A` 而非 `0D 0A`。

**验证结果**：CRLF 60 行 / 纯 LF 0 行、非 ASCII 的 `REM` 行 0 条；用 `cmd /c` 真实拉起脚本，窗口输出**无任何报错**，服务 `:5678` 与 `/api/posts` 均返回 **200**，浏览器确认被拉起。

**提交**：`22782bc`

## 14:05 修改 · 改名与 URL 的关系定案，新增 ADR-011

**改了什么**：
- `博客管理工具/技术架构.md` —— 5.5 节改写：第 6 条从「不自动改文件名」改为「**显式询问、默认不改**」；新增 **5.5.1**（改标题要不要连文件名一起改）与 **5.5.2**（URL 自动定位 / 重定向方案，含 A/B/C 对比与分两步走的判断）；第六节汇总表补第 6b 条；第七节风险表补「改名后旧链接失效」；第八节导航补两处
- `搭建设计和过程/设计方案/设计决策记录.md` —— 新增 **ADR-011**（改名是显式操作，重定向留到上线时）

**为什么**：用户追问「改标题不会自动改文件名，那能不能实现 URL 的自动定位」。分析后确认两件事：

1. **能做** —— 静态站用「生成跳转页」（`<meta refresh>`）实现重定向，纯文件方案、不绑托管商
2. **但现在不该做** —— 依据 `需求与目标.md` 的硬数字「第 3 类读者当前数量为 0」：**没人访问过 = 没人收藏过链接 = 现在改 URL 代价为 0**。此时做重定向等于为不存在的访问者建档

**关键判断**：改名本身不是问题，**「不经决策就改名」才是问题**。故定为「弹窗询问 + 默认不改」——
把选择权给用户，但不让 URL 变化偷偷发生。重定向机制留到上线时（触发条件明确），方案已预先选定并存档。

**提交**：`de2555f`
