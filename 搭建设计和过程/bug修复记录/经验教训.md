# 经验教训

> 只放**跨 bug 的通用规律**。单个 bug 的具体反思留在 `bug修复记录/YYYY-MM-DD.md` 对应卡片里。
>
> 判断标准：这条规律能不能一句话说清、并且以后还可能再犯？能，才写进来。

## 规律清单

- **L-001** 排除类规则别靠列举文件名，要用通配符覆盖整类，或把文件放进已被整体忽略的目录 —— 来源 BUG-001（2026-09-19）
- **L-002** 长任务卡住的判据是「可观测副作用是否变化」，不是「等了多久」 —— 来源 BUG-002（2026-09-19）
- **L-003** 在 Windows 上删海量小文件目录（如 node_modules）要用 `robocopy /MIR`，别用 `Remove-Item -Recurse` —— 来源 BUG-002（2026-09-19）
- **L-004** 覆盖写一个旧文件会继承它的编码签名（如 BOM），写「对字节敏感」的文件时要先确认或换新文件名 —— 来源 BUG-003（2026-09-19）
- **L-005** 用程序生成 Windows 的 `.bat` / `.cmd` 必须写 CRLF 行尾，且注释保持纯 ASCII（`chcp 65001` 加中文注释会报错） —— 来源 BUG-008（2026-09-20）
- **L-006** 「脚本内容对但双击不工作」先查文件的行尾与编码，不要先查逻辑 —— 来源 BUG-008（2026-09-20）
- **L-007** HTML 的 `hidden` 属性会被 CSS 里任何显式 `display` 盖过，必须配一条 `[hidden] { display: none !important }` 兜底 —— 来源 BUG-009（2026-09-20）
- **L-008** 组件的动态内容全空 + 交互全失效 → 先怀疑「它根本不该出现」，而不是「内容/事件写错了」 —— 来源 BUG-009（2026-09-20）
- **L-009** 测试通过不等于测到点子上：先确认测试能测出「坏的情况」（反向复现），再相信绿灯 —— 来源 BUG-009（2026-09-20）
- **L-010** 写临时输出文件时，目标路径必须是「已被整体忽略的目录」的**绝对路径**；写相对路径就会落在当前工作目录里等着被提交 —— 来源 BUG-011（2026-09-20）
- **L-011** 「TCP 能连通」和「netstat 能查到该端口」是两件独立的事，不能互相推断；要"找出这个进程是谁"，先用探针验证查法可行 —— 来源 BUG-010（2026-10-07）
- **L-012** 按**命令行**认进程比按**端口**认进程可靠得多（端口只说"有东西在听"，命令行能说"它是谁"） —— 来源 BUG-010（2026-10-07）
- **L-013** 本机 `spawnSync` / `execSync` 调外部命令一律 EBUSY —— 调外部命令**一律用异步 `spawn`** —— 来源 BUG-012（2026-10-07）
- **L-014** `npm install` 超过 60 秒没有任何输出，直接中断换国内镜像源（`registry.npmmirror.com`），别硬等 —— 来源 BUG-002 / BUG-013（2026-10-07）
- **L-015** 框架报错说「某个包不再默认安装」是**版本升级信号**：照它说的补装即可，不要急着改写法 —— 来源 BUG-013（2026-10-07）
- **L-016** 「构建成功」不等于「看起来对」—— 第三方样式表（如 `katex.min.css`）漏引时构建不报错，只是难看；涉及视觉的改动必须实际渲染确认 —— 来源 BUG-013（2026-10-07）

## 详细说明

### L-001 排除规则别靠"点名"

**规律**：凡是靠逐条列举文件名来排除的 ignore 规则，都会随着新文件名出现而失效。

**两种正确做法：**

1. **整体目录** —— 把临时 / 生成的文件统一放进一个已被忽略的目录（本项目用 `.workbuddy/tmp/`）
2. **通配符覆盖整类** —— 如 `/_*.txt` 一次覆盖根目录所有下划线开头的 txt

**为什么重要**：点名式规则的维护成本随文件种类线性增长，而且**失效时静默无提示** —— 不报错、不警告，只会悄悄把不该提交的东西提交上去，等发现时已经在历史里了。

**来源**：BUG-001

### L-002 判断"卡死"要看副作用，不看耗时

**规律**：一个没有输出的长任务，**不能靠"再等等看"来判断它是慢还是死了**。
必须挑几个会随进度变化的可观测指标，隔一段时间对比，**指标零变化 = 卡死**。

**可用的指标**（本项目实测有效）：

| 指标 | 怎么取 |
|---|---|
| 目标目录条目数 | `(Get-ChildItem <目录>).Count` |
| 目标目录总体积 | `Measure-Object -Property Length -Sum` |
| 最近 N 分钟内被修改的文件数 | 按 `LastWriteTime` 过滤 |
| 进程累计 CPU 时间 | `Get-Process <名> \| Select CPU` |

**为什么重要**：这次一个 npm 安装卡死了 23 分钟，全程**没有任何报错、没有任何输出**。
如果早点用「间隔 10 分钟对比四项指标」的办法，能省下十几分钟。
更糟的是「没输出」很容易被误读成「正在下载大文件」，让人白白等待。

**补充**：任务本身也会留痕迹。npm 的调试日志在 `%LOCALAPPDATA%\npm-cache\_logs\`，
卡住时翻它末尾，通常能直接看到停在哪个包、哪一步。

**来源**：BUG-002

### L-003 Windows 上删海量小文件目录，用 robocopy 而不是 Remove-Item

**规律**：在 Windows 上清理 `node_modules` 这类"文件数极多、路径极深"的目录时，
**`Remove-Item -Recurse -Force` 会因长路径限制静默失败一部分** ——
命令本身不报错，你以为删干净了，其实留了一堆残留。

**可靠做法**：

```powershell
New-Item -ItemType Directory -Path <空目录> -Force
robocopy <空目录> <要删的目录> /MIR
Remove-Item <要删的目录> -Recurse -Force
```

`robocopy /MIR` 把空目录镜像过去，等于清空，且**不受长路径限制**，几秒完成。

**为什么重要**：这次"删过了但其实没删完"，导致 npm 在半残目录上做增量安装，
最终 `astro build` 报 `ERR_MODULE_NOT_FOUND`（某个包缺 `index.js`）。
**排查方向一度跑偏到"是不是 `--ignore-scripts` 导致的"**，实际根因是删不干净。

**配套要求**：这类删除**删完必须验证** —— 数条目、看大小是否为 0，不能只看命令有没有报错。

**来源**：BUG-002

### L-004 覆盖写旧文件会继承它的编码签名

**规律**：一个文件如果曾被 A 工具创建（带 BOM 或某种特定编码），之后用 B 工具"覆盖写"，
**可能只替换了内容、却保留了原有的编码签名**。BOM 就这样长期潜伏在文件开头。

**本次实例**：`COMMIT_MSG.txt` 由 PowerShell `Set-Content -Encoding UTF8` 创建（PS 5.1 会写 BOM），
之后覆盖写仍带 BOM；`git commit -F` 把 BOM 当作正文收进提交对象，`git log --oneline` 里就多出一个乱码字符。

**两种可靠做法**：

1. **换新文件名**，而不是覆盖旧文件 —— 新建的文件不带历史包袱
2. **写完验头 3 字节** —— `EF BB BF` 就是 BOM。
   要写无 BOM 的 UTF-8：先以 `utf-8-sig` 读入（自动剥离），再以 `utf-8` 写回；
   或在 PowerShell 里用 `UTF8Encoding($false)`

**为什么重要**：BOM 是典型的"看不见但会被程序当成数据"的东西。
Markdown 渲染器普遍容忍它，所以问题长期不暴露 —— 直到它被塞进 git 提交信息、JSON、配置文件这类**对字节敏感**的地方才显形。
而且**全程静默、无任何报错**，只能靠核对输出发现。

**来源**：BUG-003

### L-005 程序生成的 `.bat` 必须 CRLF + ASCII 注释

**规律**：用 Node / Python / 脚本"写"出来的 Windows 批处理文件，默认往往是 LF 行尾，
而 **cmd.exe 要求 CRLF**。行尾不对时它逐行解析会错位：`set` 赋值不生效（变量变空）、
`cd` 不生效，脚本会带着一堆空值继续往下跑，最后以"命令找不到"（9009）收场。

**第二个雷**：很多人为了显示中文特地加 `chcp 65001`，但这会让**含中文的 `REM` 注释**开始报错 ——
cmd.exe 解析某些多字节序列时会吞掉行首的 `REM ` 前缀，然后拿注释去当命令执行。
实测踩中的字符是**全角括号 `（）` 与全角等号 `＝`**。

**可靠写法**：

1. 生成时显式写 `\r\n`，别依赖编辑器/工具的默认换行
2. **注释一律纯 ASCII**（英文），中文只放在 `echo "..."` 里 —— echo 的内容不受影响，实测正常显示
3. 写完验一下：CRLF 行数 > 0、纯 LF 行数 == 0、非 ASCII 的 `REM` 行 == 0

**为什么重要**：这两个问题叠在一起的效果是**「黑窗口一闪而过、零反馈」** ——
连兜底的 `pause` 都被跳过，报错看不见。第一反应容易误判成"文件损坏"或"杀毒软件拦了"。
而只要用程序生成过 `.bat`，就几乎必然踩中第一层。

**来源**：BUG-008

### L-006 「脚本内容对但双击不工作」先查行尾与编码

**规律**：自己写的脚本，在 PowerShell / Node / 编辑器里跑得好好的，一双击就废 ——
这时候**不要先怀疑逻辑**（逻辑不可能换个执行环境就突然错），
**先怀疑文件本身**：行尾（CRLF vs LF）、编码（BOM、UTF-8 vs GBK）、文件扩展名关联。

**排查手法**：直接读字节，别靠肉眼看。
`[System.IO.File]::ReadAllBytes(...)` 看前几个字节有没有 `EF BB BF`（BOM）、
统计 `0D 0A`（CRLF）与孤立 `0A`（LF）各多少 —— 这次就是靠这个一眼看出"CRLF 0 行、纯 LF 55 行"。

**配套**：一闪而过的报错抓不到时，**写诊断脚本把每一步 `echo [N] ... >> file` 落盘再读**。
本次就是靠它发现 `cd` 明明写了却没生效。

**为什么重要**：「零反馈」的故障最容易让人乱猜方向、浪费时间。
而"读字节"这个动作成本极低、结论却是确定的，比任何猜测都快。

**来源**：BUG-008

### L-007 `hidden` 属性会被 CSS 的 `display` 盖过，必须配兜底规则

**规律**：HTML 的 `hidden` 属性**不是什么特殊开关**，它只是浏览器默认样式表里的一条
`[hidden] { display: none }`，优先级很低（`0,1,0`）。

**只要你手写的 CSS 给同一个元素声明了 `display`，`hidden` 就立刻失效** ——
因为作者样式优先于浏览器默认样式。元素会**安安静静地显示出来**，不报错、不警告。

**可靠做法**：在任何项目的基础样式里，**一开始就写这条模板级安全网**：

```css
[hidden] {
  display: none !important;
}
```

**为什么用 `!important`**：这样它就能盖过任何组件自己声明的 `display`（如 `.modal { display: flex }`），
不必再逐个组件去补 `display: none` 的覆盖规则 —— 也就不用指望"以后每个新组件都记得处理"。

**典型受害组件**：弹窗 / 遮罩（常用 `display:flex` 居中）、tooltip、下拉菜单、
用 `display:grid` 排版的列表容器 —— 凡是"既要能隐藏、又要有特定 display 布局"的都会中招。

**为什么重要**：这类 bug 会**伪装成逻辑 bug**。本次现象是"弹窗内容全空、按钮没反应"，
看起来像 JS 的事件绑定或赋值写错了，实际是那个弹窗**根本没被程序调用过**，
只是"因为没藏住而被迫露在屏幕上"。往 JS 里查会白费很多时间。

**来源**：BUG-009

### L-008 内容全空 + 交互全失效 → 先怀疑「它本不该出现」

**规律**：如果一个组件**所有动态字段都是空的、所有交互都没反应**，
那通常不是"内容或事件写错了"，而是**"这个组件根本不该出现在这里"** ——
它没被任何代码初始化过，所以既没数据、也没绑事件。

**判别方法**：

| 现象 | 更可能的原因 |
|---|---|
| 字段**部分**为空、部分正常 | 取值逻辑写错了 |
| 字段**全部**为空，且按钮全无反应 | 组件**没被初始化** / 不该显示 |
| 单个按钮失效，其他正常 | 那个按钮的事件没绑对 |

**为什么重要**：这条能省下一大截排查时间 —— 往"初始化时机 / 显示条件"查，
比往"每个字段怎么取值"查快得多，因为后者有几十个地方要逐个看。

**来源**：BUG-009

### L-009 测试通过不等于测到点子上，先做「反向复现」

**规律**：一个"全绿"的测试，只有在**它确实能测出坏情况**的前提下才有意义。
否则绿灯可能只是测试环境**自带的能力把 bug 掩盖了**。

**本次实例**：用 jsdom 验证 CSS 修复，报告"13 项全过"，看起来完美。
但 jsdom **自己内置了 `[hidden] { display: none }` 的默认样式** ——
于是无论修复规则在不在，它都返回 `none`，**修复前后没区别**，测试完全是假阳性。
改用**真实浏览器**（Chromium）重测，并**特意去掉修复规则跑一遍确认能复现坏的显示**，
才算真正验证了根因。

**可操作的做法**：改完 bug 后，**先把修复撤掉跑一次，确认测试变红**；
再装回修复跑一次，确认变绿。两头都验过，这条测试才可信。

**为什么重要**：依赖"内置默认行为"的测试工具（DOM 实现、CSS 引擎、mock 框架）很容易
把被测代码的缺陷补齐。**测试环境越"聪明"，越要警惕它替你把 bug 兜住了。**

**来源**：BUG-009

### L-010 临时输出文件必须写「已忽略目录」的绝对路径

**规律**：需要把命令输出重定向到文件时（本机 PowerShell 抓不到 stdout，必须 `Out-File`），
**目标路径要写「已被整体忽略的目录」的绝对路径**，例如：

```powershell
... | Out-File "D:\file\myblogweb\.workbuddy\tmp\x.txt" -Encoding utf8
```

**别写相对路径**（如 `Out-File t2.txt`）—— 那样文件会落在**当前工作目录**里，
而当前工作目录往往是仓库内的某个子目录，于是它就静静躺在那儿等着被 `git add -A` 收走。

**为什么重要**：
1. 这类误入**永远不报错、不警告**，只能靠回看提交明细发现
2. `.gitignore` 里为「不误伤子目录」而加的前导斜杠规则（如 `/_*.txt`），
   反过来意味着**子目录里的临时文件完全没人管** —— BUG-001 是根目录踩的，
   BUG-011 是 `博客管理工具/` 子目录踩的，**同一个坑换了个位置又踩一次**
3. 真正的解法不是把忽略规则越写越多，而是**一开始就别把临时文件产生在仓库内容区**

**配套习惯**：跟 AI 说「写个文件给我看输出」时，或自己用命令抓输出时，
**先确认落在哪儿**；提交后**回看一遍 `create mode` 那几行**。

**来源**：BUG-011（BUG-001 的复发）

### L-011 「TCP 能连通」≠「netstat 能查到该端口」

**规律**：判断"某端口有没有服务"和"查出该端口属于哪个进程"是**两套完全不同的机制**，
前者能成立**推不出**后者能用。

**本次实例**：`isPortInUse()` 用 TCP 连接去探，一直工作正常；
于是理所当然地认为"既然端口通，那用 `netstat -ano` 就能查出进程号"。
实测结果：**netstat 输出里压根没有 4321 那一行**，`127.0.0.1` / `::1` / `[::]` 三种写法全搜过都没有。
而同一时刻 `[::1]:4321` 明明返回 200。

**可操作的做法**：凡是"要找出某个进程是谁"这类需求，
**先用一个最小探针脚本验证这个查法在这台机器上确实有输出**，再去写业务代码。
别把"能检测"当成"能定位"。

**为什么重要**：这次是按计划写完了一整套 `netstat` 解析逻辑（连 IPv6 方括号格式都处理了），
测的时候才发现整条路根本不成立，**白写一大段还多绕一轮**。
探针脚本成本是 2 分钟，代价差得很远。

**来源**：BUG-010

### L-012 按命令行认进程，比按端口认进程可靠

**规律**：需要"找到我们自己的某个 node 进程"时，**优先看命令行，不要看端口**。
- 端口只能说"有个东西在监听" —— 不知道是谁
- 命令行能直接说明"它是谁、在跑什么、从哪个目录起的"

**本项目的做法**（可直接复用）：

```javascript
// PowerShell 拿所有 node 进程的 pid + 命令行
Get-CimInstance Win32_Process |
  Where-Object { $_.Name -eq 'node.exe' } |
  Select-Object ProcessId,CommandLine | ConvertTo-Json -Compress
```

然后筛出**命令行同时包含 `astro` 和本站点目录**的。

**Astro 进程的命令行特征**（实测）：

```text
"node" "D:\file\myblogweb\site\node_modules\.bin\..\astro\bin\astro.mjs" dev
```

**为什么重要**：端口方案不但可能查不到（见 L-011），
更重要的是**不安全** —— 端口被别的程序占用时，"按端口找进程"会找到**别人的进程**，
下一步就是误杀。命令行匹配带上了"我们的站点路径"这个条件，天然排除误伤。

**来源**：BUG-010

### L-013 本机调外部命令一律用异步 `spawn`，不用 `spawnSync`

**规律**：在这台机器上，node 的**同步**子进程 API（`spawnSync` / `execSync`）
调任何外部命令都直接返回 **`EBUSY`**，`stdout` 是空字符串、`status` 是 `null`。
**异步 `spawn` 完全正常**。

**实测对照**：

```text
spawnSync netstat  → status=null  error=EBUSY  stdout=""
spawn     netstat  → code=0       收到 26893 字节输出
spawn(..., {shell:true}) → code=0 收到 26819 字节输出
```

**可复用的替代写法**：

```javascript
function runCommand(cmd, args) {
  return new Promise((resolve) => {
    let out = '';
    const child = spawn(cmd, args, { windowsHide: true });
    child.stdout?.on('data', (d) => { out += d.toString(); });
    child.on('error', () => resolve(''));
    child.on('close', () => resolve(out));
    // 记得加兜底超时，别让命令卡住把请求挂死
    setTimeout(() => { try { child.kill(); } catch {} resolve(out); }, 10000);
  });
}
```

**为什么重要**：
1. 这是**反直觉的** —— Windows 上按常规习惯写 `spawnSync` 是很自然的事，
   而"同步 API 整个不可用"不是任何一种常见故障，不会有人预想到
2. 失败方式很隐蔽：**不抛异常**，只返回一个空的 `stdout` 和一个 `EBUSY` 错误对象；
   如果代码里没检查 `r.error`，就会表现成"命令跑了但什么都没查到"，
   很容易误判成"输出解析写错了"而不是"命令根本没跑起来"
3. 这次**连探针脚本都踩了同一个坑**，导致多绕了一轮才有结论

**配套习惯**：调用外部命令后，**要检查 `r.error`**（异步版是 `child.on('error')`），
不能只看 `stdout` 有没有内容 —— 空输出有两种可能，得能区分开。

**来源**：BUG-012

### L-014 `npm install` 没输出就换源，别硬等

**规律**：`npm install` 超过 60 秒**没有任何输出**，基本可以判定是网络问题（源太慢），
直接中断，换成国内镜像重试：

```bash
npm_config_registry=https://registry.npmmirror.com npm install <包名>
```

（也可以写进 `.npmrc` 一劳永逸：`registry=https://registry.npmmirror.com/`）

**为什么重要**：
1. **这是第二次踩同一个坑** —— BUG-002（2026-09-19）那次是 esbuild 的 postinstall
   失败后挂起 23 分钟；这次是官方源太慢，挂了 5 分半。**同类问题已经出现过两回**
2. 换源前后的对比极其鲜明：**挂 5 分 29 秒 → 换源后 5 秒装完 53 个包**
3. 挂起时**没有任何报错**，看起来像"还在努力"，实际是彻底停滞。
   判断依据不是"等了多久"，而是**可观测副作用有没有变化**
   （`node_modules` 里有没有出现目标包的目录）—— 这正是 L-002 说的那条

**配套习惯**：`npm install` 超过 60 秒还没动静，开另一个终端 `ls node_modules | grep <包名>`
看一眼目标包目录建出来没有。没有 → 换源。

**来源**：BUG-002 / BUG-013

### L-015 「某个包不再默认安装」是版本升级信号，照它说的补装

**规律**：框架报错说「XXX 不再默认安装，请运行 `npm install XXX`」时，
**这是版本升级带来的 breaking change，不是你的配置写错了**。照报错说的补装即可，
不要急着去改配置写法。

**实例**（BUG-013）：Astro 7 把默认 Markdown 处理器从 `unified` 换成了 Sätteri，
于是 `markdown.remarkPlugins` 这类配置直接失效，报错说
`@astrojs/markdown-remark` 不再默认安装 —— 补装这个包就好，
`astro.config.mjs` 里的写法**一个字都不用改**。

**为什么重要**：
1. **网上教程普遍滞后** —— 绝大多数 Astro 数学公式教程还停留在 v4/v5 的写法，
   照着抄会撞上这个报错，而教程里没有这一条
2. 报错信息本身已经把解法写出来了（`Install it with: npm install ...`），
   但**第一反应容易是"我配置写错了"，去改写法反而越改越乱**

**配套习惯**：遇到这类报错，先看它有没有给"安装什么"的指示。给了就直接装，先别动代码。

**来源**：BUG-013

### L-016 「构建成功」不等于「看起来对」

**规律**：第三方样式表（`katex.min.css`、`highlight.js` 的主题等）**不会自动引入**，
漏引时**构建完全不报错**，只是页面上难看。凡是涉及视觉效果的改动，
构建通过只是及格线，**必须实际渲染看一眼**。

**实例**（BUG-013）：`rehype-katex` 只负责把数学节点转成带 class 的 HTML 结构，
至于这些 class 长什么样，全靠使用者自己引 `katex.min.css`。
漏引的话公式会退化成一堆歪斜的普通文字，而 `npm run build` 全程一声不吭、退出码 0。

**怎么验证**（两条互补，都要做）：
1. **查产物** —— 在 `dist/` 里 grep 一下有没有那个 css 的引用
   ```bash
   grep -o 'katex[^"]*\.css' dist/posts/<文章>/index.html
   ```
2. **看渲染** —— 用真实浏览器截图，肉眼确认位置对不对

**为什么重要**：这是「静默失败」的典型 —— 没有任何信号告诉你出问题了，
**不主动去看就永远发现不了**。而这类失败恰好只影响读者体验，不影响构建流程，
所以自动化测试也抓不到（除非专门写视觉断言）。

**来源**：BUG-013
