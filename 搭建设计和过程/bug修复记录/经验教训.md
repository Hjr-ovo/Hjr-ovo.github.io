# 经验教训

> 只放**跨 bug 的通用规律**。单个 bug 的具体反思留在 `bug修复记录/YYYY-MM-DD.md` 对应卡片里。
>
> 判断标准：这条规律能不能一句话说清、并且以后还可能再犯？能，才写进来。

## 规律清单

- **L-001** 排除类规则别靠列举文件名，要用通配符覆盖整类，或把文件放进已被整体忽略的目录 —— 来源 BUG-001（2026-09-19）
- **L-002** 长任务卡住的判据是「可观测副作用是否变化」，不是「等了多久」 —— 来源 BUG-002（2026-09-19）
- **L-003** 在 Windows 上删海量小文件目录（如 node_modules）要用 `robocopy /MIR`，别用 `Remove-Item -Recurse` —— 来源 BUG-002（2026-09-19）
- **L-004** 覆盖写一个旧文件会继承它的编码签名（如 BOM），写「对字节敏感」的文件时要先确认或换新文件名 —— 来源 BUG-003（2026-09-19）
- **L-005** 用程序生成 Windows 的 `.bat` / `.cmd` 必须写 CRLF 行尾，且注释保持纯 ASCII（`chcp 65001` 加中文注释会报错） —— 来源 BUG-008（2026-09-20）
- **L-006** 「脚本内容对但双击不工作」先查文件的行尾与编码，不要先查逻辑 —— 来源 BUG-008（2026-09-20）

## 详细说明

### L-001 排除规则别靠"点名"

**规律**：凡是靠逐条列举文件名来排除的 ignore 规则，都会随着新文件名出现而失效。

**两种正确做法：**

1. **整体目录** —— 把临时 / 生成的文件统一放进一个已被忽略的目录（本项目用 `.workbuddy/tmp/`）
2. **通配符覆盖整类** —— 如 `/_*.txt` 一次覆盖根目录所有下划线开头的 txt

**为什么重要**：点名式规则的维护成本随文件种类线性增长，而且**失效时静默无提示** —— 不报错、不警告，只会悄悄把不该提交的东西提交上去，等发现时已经在历史里了。

**来源**：BUG-001

### L-002 判断"卡死"要看副作用，不看耗时

**规律**：一个没有输出的长任务，**不能靠"再等等看"来判断它是慢还是死了**。
必须挑几个会随进度变化的可观测指标，隔一段时间对比，**指标零变化 = 卡死**。

**可用的指标**（本项目实测有效）：

| 指标 | 怎么取 |
|---|---|
| 目标目录条目数 | `(Get-ChildItem <目录>).Count` |
| 目标目录总体积 | `Measure-Object -Property Length -Sum` |
| 最近 N 分钟内被修改的文件数 | 按 `LastWriteTime` 过滤 |
| 进程累计 CPU 时间 | `Get-Process <名> \| Select CPU` |

**为什么重要**：这次一个 npm 安装卡死了 23 分钟，全程**没有任何报错、没有任何输出**。
如果早点用「间隔 10 分钟对比四项指标」的办法，能省下十几分钟。
更糟的是「没输出」很容易被误读成「正在下载大文件」，让人白白等待。

**补充**：任务本身也会留痕迹。npm 的调试日志在 `%LOCALAPPDATA%\npm-cache\_logs\`，
卡住时翻它末尾，通常能直接看到停在哪个包、哪一步。

**来源**：BUG-002

### L-003 Windows 上删海量小文件目录，用 robocopy 而不是 Remove-Item

**规律**：在 Windows 上清理 `node_modules` 这类"文件数极多、路径极深"的目录时，
**`Remove-Item -Recurse -Force` 会因长路径限制静默失败一部分** ——
命令本身不报错，你以为删干净了，其实留了一堆残留。

**可靠做法**：

```powershell
New-Item -ItemType Directory -Path <空目录> -Force
robocopy <空目录> <要删的目录> /MIR
Remove-Item <要删的目录> -Recurse -Force
```

`robocopy /MIR` 把空目录镜像过去，等于清空，且**不受长路径限制**，几秒完成。

**为什么重要**：这次"删过了但其实没删完"，导致 npm 在半残目录上做增量安装，
最终 `astro build` 报 `ERR_MODULE_NOT_FOUND`（某个包缺 `index.js`）。
**排查方向一度跑偏到"是不是 `--ignore-scripts` 导致的"**，实际根因是删不干净。

**配套要求**：这类删除**删完必须验证** —— 数条目、看大小是否为 0，不能只看命令有没有报错。

**来源**：BUG-002

### L-004 覆盖写旧文件会继承它的编码签名

**规律**：一个文件如果曾被 A 工具创建（带 BOM 或某种特定编码），之后用 B 工具"覆盖写"，
**可能只替换了内容、却保留了原有的编码签名**。BOM 就这样长期潜伏在文件开头。

**本次实例**：`COMMIT_MSG.txt` 由 PowerShell `Set-Content -Encoding UTF8` 创建（PS 5.1 会写 BOM），
之后覆盖写仍带 BOM；`git commit -F` 把 BOM 当作正文收进提交对象，`git log --oneline` 里就多出一个乱码字符。

**两种可靠做法**：

1. **换新文件名**，而不是覆盖旧文件 —— 新建的文件不带历史包袱
2. **写完验头 3 字节** —— `EF BB BF` 就是 BOM。
   要写无 BOM 的 UTF-8：先以 `utf-8-sig` 读入（自动剥离），再以 `utf-8` 写回；
   或在 PowerShell 里用 `UTF8Encoding($false)`

**为什么重要**：BOM 是典型的"看不见但会被程序当成数据"的东西。
Markdown 渲染器普遍容忍它，所以问题长期不暴露 —— 直到它被塞进 git 提交信息、JSON、配置文件这类**对字节敏感**的地方才显形。
而且**全程静默、无任何报错**，只能靠核对输出发现。

**来源**：BUG-003

### L-005 程序生成的 `.bat` 必须 CRLF + ASCII 注释

**规律**：用 Node / Python / 脚本"写"出来的 Windows 批处理文件，默认往往是 LF 行尾，
而 **cmd.exe 要求 CRLF**。行尾不对时它逐行解析会错位：`set` 赋值不生效（变量变空）、
`cd` 不生效，脚本会带着一堆空值继续往下跑，最后以"命令找不到"（9009）收场。

**第二个雷**：很多人为了显示中文特地加 `chcp 65001`，但这会让**含中文的 `REM` 注释**开始报错 ——
cmd.exe 解析某些多字节序列时会吞掉行首的 `REM ` 前缀，然后拿注释去当命令执行。
实测踩中的字符是**全角括号 `（）` 与全角等号 `＝`**。

**可靠写法**：

1. 生成时显式写 `\r\n`，别依赖编辑器/工具的默认换行
2. **注释一律纯 ASCII**（英文），中文只放在 `echo "..."` 里 —— echo 的内容不受影响，实测正常显示
3. 写完验一下：CRLF 行数 > 0、纯 LF 行数 == 0、非 ASCII 的 `REM` 行 == 0

**为什么重要**：这两个问题叠在一起的效果是**「黑窗口一闪而过、零反馈」** ——
连兜底的 `pause` 都被跳过，报错看不见。第一反应容易误判成"文件损坏"或"杀毒软件拦了"。
而只要用程序生成过 `.bat`，就几乎必然踩中第一层。

**来源**：BUG-008

### L-006 「脚本内容对但双击不工作」先查行尾与编码

**规律**：自己写的脚本，在 PowerShell / Node / 编辑器里跑得好好的，一双击就废 ——
这时候**不要先怀疑逻辑**（逻辑不可能换个执行环境就突然错），
**先怀疑文件本身**：行尾（CRLF vs LF）、编码（BOM、UTF-8 vs GBK）、文件扩展名关联。

**排查手法**：直接读字节，别靠肉眼看。
`[System.IO.File]::ReadAllBytes(...)` 看前几个字节有没有 `EF BB BF`（BOM）、
统计 `0D 0A`（CRLF）与孤立 `0A`（LF）各多少 —— 这次就是靠这个一眼看出"CRLF 0 行、纯 LF 55 行"。

**配套**：一闪而过的报错抓不到时，**写诊断脚本把每一步 `echo [N] ... >> file` 落盘再读**。
本次就是靠它发现 `cd` 明明写了却没生效。

**为什么重要**：「零反馈」的故障最容易让人乱猜方向、浪费时间。
而"读字节"这个动作成本极低、结论却是确定的，比任何猜测都快。

**来源**：BUG-008
