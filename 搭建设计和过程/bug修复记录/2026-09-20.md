## BUG-008 双击 启动.bat 黑窗口一闪而过（LF 行尾 + 中文注释双重故障）

- 发现时间：2026-09-20 15:15（用户双击后反馈「一闪而过就没了」）
- 现象：双击 `启动.bat`，黑色命令行窗口**出现不到一秒就消失**，工具没起来、浏览器也没开。
  因为跑得太快，连脚本里兜底的 `pause` 都没来得及显示任何信息
- 复现步骤：
  1. 在资源管理器里双击 `博客管理工具\启动.bat`
  2. 观察：黑窗口一闪即没，无任何提示
- 报错信息：一闪而过时看不到。用重定向抓下来，实际是**两条**错误：
  ```
  '""' is not recognized as an internal or external command
  '己会打开浏览器到' is not recognized as an internal or external command
  '上的「打开博客」按钮控制它）' is not recognized as an internal or external command
  ```
  以及 `node exited rc=9009`（= 命令找不到）
- 定位过程：
  1. 先怀疑「找不到 node」→ 写诊断脚本把每一步写进文件，发现 `[4] NODE FOUND`，**node 是找到了的**
  2. 但 `[6] cd tool, now=D:\file\myblogweb` —— **`cd` 没生效！** 本该切到 `博客管理工具\`，却停在上级目录
  3. 且 `'""' is not recognized` 说明 `%NODE_EXE%` 展开后是**空的**（引号里没内容）
  4. 用 `[System.IO.File]::ReadAllBytes` 直接读字节：**前 16 字节 `40 65 63 68 6F 20 6F 66 66 0A`** ——
     `\n` 是 `0A`（LF），**不是 Windows 的 `0D 0A`（CRLF）**。全文统计：**CRLF 0 行、纯 LF 55 行**
  5. 把行尾转成 CRLF 后重测：`[6] cd tool` 成功、node 正常启动 → **第一层根因确认**
  6. 但转完之后又冒出新的两条：`'己会打开浏览器到' is not recognized` ——
     定位到是**含中文的 `REM` 注释行**出问题（共 5 行含全角括号 `（）` / 全角等号 `＝`）
- 根因：**两层，都是文件编码 / 行尾与 cmd.exe 的兼容问题，叠在一起**
  1. **第一层：行尾是 LF 而非 CRLF。** 文件是我用工具以 `\n` 写出的，而 Windows 批处理**必须用 CRLF**。
     行尾不对时 cmd.exe 逐行解析会错位：`set "NODE_EXE=..."` 这类行没被正确执行（变量成空 → 展开出 `""`），
     `cd /d "%~dp0"` 也没生效。结果是脚本**继续往下跑**、但每一步都用错的值，
     最后 `node` 调用失败（9009），脚本走到末尾，而 `pause` 前面那行同样没被正确解析 —— 于是窗口直接关掉
  2. **第二层：`chcp 65001` + 含中文的 `REM` 注释。** 切到 UTF-8 代码页后，
     cmd.exe 解析某些多字节序列时会**吞掉行首的 `REM ` 前缀**，于是注释被当成命令去执行 → 报「不是内部或外部命令」。
     踩中的字符是全角括号 `（）` 与全角等号 `＝`（共 5 行）
  → 两层叠加的效果就是"一闪而过"：既没启动成功，也没有任何可读的提示
- 修复：
  1. **行尾统一成 CRLF**（用脚本读入后 `\r\n` 重写，不用编辑器另存，避免又被写成 LF）
  2. **把 `REM` 注释全部改成纯 ASCII**，中文只保留在 `echo "..."` 里（echo 的内容不受此问题影响，实测正常显示）
  3. 顺手把 `title` 也改成 ASCII（`Blog Tool`），并把「找不到 node」的提示写得更明确
- 涉及文件：`博客管理工具/启动.bat`
- 验证：✅ 实测
  - 行尾：**CRLF 60 行、纯 LF 0 行**；**非 ASCII 的 `REM` 行 0 条**
  - 用 `cmd /c` 真实拉起 `启动.bat`：窗口输出**干干净净**，无任何 `not recognized` 报错：
    ```
    博客管理工具已启动
    ────────────────────────────────────────
    管理界面：  http://127.0.0.1:5678/
    文章目录：  D:\file\myblogweb\site\src\content\posts
    删除备份：  D:\file\myblogweb\.workbuddy\tmp\deleted-posts
    ────────────────────────────────────────
    关掉这个窗口 = 关闭工具（博客不受影响）
    ```
  - 服务可用：`http://127.0.0.1:5678/` 返回 **200**、`/api/posts` 返回 **200**（读到 1 篇文章）
  - 浏览器：确认真实被拉起（调用前后浏览器进程数有变化）
- 反思：
  1. **「一闪而过」几乎总是行尾或编码问题，不是逻辑问题。** 因为自己写的脚本在 PowerShell / Node 里跑得好好的，
     逻辑不可能突然错 —— 换了个执行环境（cmd.exe）才暴露。**凡"脚本内容对但双击不工作"，先查文件本身的行尾与编码**
  2. **Windows 批处理永远是 CRLF**，这是硬要求不是习惯。用程序生成 `.bat` / `.cmd` 时必须显式写 `\r\n`，
     否则在 Git Bash / 编辑器里看着完全正常，一双击就废
  3. **这个坑最阴的地方是「零反馈」** —— 报错一闪而过看不见，`pause` 也被跳过，
     所以第一反应会是"文件损坏了"或"是不是杀毒软件拦了"。**先别猜，用诊断脚本把每一步写进文件再读**，
     这次就是靠 `echo [N] ... >> file` 才定位到 `cd` 没生效
  4. **`chcp 65001` + 中文注释是个被低估的组合雷**：很多人为显示中文特地加 `chcp 65001`，
     结果反而让中文 `REM` 注释开始报错。**安全的做法是注释用 ASCII、中文只放 `echo` 里**，
     两头都稳（这也正是 Unity / 各类工具链的 bat 普遍用英文注释的原因）

- 状态：已修复

## BUG-007 工具误报「博客启动失败」，其实 Astro 2 秒就绪了

- 发现时间：2026-09-20 14:13（跑博客管理工具的一键启动测试时）
- 现象：调 `/api/blog/start`，工具**白等 60 秒**后报「等了 60 秒博客还没起来」。
  但同一时刻，Astro 的输出明明是 `ready in 1892 ms`，而且手动访问 `localhost:4321` 返回 200 —— **博客早就好了**
- 复现步骤：
  1. 启动博客管理工具
  2. 点「打开博客」（或调 `/api/blog/start`）
  3. 观察：Astro 正常启动，但工具的等待轮询一直认为"还没就绪"，直到超时
- 报错信息：`等了 60 秒博客还没起来。可能是依赖没装（在 site 目录跑一次 npm install --ignore-scripts），或者首次启动比较慢`
  —— **完全指错了方向**，因为根本不是慢
- 定位过程：
  1. 看 Astro 自己的输出：`ready in 1892 ms` + 后续 `[200] / 71ms` → **肯定不是没启动**
  2. 单独写脚本，对三个地址各发一次请求：
     | 地址 | 结果 |
     |---|---|
     | `http://127.0.0.1:4321/` | ❌ `ECONNREFUSED` |
     | `http://localhost:4321/` | ✅ 200 |
     | `http://[::1]:4321/` | ✅ 200 |
  3. 再用 `net.connect` 核对底层：连 `127.0.0.1:4321` 拒绝，连 `::1:4321` 通
  → **根因锁定：地址族不匹配**
- 根因：**Astro 的 dev server 只绑 IPv6 的 `::1`，不绑 IPv4 的 `127.0.0.1`**（新版 Vite 的默认行为）。
  而我的就绪检测只查了 IPv4 的 `127.0.0.1` —— 查了个"没人监听"的地址，自然永远得到 false，
  于是把"博客早就好了"误判成"还没起来"，一直等到 60 秒超时
- 修复：`isBlogRunning()` 与 `isPortInUse()` 都改成**同时试多个地址**：
  - `isPortInUse()`：并行 `net.connect` 到 `127.0.0.1` 与 `::1`，任一通即算端口被占
  - `isBlogRunning()`：依次 `fetch` `localhost` / `127.0.0.1` / `[::1]` 三个 URL，任一返回 ok 即算活着
  - 顺带修掉调用处：`server.mjs` 里原先传了 `TOOL_HOST` 参数，新签名不再需要host 参数
- 涉及文件：`博客管理工具/src/blog-server.mjs`、`博客管理工具/src/server.mjs`
- 验证：✅ 实测
  - 博客未启动时调用 → `ok: true`，耗时 **2.4 秒**（原先 60 秒超时 + 误报失败）
  - 博客已启动时再调用 → `ok: true, alreadyRunning: true`，耗时 **0.1 秒**，**没有重复启动**
  - 完整链路测试（发文 → 博客出现 → 改 → 草稿 → 删）19 项全过
- 反思：**「连不上」有三种完全不同的原因，别急着归咎于应用层。**
  这次第一反应是"Astro 启动慢"或"依赖没装"，但真正的原因是**测试代码连错了地址族**。
  更具体的一条：`127.0.0.1` 和 `localhost` **不是等价写法** —— 在现代系统上 `localhost` 可能解析到
  IPv6 的 `::1`，而服务只监听了其中一个协议栈时，两者结果能完全相反。
  浏览器会自动重试各种解析结果，所以**人手动访问没问题、程序按固定 IP 去连却失败** ——
  这个差异只有写成自动化检测时才暴露。**凡是"服务起来了但程序说连不上"，先怀疑地址族，别先怀疑服务**

- 状态：已修复

## BUG-006 frontmatter 里的反斜杠越存越多（转义没做反转义）

- 发现时间：2026-09-20 14:05（核心逻辑自测第 2 组发现）
- 现象：标题或摘要里含双引号时，写进文件再读出来，引号前面会**多出一个反斜杠**；
  如果反复"读出→保存"，反斜杠会**每次多一层**越积越多
- 复现步骤：
  1. 新建文章，摘要填 `含 " 引号 和 # 井号`
  2. 保存 → 读回 → 摘要变成 `含 \" 引号 和 # 井号`
  3. 再保存一次 → 变成 `含 \\\" 引号…`
- 报错信息：**不报错**。YAML 仍然合法，Astro 也能构建 —— 只是**内容被悄悄改坏了**
- 定位过程：
  1. 自测的"往返一致性"用例失败：期望 `含 " 引号 和 # 井号`，实际 `含 \" 引号 和 # 井号`
  2. 直接打印 `buildFile()` 的产物：`description: "含 \" 引号 和 # 井号"`
     → **写出去的时候转义是对的**（YAML 里双引号字符串确实该转义 `\"`）
  3. 那问题就在读回来的时候 → 查 `stripQuotes()`：
     ```js
     return s.slice(1, -1);   // 只剥掉首尾引号，没管内部转义
     ```
     → **确认：解析时没有做反转义**
- 根因：**转义与反转义不对称。** `yamlString()`（写）会把双引号转义成 `\"`，
  但 `stripQuotes()`（读）只把首尾的引号剥掉，**没有把 `\"` 还原成 `"`**。
  于是每次读写循环都留下一层反斜杠。
  这是"只实现了一半的对称逻辑" —— 写的时候想到了 YAML 规则，读的时候忘了对应的规则
- 修复：`stripQuotes()` 补上反转义：
  - 双引号字符串：`\"` → `"`、`\\` → `\`
  - 单引号字符串：按 YAML 规则 `''` → `'`
- 涉及文件：`博客管理工具/src/frontmatter.mjs`
- 验证：✅ 实测
  - 含引号、冒号、`#` 的标题/摘要往返一致（新增 2 条专门用例）
  - 含 `C++`、`Node.js` 这类特殊字符的 tags 往返一致
  - 核心逻辑自测 **54 / 54 全过**
- 反思：**凡是有「编码」就必须有配套的「解码」，两者要在同一个地方一起写、一起测。**
  这次写转义时很上心（还专门处理了 `#` 和冒号），但读的路径只考虑了"剥引号"这最简单的情况 ——
  因为**写的时候我想到的是"要产出合法 YAML"，读的时候想到的是"要把值取出来"，两个目标不同，就漏了一半**。
  实用做法：**别分开想**，直接写「往返测试」（存进去再读出来，看是否一样）——
  这个测试是唯一能自动发现"转义不对称"的手段，光看单侧代码是看不出来的

- 状态：已修复

## BUG-005 用 `shell: true` 启动 npm，路径里的空格把 cmd.exe 搞糊涂了

- 发现时间：2026-09-20 14:12（第一次测试「一键打开博客」时）
- 现象：点「打开博客」立刻失败，报 `Astro 进程退出了（退出码 1）`，
  日志里是一段乱码的中文错误，能辨认出 `'C:\Program' 不是内部或外部命令`
- 复现步骤：1. 用 `spawn('C:\\Program Files\\nodejs\\npm.cmd', ['run','dev'], { shell: true })` 启动 2. 立即失败
- 报错信息：`'C:\Program' 不是内部或外部命令，也不是可运行的程序或批处理文件。`
- 定位过程：
  1. 报错里 `'C:\Program'` 被**截断在空格处** → 一眼看出是路径空格问题
  2. 确认原因：开了 `shell: true` 后，命令交给 `cmd.exe` 解析；
     cmd 按空格切分命令，把 `C:\Program` 当命令名、`Files\nodejs\npm.cmd` 当参数
  3. 查 `C:\Program Files\nodejs\` 目录，确认存在 `node_modules\npm\bin\npm-cli.js`
     → **有更好的启动方式**
- 根因：**`shell: true` + 含空格的绝对路径不兼容。**
  Windows 上要直接执行 `.cmd` 文件确实需要 `shell: true`（否则报 EINVAL），
  但一开 shell，路径就落到了 `cmd.exe` 的切分规则里，空格成了致命伤。
  这是个两难：不开 shell 跑不了 .cmd，开了 shell 又过不了空格
- 修复：**绕开 .cmd，直接用 node 执行 npm 的入口脚本**：
  ```js
  spawn('C:\\Program Files\\nodejs\\node.exe',
        ['C:\\Program Files\\nodejs\\node_modules\\npm\\bin\\npm-cli.js', 'run', 'dev'],
        { shell: false, cwd: SITE_ROOT })
  ```
  这样**没有 shell 参与解析**，空格路径不再是问题。
  顺带加了两项：
  - 启动前检查 `node.exe` / `npm-cli.js` / `site` 目录是否存在，缺了就给出明确的路径提示（而不是抛一个难懂的错）
  - 收集输出时**剥掉 ANSI 颜色码**，否则日志显示到界面上是一堆 `^[[36m` 乱码
- 涉及文件：`博客管理工具/src/config.mjs`、`博客管理工具/src/blog-server.mjs`
- 验证：✅ 实测 —— 博客 2.4 秒启动成功，页面返回 200，输出日志干净无乱码
- 反思：**「需要 shell」往往不是真的需要，只是没找到"绕过壳"的入口。**
  这次的两难（不开 shell 跑不了 .cmd／开了 shell 过不了空格）看着无解，
  但换个入口（不跑 .cmd，直接跑它背后的 .js）两个问题同时消失。
  更一般的一条：**遇到"这条命令在当前方式下没法跑"，先花一分钟看看它背后是什么** ——
  `.cmd` / `.bat` 通常只是薄薄一层包装，包装里面那个真正的程序往往能被直接调用，
  而直接调用就绕开了 shell、编码、引号、空格这一整类麻烦
- 状态：已修复

## BUG-004 工具单测里 `slugify('')` 返回空字符串，会生成空文件名

- 发现时间：2026-09-20 14:05（核心逻辑自测第 4 组发现）
- 现象：`slugify('')` 返回 `''` 而不是兜底名。若标题为空时调用它，
  上层的 `createPost()` 会拿到空文件名，拼出 `site/src/content/posts/.md`
- 复现步骤：
  1. 调 `slugify('')`（或标题只有标点、被清洗后什么都不剩的极端情况）
  2. 得到空字符串
- 报错信息：**在单测里才发现**。实际走界面时前端会先拦"标题没填"，所以没暴露 ——
  **但这是运气，不是设计**
- 定位过程：读 `slugify()` 代码，发现开头有这样一段：
  ```js
  let s = String(title || '').trim();
  if (s === '') return '';      // ← 提前返回了空串
  ...
  if (slug === '') slug = 'post-' + todayStamp();   // ← 兜底在很后面
  ```
  → 空标题在**第一行就返回了**，后面那个兜底逻辑**永远不会被执行**
- 根因：**"提前返回"绕过了兜底逻辑。**
  写的时候在开头加了个"空标题直接返回"的快速路径，又在末尾加了个兜底名 ——
  但这两处逻辑冲突：开头既然返回了空串，末尾的兜底就成了**死代码**。
  属于"改了一处、忘了另一处"的典型：兜底是后加的，加的时候没回头检查开头的早退分支
- 修复：把开头的提前返回改成**直接生成兜底名**，让两条路径汇合：
  ```js
  if (s === '') return 'post-' + todayStamp();
  ```
- 涉及文件：`博客管理工具/src/slug.mjs`
- 验证：✅ 实测 —— `slugify('')` 返回形如 `post-2026-09-20`；
  自测新增用例（用正则断言格式，不写死日期）通过
- 反思：**添加"兜底/默认值"逻辑时，必须回头检查所有"提前返回"的分支。**
  早退分支（`if (...) return`）最容易被忽略，因为它写在函数最上面、看起来"已经处理完了"。
  实用做法：**兜底逻辑要么写在唯一的出口处，要么在函数开头就把它和正常路径合并** ——
  别让"末尾兜底"和"开头早退"同时存在，那必须有一个是死的

- 状态：已修复
