# 2026-10-18 bug 修复记录

## BUG-016 端到端测试的「备份」把崩溃现场的脏数据当真实内容保存，还原反而把污染固化

- 发现时间：2026-10-18 14:36
- 现象：分类改名端到端测试（`.workbuddy/tmp/test-taxonomy.mjs`）重跑后，
  `site/src/data/redirects.json` 里残留两条测试重定向
  （`/categories/测试分类甲 → /categories/测试分类乙/`、`/tags/测试标签甲 → /tags/测试标签丙/`），
  `_说明` 也变成「测试用」。`git status` 显示该文件被修改，而测试日志末尾明明显示「清理现场」全过。
- 复现步骤：
  1. 跑一遍 test-taxonomy.mjs，构建步骤被 SIGTERM 杀掉（本机偶发，见下）
  2. SIGTERM 不触发 `main().catch`，测试文章与重定向表原样留在仓库里
  3. 再跑一遍 test-taxonomy.mjs → 开头 `backupRedirects()` 读到的就是这份脏状态
  4. 测试末尾 `restoreRedirects()` 把脏状态原样写回 → git diff 出现测试数据
- 报错信息：无报错，纯逻辑错误——备份策略假设「跑测试前文件一定是干净的」。
- 定位过程：测试日志显示清理通过、但文件仍脏 → 读 backup/restore 代码 →
  发现备份值取自 `main()` 开头读取的当时内容；对比 git diff 里的残留内容，
  与「上一轮崩溃现场」完全一致，确认备份源本身就是脏的。
- 根因：**备份的时机假设现场干净**。会崩溃的流程（SIGTERM 连 `catch` 都不触发）
  会把「崩溃现场」留给下一轮，而下一轮的备份忠实地把崩溃现场当成宝贝保存，
  最后的「还原」反而把污染固化下来。备份策略缺一环：**不校验备份内容是否可信**。
- 修复：`backupRedirects()` 先识别测试特征（`_说明` 为「测试用」、键名含
  「测试分类 / 测试标签」），命中就不当备份（置 null）；`restoreRedirects()`
  对 null 一律写规范空表（`CANONICAL_REDIRECTS`，文案与线上文件一致）。
  另把两个函数导出、`main()` 加「直接运行才执行」守卫，这段逻辑可以脱离
  完整测试单独验证。当前线上文件已用 `git checkout` 还原。
- 涉及文件：`.workbuddy/tmp/test-taxonomy.mjs`（临时测试脚本，未入库）、
  `site/src/data/redirects.json`（已还原为提交版本）
- 验证：新写驱动 `.workbuddy/tmp/test-redirects-backup.mjs` 单测这段逻辑，
  三场景全过——① 崩溃脏状态 → 还原成规范空表且无测试残留；
  ② 表里有真实内容 → 原样保留；③ 文件不存在 → 重建空表。跑完 `git status` 干净。
- 反思：**「先备份再动手」的前提是备份时现场干净；会崩溃的流程不能做这个假设。**
  要么备份带校验（识别得出「这不是正常状态」），要么结束状态完全不依赖备份。
  顺带：测试清理只挂在 `catch` 上是不够的，SIGTERM 面前 `catch` 形同虚设——
  清理策略要按「随时可能被杀」来设计。
- 状态：已修复
