## BUG-012 本机 `spawnSync` 调外部命令一律 EBUSY，导致关闭博客永远失败

- **发现时间**：2026-10-07 20:05
- **现象**：`stopBlog()` 写好后测试，B3 回退分支报「博客页面确实在响应，但没能查出是哪个进程在跑」。单独写探针脚本一验，发现 `spawnSync('netstat', ...)` 直接返回 `error=EBUSY`、`stdout` 是空字符串。`spawnSync('taskkill', ...)` 同理。
- **复现步骤**：
  1. 写个脚本，`import { spawnSync } from 'node:child_process'`
  2. `spawnSync('netstat', ['-ano', '-p', 'TCP'], { encoding: 'utf8', windowsHide: true })`
  3. 打印 `r.error` → 得到 `Error: spawnSync netstat EBUSY`，`r.status` 为 `null`，`r.stdout` 为 `''`
  4. 换成异步 `spawn('netstat', [...])` → **完全正常**，收到 26893 字节输出
- **报错信息**：
  ```text
  netstat: status=null  error=EBUSY spawnSync netstat EBUSY
     stdout 前 200 字: ""
  tasklist: status=null  error=EBUSY spawnSync tasklist EBUSY
     stdout 前 200 字: ""
  ```
- **定位过程**：
  1. B3 分支失败 → 先怀疑是 netstat 的输出格式没解析对，写探针脚本想看一眼 4321 那行长什么样
  2. 探针脚本自己也挂了，报 `netstat 失败: spawnSync C:\Windows\system32\cmd.exe EBUSY`
  3. 这时还没往「命令本身跑不起来」上想，以为是 `execSync` 的问题
  4. 写了个对比脚本，同一件事分别用 `spawnSync` / `spawn` / `spawn(..., {shell:true})` 各跑一遍
  5. 结果一目了然：**同步版全 EBUSY，异步版全正常**。根因锁定
- **根因**：这个运行环境里，node 的**同步**子进程 API（`spawnSync` / `execSync`）失效，一律抛 `EBUSY`（设备或资源忙）。异步的 `spawn` 不受影响。我按 Windows 上的常规习惯用了 `spawnSync`，没想过同步版本会整个不能用。
- **修复**：
  - `blog-server.mjs` 里新增 `runCommand(cmd, args)`，用异步 `spawn` 收集 stdout 并返回 Promise（带 10 秒兜底超时）
  - 所有 `spawnSync` 调用改成 `await runCommand(...)`
  - 连带把 `isProcessAlive()`、`gracefulKill()`、`forceKill()` 都改成异步（因为要在里面 await）
  - 删掉了不再使用的 `findPidOnPort()` / `isNodeProcess()`
- **涉及文件**：`博客管理工具/src/blog-server.mjs`
- **验证**：
  - 探针脚本确认 `spawn` 版能拿到 26893 字节 netstat 输出
  - 端到端测试：关闭博客走 PID 记录成功（7.4s）、B3 命令行反查成功（7.0s）
  - 全文检索 `blog-server.mjs`，代码里的 `spawnSync` 调用数为 **0**（只出现在解释性注释里）
- **反思**：**在这台机器上，调用外部命令一律用异步 `spawn`，不要用 `spawnSync` / `execSync`。** 更普适一点：**习惯性的"同步版更简单"在这里是陷阱** —— 写完先跑一个最小验证，别等整条链路测挂了再回头一个个查。这次的教训是探针脚本本身也踩了同一个坑，白白多绕一轮。
- **状态**：已修复

## BUG-010 原定「查 4321 端口反查 PID」方案根本行不通
- **发现时间**：2026-10-07 19:55
- **现象**：`stopBlog()` 的 B3 回退分支（用 netstat 查谁占着 4321）永远查不到进程号。但同一时刻博客明明在正常响应。
- **复现步骤**：
  1. 起 Astro（`npm run dev`），确认 `[::1]:4321` 返回 200
  2. 跑 `netstat -ano -p TCP`，在输出里搜 `:4321`
  3. **一行都没有**
  4. 同时 `http.request({host:'::1', port:4321})` 正常返回 9832 字节的页面
- **报错信息**：
  ```text
  === netstat 里含 :4321 的行 ===
  (一行都没有)

  === HTTP 探测 ===
  127.0.0.1: {"status":"ERR","err":"ECONNREFUSED"}
  ::1      : {"status":200,"len":9832,...}
  ```
- **定位过程**：
  1. B3 分支报「端口 4321 上找不到监听者」，第一反应是解析逻辑写错了（IPv6 地址带方括号，格式没处理对）
  2. 把 netstat 原始输出整段抓下来看，发现不是解析问题 —— **压根没有那一行**
  3. 顺手做了 HTTP 探测，才发现真正的原因：`127.0.0.1:4321` 是 `ECONNREFUSED`，只有 `[::1]:4321` 通
  4. 也就是说 Astro 只绑了 IPv6。这个事实本项目其实早就踩过（见 BUG-007 和 `isPortInUse()` 的注释），但当时只在"检测"环节处理了，没想到"反查进程"环节会遇到同样的问题
  5. 改用替代方案：用 PowerShell 的 `Get-CimInstance Win32_Process` 拿 node 进程的**命令行**，匹配 `astro` + 站点路径 → 成功拿到 PID
- **根因**：两层叠加。
  1. **Astro dev server 默认只绑 IPv6 的 `::1`**，不绑 IPv4（这是 BUG-007 就发现过的事实）
  2. 更关键的是：**`netstat -ano` 在这台机器上不显示 4321 这一行**（127.0.0.1 / ::1 / 0.0.0.0 三种格式全试过，都没有）
  所以"用端口反查进程号"这条路从根上就走不通，不是代码写错了。
- **修复**：
  - 放弃 netstat 方案，新增 `findAstroPid()`：用 `spawn` 调 PowerShell 拿所有 node 进程的 `ProcessId` + `CommandLine`，筛出**命令行同时含 `astro` 和站点路径**的
  - Astro 进程的命令行长这样，特征很明显：
    ```text
    "node" "D:\file\myblogweb\site\node_modules\.bin\..\astro\bin\astro.mjs" dev
    ```
  - 这个方法比查端口更准 —— 端口只能说明"有人在 4321"，命令行能直接证明"这就是我们站点的 Astro"
  - 关掉日志里的措辞也改了：`method` 从「端口反查」改成「命令行反查」
- **涉及文件**：`博客管理工具/src/blog-server.mjs`
- **验证**：
  - 探针脚本确认能拿到 `{"ProcessId":32976,"CommandLine":"\"node\" \"D:\\file\\myblogweb\\site\\node_modules\\.bin\\\\..\\\\astro\\bin\\astro.mjs\" dev"}`
  - 端到端测试：手动删掉 pid 文件后点关闭，`method: 命令行反查`，博客成功关掉
- **反思**：
  1. **"端口占用"不等于"端口能被查到"** —— 检测连通性（TCP 连一下）和查进程归属（netstat）是两套完全不同的机制，能用前者推出后者是错觉。凡是"要找出这个进程是谁"，别默认 netstat 一定管用，先用探针验证一次。
  2. **按命令行认进程比按端口认进程更可靠** —— 端口只说明"有个东西在监听"，命令行能说明"它到底是谁、在跑什么"。以后需要"找到我们自己的某个 node 进程"，优先考虑这条路。
- **状态**：已修复
