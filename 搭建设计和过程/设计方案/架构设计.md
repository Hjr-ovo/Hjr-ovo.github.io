# 架构设计

> 状态：**已确定（2026-09-20）** —— 依赖的三项决策（技术选型、写作流程、URL 结构）已全部拍板。
>
> 依据：`技术选型.md`（选定 Astro）、`需求与目标.md`（v1.0 定稿）、本文档「决策记录」一节。
> 本文描述**结构**（东西放哪、怎么连起来），不描述**实现**（代码怎么写）。

## 一、整体结构

分层的思路：**文档与代码分开，代码与产物分开。**

```text
D:\file\myblogweb\                  ← 仓库根目录（git 管这一层）
├── 搭建设计和过程/                  ← 全部设计文档与过程记录【不参与网站运行】
│   ├── README.md                        总览与索引
│   ├── 设计方案/                        定型的设计文档
│   ├── 文件改动记录/                    一天一个文件
│   └── bug修复记录/                     一天一个文件
│
├── site/                            ← Astro 项目的家【网站本体】
│   ├── src/                             源代码（页面、组件、样式）
│   ├── public/                          【源码】原样拷到网站根目录的静态资源
│   ├── dist/                            【产物】构建输出，自动生成
│   ├── astro.config.mjs                 Astro 配置
│   └── package.json                     依赖与命令
│
├── .workbuddy/                      ← 工具内部数据【已排除出仓库】
└── .gitignore                       ← 排除规则
```

**为什么文档和代码放在同一个仓库里**：见 ADR-002 —— 它们描述的是同一个项目，
文档（需求、设计、改动原因）与代码改动应当在**同一次提交里一起留痕**，
分开两个仓库会让「改了代码却不知道当时的判断依据」变成常态。

> 注：ADR-002 原本还提到「用提交号双向索引」，该机制已于 2026-09-20 取消（见 **ADR-012**），
> 但「同仓管理」这一结论不受影响 —— 同仓的价值在于**同一次提交里能同时看到代码与文档的对应改动**，
> 而不依赖是否记录提交号。

**为什么代码还要再套一层 `site/`**：让"网站本身"和"关于网站的一切"物理隔开。
删掉 `搭建设计和过程/` 网站照样跑；删掉 `site/` 文档也不受影响。

### 三个目录的关键区别（最容易搞混）

| 目录 | 是什么 | 手改吗 | 进版本库吗 |
|---|---|---|---|
| `src/` | 源码：页面、组件、样式 | ✅ 改 | ✅ 进 |
| `public/` | **源码**：原样拷到网站根目录的资源（favicon、需固定路径的图片） | ✅ 改 | ✅ **进**（容易误以为它是产物） |
| `dist/` | **产物**：构建自动生成的一堆 HTML | ❌ 不改 | ❌ 不进（已忽略） |

> ⚠️ `public/` 是源码不是产物，这是 Astro 与其他生成器习惯相反的地方，已在根 `.gitignore` 里重点标注。

## 二、内容链路（写文章 → 看到网页）

这是本项目的核心流程，**用户只做前两步**：

```text
① 在 Obsidian 写 Markdown
        ↓
② 整篇复制到 site/src/content/     ← 唯一的"手动"步骤
        ↓
③ Astro 构建（schema 校验 → 生成 HTML）
        ↓
④ 本地预览 / 未来上线
```

| 环节 | 谁负责 | 说明 |
|---|---|---|
| ① 写作 | **用户** | 在 Obsidian 里写，已有一套成熟工作流（模板、双链、图床） |
| ② 搬运 | **用户** | 复制 Markdown 文件到 `site/src/content/`。**这是"发文章"的全部动作** |
| ③ 构建 | Astro | 读内容 → 校验 frontmatter → 生成静态 HTML 到 `dist/` |
| ④ 预览 | 一条命令 | `npm run dev`，浏览器打开 `localhost:4321` |

### 图片的处理（已确认无需额外动作）

图片走 **PicGo 图床**，由 Obsidian 插件 `obsidian-image-auto-upload-plugin` 自动完成：

```text
粘贴图片 → 插件自动上传到 PicGo → 自动把链接替换成网络地址
```

**这意味着复制到博客时图片链接天然可用**，不需要手动搬图或改路径。

| 参数 | 实测配置（2026-09-20 读取插件配置确认） |
|---|---|
| 上传方式 | 粘贴即上传（`uploadByClipSwitch: true`） |
| 上传器 | PicGo（本机服务 `127.0.0.1:36677`） |
| 链接替换 | **自动**（`applyImage: true`） |

> **代价（诚实记录）**：图片存在 GitHub 图床而非仓库内，**站点依赖外部服务**。
> 若图床仓库改为私有或链接失效，文章里的图片会全部裂掉。
> 这是用"仓库体积小"（不需要把二进制图片塞进 git）换来的，属于自觉的取舍。

## 三、URL 结构（**已定死**）

> 这是全项目**唯一"以后改起来贵"的东西** —— 一旦公开，别人的收藏和分享链接就固定了，
> 改 URL = 制造死链。而现在还没人收藏过任何链接，**正是把 URL 定死的最好时机**。

**决定：文章 URL 不带分类。**

```text
✅ /posts/<文章文件名>           例：/posts/astro-install-pitfalls
❌ /posts/<分类>/<文章文件名>     例：/posts/开发工具/astro-install-pitfalls
```

**为什么这个决定重要**：需求文档里已经写明「主题分类前期鼓励频繁调整，攒到二十来篇再固化」。
如果 URL 里带了分类，**每次调整分类 = 一批死链**。不带分类的话，分类体系可以随便改，
所有链接纹丝不动。

| 优势 | 说明 |
|---|---|
| 分类可自由调整 | 改分类不影响任何已有链接 |
| 链接短、好分享 | 没有多层路径 |
| 万一以后想加分类 | 可以「新增」`/categories/<主题>` 这类**列表页**，而不必改动文章本身的 URL |

**代价**：单看 URL 不知道文章属于哪个主题。但这是列表页和导航栏的职责，不是 URL 的职责。

> 文件名用英文短横线式（`kebab-case`），不用中文 —— 中文 URL 在分享、粘贴、
> 跨平台时会变成一长串百分号编码，很难看也很难用。**文章标题照常写中文，只是文件名用英文。**

## 四、页面结构

第 1 版只做「必须有」里点名的，其余一律不做（避免一开始就铺太大）。

| 页面 | URL | 状态 | 干什么 |
|---|---|---|---|
| 首页 | `/` | ✅ 已做 | 按时间倒序只列**最近 10 篇**，底部按钮去归档页；导航里没有入口，从站名/头像进 |
| 全部文章（归档） | `/posts/` | ✅ 已做 | 按年份分组的全部文章；**导航栏「全部文章」指向这里**（2026-10-17 起） |
| 文章详情 | `/posts/<文件名>/` | ✅ 已做 | 正文阅读，含日期、阅读时长、目录、相关文章 |
| 分类列表 / 分类详情 | `/categories/`、`/categories/<主题>/` | ✅ 已做 | 某主题下的文章 |
| 标签列表 / 标签详情 | `/tags/`、`/tags/<标签>/` | ✅ 已做 | 某标签下的文章 |
| 站内搜索 | `/search/` | ✅ 已做 | 标题 / 标签 / 正文三范围，可勾选组合 |
| 关于 | `/about/` | ✅ 已做 | 个人介绍，文案在 `data/about.ts` |

文章 → 分类 / 标签 / 相关文章；分类、标签、归档 → 文章。

> ✅ **已补上**（2026-10-14）：分类页 `/categories/`、标签页 `/tags/` 都已上线，
> 列表页与文章页里的分类、标签胶囊现在都是可点的 `<a>`。

**「想要有」6 项已于 2026-10-17 全部落地**：站内搜索、深色模式、目录导航、阅读时长、相关文章、
关于页（`/about/`）。**多设备适配已于同日完成**（此前按用户决定推迟到功能做完之后）：
窄屏目录从「直接隐藏」改为可折叠面板，实测 320–1440px 无横向溢出。

> 写成 `src/content/config.ts` 会**静默失效** —— 不报错，但 frontmatter 校验完全不生效。
> 也就是说，你会失去 Astro 相对 Hugo 的最大优势而不自知。

## 五、内容格式（frontmatter）

每篇文章开头的字段。**用户 2026-09-20 确认：全部保留。**

```yaml
---
title: 标题
description: 一句话摘要，给搜索引擎和列表页用
pubDate: 2026-09-20
updatedDate: 2026-09-25        # 选填，不写就不显示
category: 开发工具              # 主题，一级分类
tags: [Git, Windows]           # 课程、来源等
draft: false                   # true = 不显示，只自己看
---
```

| 字段 | 必填 | 对应哪条需求 |
|---|---|---|
| `title` | ✅ | 文章标题 |
| `description` | ✅ | 面向搜索引擎的第 3 类读者 |
| `pubDate` | ✅ | 「文章日期」 |
| `updatedDate` | 选填 | 「最后更新时间」—— 不是每篇都会改，不写即不显示 |
| `category` | ✅ | 「按主题分类」 |
| `tags` | 选填 | 「课程与来源作标签」 |
| `draft` | ✅ | 让「写了但先不发」成为可能 |

> **Astro 的 schema 校验是我们的安全网**：frontmatter 写错（比如日期格式不对、必填字段缺了）
> **会直接报错并指出哪一行**。这是当初选 Astro 而非 Hugo 的次要理由（见 ADR-004），
> 在这里正式派上用场。

### 校验已实测验证（2026-09-20）

实现时故意把 `pubDate` 填成一段文字，构建立即失败（exit code 1），报错内容：

```
[InvalidContentEntryDataError] posts → _schema-test data does not match collection schema.
pubDate: Expected type "date", received "object"
Location: D:\file\myblogweb\site\src\content\posts\_schema-test.md:0:0
```

**精确指出是哪个文件、哪个字段、错在哪。** 作为对照，Hugo 在这种情况下会静默把日期当空值，
页面照常生成 —— 你不会知道出了问题。这条差异是实测的，不是推测。

### 实现细节（比上面表格多出的两点）

| 项 | 说明 |
|---|---|
| `tags` 默认值 | 不写就等于空数组，不必每篇都写 `tags: []` |
| `draft` 默认值 | 不写就等于 `false`（即公开），只有要藏起来才写 `draft: true` |

这两处用 schema 的默认值处理，是为了**减少每篇文章的必填负担** —— 写得越少，
越不容易出错，也越愿意写（对着成功标准第 5 条）。

## 五之二、数学公式（2026-10-07 落地）

需求文档里「必须有」点名的**数学公式**已实现。技术栈：

| 包 | 作用 | 版本 |
|---|---|---|
| `remark-math` | 认出 Markdown 里的 `$...$` / `$$...$$`，标记成数学节点 | 6.0.0 |
| `rehype-katex` | 把数学节点渲染成真正的 HTML 结构 | 7.0.1 |
| `katex` | 提供排版样式与字体（19 个 `.woff2`，随构建打包） | 0.19.0 |
| `@astrojs/markdown-remark` | **Astro 7 的必要前提**，见下方坑 | — |

**写法**（沿用全网的通行约定，跟 Obsidian / Typora / GitHub 一致）：

```markdown
行内公式：时间复杂度是 $O(n \log n)$

行间公式：
$$
\sum_{i=1}^{n} i = \frac{n(n+1)}{2}
$$
```

> ⚠️ **为什么必须写 `$$` 而不是 `\(...\)`**：早期 Markdown 数学排版用过 LaTeX 的
> `\(...\)` / `\[...\]` 写法，但那会跟正文里的反斜杠打架（比如写 Windows 路径 `C:\Users`）。
> 现在通行的是 `$` 写法，**Obsidian 里也是这个**，所以你在 vault 里写的公式复制过来直接能用，
> 不需要二次转换。

### ⚠️ 三个坑（都是实测踩到的，不是推测）

**① Astro 7 默认换了 Markdown 处理器，`markdown.remarkPlugins` 会直接报错**

报错原文：

```
`markdown.remarkPlugins`, `markdown.rehypePlugins`, and `markdown.remarkRehype` run on the
`unified` processor from `@astrojs/markdown-remark`, which is no longer installed by default
now that Sätteri is the default Markdown processor.
```

**Astro 7 起默认处理器换成了 Sätteri，而它不认这两个插件**，必须显式补装
`@astrojs/markdown-remark` 才能把 `unified` 那套流水线装回来。
（这条网上教程基本还没更新，装的时候容易卡住。）

**② 样式表必须手动引，且要放在 `global.css` 之后**

KaTeX 的排版（分数线位置、根号形状、上下标偏移）全靠 `katex/dist/katex.min.css`。
不引的话公式会退化成一堆歪斜的普通文字 —— **而且构建不报错**，只有肉眼看才发现。
引的位置放在 `BaseLayout.astro` 里、`global.css` 之后，这样我们自己的覆盖规则能生效。

**③ `$$` 前后要各留一个空行**

紧贴着上一行文字写 `$$`，有些 Markdown 解析器会把它当成行内公式处理。留空行最保险。

### 样式的两条微调

只改两处，**不重写 KaTeX 的排版规则** —— 数学排版的分寸感是它的长处，手改容易改坏：

| 调整 | 原因 |
|---|---|
| `.katex` 字号压到 `1.05em` | KaTeX 默认 1.21em，在正文里偏大、显得突兀 |
| `.katex-display` 加外边距 + `overflow-x: auto` | 上下给点呼吸空间；超宽公式**横向滚动**而不是撑破页面 |

### 实测验证（2026-10-07）

用一篇临时文章 `test-math-rendering.md` 覆盖了求和、极限、矩阵、积分、希腊字母、
关系符号、位运算等场景，真实浏览器实测：

| 检查项 | 结果 |
|---|---|
| KaTeX 渲染节点数 | 14 个（行内 + 行间） |
| 行间公式块 | 6 个 |
| **解析失败节点（`.katex-error`）** | **0 个** ✅ |
| 残留的裸 LaTeX 源码 | 0 处 ✅ |
| 字体加载 | `fontStatus: loaded`，20 个 KaTeX 字体 ✅ |
| 超宽积分公式 | 宽度与容器等宽，未撑破 ✅ |

验证完这篇临时文章已删除。

## 五之三、文章改名的旧链接（2026-10-07 落地）

**问题**：URL 是 `/posts/<文件名>/`（ADR-006）。文件名一改，旧链接就失效。
静态站没有服务端，**没法真的发 HTTP 301** —— 只能在旧地址放一个「跳转页」。

**解决办法（用的是 Astro 官方内置能力，不是自己造轮子）**：

```text
① 改名 → 工具往重定向表追加一条：old-name → new-name
② 构建 → Astro 在旧地址生成 dist/posts/old-name/index.html
③ 访问旧链接 → 页面里一句 <meta http-equiv="refresh"> 把人送到新地址
```

**三个文件的分工**：

| 文件 | 角色 | 谁维护 |
|---|---|---|
| `site/src/data/redirects.json` | **数据**：`{ "旧名": "新名" }` | 博客管理工具改名时自动追加 |
| `site/src/utils/redirects.mjs` | **代码**：读表 → 转成 Astro 要的格式 | 手写一次，之后不动 |
| `site/astro.config.mjs` | 一行 `redirects: loadRedirects()` | 手写一次，之后不动 |

**为什么不写进 `astro.config.mjs`**：那是手写代码。工具每次改名都去改它，
容易改坏、也容易跟手工编辑打架。**数据归数据，代码归代码。**

**生成的跳转页长这样**（Astro 自动带的，比手写还周全）：

```html
<title>Redirecting to: /posts/new-name/</title>
<meta http-equiv="refresh" content="0;url=/posts/new-name/">
<meta name="robots" content="noindex">          <!-- 叫搜索引擎别收录这个中间页 -->
<link rel="canonical" href="/posts/new-name/">  <!-- 声明权威地址是新地址 -->
```

**⚠️ 一条硬约束（BUG-014）**：表里的 key **必须是「已经不存在的文件名」**。
若旧文件还在，跳转页会和真实文章页抢同一个地址，Astro 会让**跳转页胜出**，
真文章被顶掉 —— 而且**只在构建日志留一行 `[WARN]`，不报错**。

**实测验证（2026-10-07）**：

| 环节 | 结果 |
|---|---|
| 工具改名后，表里写入记录 | ✅ `"sample-mysql-bplus-tree": "mysql-index"` |
| 构建时无冲突警告 | ✅ 日志干净 |
| 旧地址产物是跳转页 | ✅ 含 `refresh` / `noindex` / `canonical` |
| 新地址产物是真实文章 | ✅ |
| **浏览器访问旧地址 → 落点** | ✅ **自动变成 `/posts/mysql-index/`，显示真实文章，用户无感** |
| 二次改名（A→B→C） | ✅ 表里 A 直接指向 C，不留跳转链 |

**顺带修的**：改名弹窗里「改后」那行原本是硬编码占位符 `/posts/<新的文件名>/`，
用户看不见真实新 URL。现已提前算出候选名再显示。

## 六、构建与发布流程

### 现在（暂不上线）

```text
写文章 → 复制到 src/content/ → npm run dev → 浏览器预览
```

| 命令 | 干什么 | 何时用 |
|---|---|---|
| `npm run dev` | 起本地服务（`localhost:4321`），改文件自动刷新 | **日常主要用法** |
| `npm run build` | 生成静态文件到 `dist/` | 检查有没有错 |

### 被否决的方案（存档理由）

| 事项 | 被否决方案 | 否决理由 |
|---|---|---|
| 写作流程 | **不复制，让 Astro 直接读 Obsidian 文件夹** | 用户的 vault 里有日记、饮食记录、考研决策记录等**私人内容**。让博客直读整个 vault，等于把"哪些能公开"的判断权交给目录结构，有误发风险。**即便加了白名单文件夹，也要求用户写文章时始终记得"这是公开的"** —— 这份额外的心智负担与「半年后还愿意写」冲突；复制一步虽笨，但**"我复制过去的才是公开的"这条边界简单、不会错** |
| 写作流程 | 在站点内直接用 Obsidian 打开 | 用户已有的 vault 工作流（模板、图床插件、双链）无法复用；且站点内写会让"私人笔记"和"公开文章"在同一套结构里混杂 |
| URL | **带分类**（`/posts/<分类>/<文件名>`） | 分类体系还在试错期、鼓励频繁调整。URL 一旦带分类，**改分类 = 制造死链**。分类是"列表页"的职责，不该固化进文章 URL |
| 主题 | **装 Astrofly**（受 hexo-butterfly 启发的 Astro 主题） | 主题是"整个项目"而非插件，装它 = 换掉全部骨架，且它基于 Astro **v6** 而本项目是 **v7**，兼容性未经验证。**在还没有一篇真实文章的时候承担这个风险不划算**。等有内容了再回头看（见下方"什么时候该回头"） |
| 主题 | HsuBlog（另一个 butterfly 风 Astro 主题） | **最后更新 2023 年 8 月，已停更三年**。Astro 三年间迭代多次，老主题大概率跑不起来且无人维护 |
| 主题 | Hexo + 官方 Butterfly | 需要放弃已定的 Astro（ADR-004），且 Hexo 的短板（依赖多、构建慢）仍在 |

### 关于主题的说明（留给未来的自己）

用户提到"看有人加 Butterfly"。**需要澄清一个事实**：
**Butterfly（jerryc127 出品）是 Hexo 的招牌主题，没有官方 Astro 版。**
中文圈说"装 Butterfly"基本都在 Hexo 语境里。受它启发的 Astro 主题只有 Astrofly 一个在活跃维护。

**什么时候该回头考虑主题**：攒够 3-5 篇真实文章之后。那时会清楚地知道——
文章多长、表格公式多不多、代码块是不是主角、哪里难看。**主题是为内容服务的，没有内容时挑主题就是纸上看房。**

> 主题是纯外观层：**改主题不碰 URL、不影响已发文章**，是随时能改的东西。
> 所以"先不做"不是欠债，只是排后。
