# 目录与命名规范

> 状态：**已确定（2026-09-20）**
>
> 本文回答两个问题：**东西放在哪**、**叫什么名字**。
> 只写"怎么放、怎么叫"，具体有哪些文件由 `架构设计.md` 说明。

## 一、第一原则：文档与代码分开

```text
D:\file\myblogweb\
├── 搭建设计和过程/     ← 文档。不参与网站运行
└── site/              ← 代码。网站本体
```

这条边界的好处：**删掉文档，网站照样跑；删掉代码，文档也读得懂。**

## 二、代码目录（`site/`）

### 现状

**2026-09-20 已完成最小可用页面**，实际落地结构：

```text
site/
├── src/
│   ├── content.config.ts            ← 【规则】定义 frontmatter 校验（⚠️ 必须在 src/ 下）
│   ├── content/posts/               ← 【货】文章，一篇文章一个 .md
│   ├── layouts/BaseLayout.astro     ← 【骨架】全站外框
│   ├── pages/index.astro            ← 【门牌】首页 → /
│   ├── pages/posts/[...slug].astro  ← 【门牌】文章页 → /posts/<文件名>/
│   ├── styles/global.css            ← 【皮肤】全局样式
│   ├── utils/format-date.ts         ← 【工具】日期格式化
│   └── consts.ts                    ← 【名片】站点名等固定值
│
├── public/                          ← 【源码】原样拷到网站根目录的资源
├── dist/                            ← 【产物】构建自动生成，不改、不进 Git
├── astro.config.mjs                 ← Astro 配置
└── package.json                     ← 依赖与命令
```

> **上线相关（2026-11-01）**：仓库根目录多了 `.github/workflows/deploy.yml`。
> 它**不在 `site/` 里**，因为 GitHub Actions 只认仓库根目录的 `.github/workflows/`。
> 这个文件干的事：每次 push 到 `main` 就进 `site/` 装依赖、跑 `npm run build`、
> 把 `site/dist` 发布到 GitHub Pages。`dist/` 仍然不进 Git，只当构建产物上传。

**`components/` 还没建** —— 目前页面只有两个，没有值得抽出来的重复零件。
**用到再建，不预先创建空文件夹**（空文件夹在 Git 里存不下来）。

> ⚠️ **两个容易搞混的地方**：
> 1. **`public/` 是源码不是产物**，要进 Git。这跟很多生成器的习惯相反
> 2. **`content.config.ts` 在 `src/` 下，不是 `src/content/` 下**。放错位置会**静默失效** ——
>    不报错，但 frontmatter 校验完全不生效（详见 `架构设计.md` 第四节）

### 各目录干什么（用一个比喻说清）

| 目录 | 比喻 | 里面放什么 |
|---|---|---|
| `content/` | **货** | 你写的文章。**这是唯一你会经常动的目录** |
| `layouts/` | **骨架** | 所有页面共用的外框（导航栏、页脚） |
| `components/` | **零件** | 能重复用的小块。比如"文章卡片"在首页和分类页都要用 |
| `pages/` | **门牌** | `index.astro` → `/`；`posts/[...slug].astro` → `/posts/xxx` |
| `styles/` | **皮肤** | 全局样式 |
| `utils/` | **工具** | 到处要用的小函数（如日期格式化） |
| `consts.ts` | **名片** | 站点名、作者这类到处要用的固定值，集中一处改 |

> **`pages/` 的规则最简单也最容易记**：**文件名就是网址**。
> `pages/about.astro` → 网站上的 `/about`。这是 Astro 的核心机制。
>
> **方括号 = 动态路由**：`pages/posts/[...slug].astro` 不是"一个叫 [...slug] 的页面"，
> 而是"一类页面"，由 `getStaticPaths()` 告诉 Astro 要生成哪些具体的 URL。

## 三、命名规则

### 通用原则

| 原则 | 说明 |
|---|---|
| **文件名不用中文** | 中文文件名在跨平台、分享、URL 里常变成百分号编码或乱码。**内容里随便写中文，文件名用英文** |
| **全小写** | 避免大小写问题（Windows 不区分大小写，但部署到 Linux 服务器**区分**，本地能跑线上挂掉） |
| **用短横线 `-` 连接** | 不用下划线、不用空格、不用驼峰。例：`post-card.astro` |
| **名字要能读懂** | `a.astro` ❌ `post-meta.astro` ✅ |

### 分类型规则

| 类型 | 规则 | 示例 |
|---|---|---|
| **文章文件** | 英文短横线式，**名字要能被搜索命中** | `astro-install-pitfalls.md` |
| *不要用* | 拼音、日期、无意义编号 | ~~`wenzhang1.md`~~ ~~`2026-09-20.md`~~ |
| **页面文件** | 同上，**文件名就是 URL** | `index.astro`、`about.astro`、`posts/[...slug].astro` |
| **组件文件** | 短横线式，能看出是什么零件 | `post-card.astro`、`site-header.astro` |
| **样式文件** | 全局用一个 `global.css`；组件专属用同名 | `global.css`、`post-card.css` |
| **脚本文件** | 短横线式，动词开头 | `format-date.ts` |
| **图片文件** | 见下方单独说明 | —— |

### 文章命名为什么这么重要（多花两句）

需求文档里写明：**第 3 类读者是搜索引擎搜到的人，标题要能被关键词命中。**

文章文件名会成为 URL 的一部分（`/posts/<文件名>`），**搜索引擎会把 URL 里的词当作内容线索**。
所以文件名不是随便起的代号，它参与"别人能不能搜到你"。

| ✅ 好 | ❌ 差 | 为什么 |
|---|---|---|
| `astro-install-pitfalls.md` | `wenzhang1.md` | 前者含关键词、可读；后者等于没有名字 |
| `git-bom-commit-issue.md` | `2026-09-19.md` | 日期文件名会立刻过时（文章会更新，日期已经写进 frontmatter） |

> **这条规则为什么敢定**：文章**标题**照常写中文（读者看的是标题），
> 但**文件名**用英文——读者几乎不会注意 URL，而机器（搜索引擎、分享链接）非常在意它。

### 图片文件

**当前图片不走仓库存放**（见 `架构设计.md` 第二节）：
Obsidian 插件在上传时就替换成 PicGo 的网络地址，所以仓库里**基本不会有图片文件**。

如果将来确实需要在站点内放图片：

| 放哪 | 命名 |
|---|---|
| `public/images/` | `YYYY-MM-DD-描述.png`（如 `2026-09-20-astro-error.png`） |
| 文章专属的图 | 建议仍走图床，与现有工作流一致，避免仓库变大 |

## 四、文档目录（`搭建设计和过程/`）

```text
搭建设计和过程/
├── README.md           ← 总览：说明有哪些文件夹、各是什么
├── 设计方案/            ← 定型的设计文档，一个主题一个文件
├── 文件改动记录/        ← 一天一个文件 + 模板.md + README.md（索引）
└── bug修复记录/         ← 一天一个文件 + 模板.md + README.md（索引）+ 经验教训.md
```

### 命名与结构规则

| 文件夹 | 文件命名 | 特殊文件 |
|---|---|---|
| `设计方案/` | **中文名**，一个主题一个文件 | —— |
| `文件改动记录/` | `YYYY-MM-DD.md`（**当天日期**） | `模板.md`、`README.md`（索引） |
| `bug修复记录/` | `YYYY-MM-DD.md`（**发现日期**） | `模板.md`、`README.md`（索引）、`经验教训.md` |

> **为什么 `设计方案/` 用中文名，而记录文件用日期**：
> 设计方案是**给人按主题找的**（"架构设计在哪？"），中文名最直观；
> 记录是**按时间顺序积累的**，日期本身就是最好的名字。

### 记录的排版形式（2026-09-20 改定）

两份记录**都不用表格**，一律用**卡片**（`## 小标题` + 分行字段）。依据见 **ADR-010**。

| 文件 | 卡片里的字段 |
|---|---|
| `文件改动记录/YYYY-MM-DD.md` | **改了什么** / **为什么** / **提交** |
| `bug修复记录/YYYY-MM-DD.md` | 发现时间 / 现象 / 复现步骤 / 报错信息 / 定位过程 / 根因 / 修复 / 涉及文件 / 验证 / 反思 / 状态 |

**为什么不用表格**：表格的横向宽度是真实痛点 —— 6 列在编辑器里要左右拖动才能看完，
阅读时视线需要频繁横向移动。卡片纵向展开，从上往下读即可。

> **索引表也一并改为列表**（`README.md` 里的日期索引、bug 一览），保持全库无表格。

### 索引规则（2026-09-20 改定）

| 文件 | 职责 | 放哪 |
|---|---|---|
| `搭建设计和过程/README.md` | **总览**：有哪些文件夹、各记什么、规则速览 | 上级 |
| `文件改动记录/README.md` | **明细索引**：有哪些天 | 文件夹内 |
| `bug修复记录/README.md` | **明细索引**：有哪些天、有哪些 bug | 文件夹内 |

**规则：日期列表只存在于文件夹内的索引里，上级总览不再重复。**

理由：早期版本把日期表放在上级 README，导致**同一个日期列表要在两个地方维护**，
迟早对不上。分开后各管一层：**总览管"有哪些文件夹"，索引管"有哪些天"。**

> **新建日期文件后要去补索引** —— 这是本套体系唯一的手动负担。
> `文件改动记录/` 补 1 处；`bug修复记录/` 补 2 处（索引 + bug 一览）。
> 各文件夹的 `模板.md` 顶部已注明这一点，防止忘记。

### 文件数增长的代价（已知，暂不处理）

一天一个文件，一年约 365 个。**两年后**这个文件夹会有 700+ 个文件，
索引页会很长、文件夹打开会变慢。

**缓解办法（现不做）**：按月份归档一层 → `文件改动记录/2026-09/2026-09-20.md`。

**为什么不现在做**：现在一个月只有几天有记录，多一层目录 = 每次多点一次。
**触发条件**：当"补索引觉得烦"或"打开文件夹觉得卡"时再改。这个改动随时能加，
代价只是移动文件 + 改链接，不影响任何其他设计。

## 五、文档内引用（已确定）

| 规则 | 说明 |
|---|---|
| 用**相对路径** | 相对于当前文件。从上级 `README.md` 引用 → `文件改动记录/2026-09-19.md` |
| 用**正斜杠 `/`** | 反斜杠在 Markdown 里是转义符，写成 `文件改动记录\2026-09-19.md` 点不动 |
| **不用**绝对路径 | 换电脑或换盘符就断 |
| **不用** Obsidian 双链 `[[...]]` | 本项目不在 Obsidian vault 内，`[[...]]` 在 GitHub / 普通编辑器里只是一串死文本 |

示例：

- 上级指向下级：`[查看](文件改动记录/2026-09-19.md)`
- 下级指回上级：`[返回总览](../README.md)`
- 同级之间：`[经验教训](经验教训.md)`

> **`../` 是"退到上一级"**。这是相对路径里唯一需要记的符号。
