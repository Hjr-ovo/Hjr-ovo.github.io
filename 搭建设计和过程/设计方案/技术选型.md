## 一、方案大类：静态 vs 动态

| 方案 | 需要什么 | 判断 |
|---|---|---|
| WordPress 这类**动态博客** | 服务器 + 数据库 + 后台管理，要运维、要防攻击 | ❌ 排除。违背已确认的「不做后台」「不自己运维」 |
| **自己写**前端 + 后端 | 前后端全部自己实现 | ❌ 排除。会让项目变成「一直在做站、零篇文章」，成功标准第 5 条直接挂掉 |
| **静态站点生成器（SSG）** | 只要会写 Markdown | ✅ **选定**。命中全部已确认需求 |
| 直接用知乎 / 掘金 / CSDN 等平台 | 什么都不用装 | ⚖️ 备选。最省事，但内容不归自己、样式不能改 |

**为什么静态方案对本项目是零损失**：静态站做不了的典型功能是评论与访问统计（都需要服务端存数据）——
而这两项已在 `需求与目标.md` 中被明确排除。**被砍掉的功能和做不了的功能恰好重合，所以不选动态方案没有任何代价。**

静态方案的附带好处：零服务器、零数据库、零运维、免费托管、无后台可被攻击、访问速度极快。

## 二、生成器候选对比

| 维度 | Hugo | Hexo | **Astro（已选）** |
|---|---|---|---|
| 安装 | 一个 exe | Node + 大量 npm 依赖 | Node + 大量 npm 依赖 |
| 写文章位置 | `content/posts/` | `source/_posts/` | `src/content/` |
| 模板语言 | Go 模板（`{{ range .Pages }}`） | EJS | **HTML + JS/TS，接近普通网页** |
| 代码高亮 | 内置（Chroma） | 内置 | 内置（Shiki），观感更好 |
| 数学公式 | 需配置，新版稍绕 | 插件 | 装两个插件 + 配置几行，**2026-10-07 已实测跑通**（见 `架构设计.md` 五之二） |
| 生成速度 | 极快 | 文章多了明显变慢 | 快（实测 1 页约 1.7 秒） |
| frontmatter 写错时 | 常常**静默失败** | 一般不报错 | **会报错并指出出错行**（schema 校验） |
| 主题数量 | 多，技术博客主题成熟 | 多，中文主题丰富 | 较少，偏文档站 |
| 报错友好度 | 一般 | 一般 | 好（自带类型检查） |
| 改造时学到的知识 | Go 模板 —— 只在 Hugo 内可复用 | EJS —— 可迁移性低 | **HTML/JS/组件 —— 前端通用** |

**Hexo 为何退出**：核心优势是中文教程最多、卡住能搜到答案。但本项目有 AI 全程在场，
用户不需要自己搜 —— 优势被抵消，而短板（依赖多、构建慢）仍在。

## 三、最终决定

### 选 Astro

决定性理由来自用户的自我定位。当被问「你希望三年后这个博客是什么样」时，用户选择了
「**一个你亲手改造过的个人网站**」，而不是「一个稳定更新的技术文章站」。
既然确定会长期动手改造它，**「改造时学到的东西能否迁移」就成了首要标准** ——
Astro 的模板是 HTML / JS，学到的在前端通用；Hugo 的 Go 模板只对 Hugo 自己有用。

次要理由：
1. Astro 内容集合带 schema 校验，frontmatter 写错会**直接报错并指出哪一行**；Hugo 常常静默失败
2. 内置 Shiki 代码高亮，技术内容观感更好

### 代价（诚实列出，不粉饰）

- **放弃了 Hugo 最大的优势**：Hugo 是单个 exe、零依赖、「放半年回来照样能跑」——这一点其实
  正对着「半年后还愿意写」那一条。选 Astro 等于用这份确定性换可迁移的技能与更强的改造能力
- 依赖多一层不确定性：Node 版本升级、`node_modules` 被误删等情况可能需要重装依赖
- 起步多几步（装 Node 依赖）

### 切换成本说明

**这不是一次定终身的选择**：文章都是 Markdown，换工具时文章能原样带走；
但主题配置与 URL 结构需重做。所以切换成本是「配置重做」而非「内容重写」。

## 五、落地情况与验证（2026-09-19）

| 项目 | 结果 |
|---|---|
| 项目位置 | **`D:\file\myblogweb\site\`**（与 `搭建设计和过程/` 平级，文档与代码分开） |
| 脚手架 | `create-astro` v5.2.4 |
| 模板 | **`minimal`（空底板）** —— 见下方说明 |
| 版本 | **Astro v7.3.3**（Vite 8 / rolldown） |
| Node 要求 | `package.json` 的 `engines.node` = `>=22.12.0`，本机 v24.15.0 满足 |
| 构建验证 | ✅ `npm run build` → `1 page(s) built in 1.69s`，产出 `dist/index.html` |
| 依赖规模 | 193 个包，约 98 MB |

**为什么选 `minimal` 空底板而不是现成的博客模板**：内容结构与目录规范还没设计。
装一个完整的博客模板等于先塞进一堆别人的设计，等我们定好自己的结构再回头返工。
空底板让每一层都是我们按自己的规范搭的，他也能看懂。

**一个必须记住的坑**：Astro 里 **`public/` 是源码不是产物**（放 favicon、图片等要原样拷到根目录的资源），
**绝不能加进 `.gitignore`**。这和其他一些生成器的习惯相反，已在根目录 `.gitignore` 里重点标注。

## 六、已排除方案（存档理由）

| 方案 | 排除理由 |
|---|---|
| WordPress 等动态博客 | 需服务器 + 数据库 + 运维，违背「不做后台」「不自己运维」 |
| 自己写前后端 | 会把项目变成「只做站不写文章」，违背成功标准第 5 条 |
| 知乎 / 掘金 / CSDN 等平台 | 内容不归自己、样式不能改，与「搭自己的博客」目标不符 |
| Hugo | 改造时学的 Go 模板不可迁移；frontmatter 写错常静默失败 |
| Hexo | 核心优势（中文资料多）被「AI 全程在场」抵消，短板仍在 |
| Jekyll | Ruby 环境在 Windows 上是出了名的难装，与「少出故障」的要求相悖 |
