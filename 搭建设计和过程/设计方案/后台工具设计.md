## 一、先说一件影响方案的事

起草本文时发现工作区有一批**未提交**的 Obsidian 适配改造：

| 文件 | 状态 | 内容 |
|---|---|---|
| `site/src/utils/remark-obsidian.mjs` | 新文件 | `==高亮==` → `<mark>`（跨节点配对）、正文 h1 整体降级 |
| `site/src/content.config.ts` | 已改 | 字段别名：`date`→`pubDate`、`explain`→`description` |
| `site/astro.config.mjs` | 已改 | 插件已接进 `remarkPlugins` |
| `site/src/components/TableOfContents.astro`、`site/src/styles/global.css` | 已改 | 配套调整 |
| `site/src/content/posts/tmp-obsidian-test.md` | 测试残留 | 自标「验证完删除」 |

**这件事直接改变了工具的定位。** 原先假设「Obsidian 入库要手工做四件事」，其中三件已经被构建层接管了：

| 原先以为要手工做的 | 现在谁做 |
|---|---|
| `date` → `pubDate`、`explain` → `description` | ✅ 构建层 `z.preprocess` 别名 |
| `#` 章节整体降一级 | ✅ 构建层 `remarkObsidian` |
| `==高亮==` → `<mark>` | ✅ 构建层 `remarkObsidian` |
| 文件名改 kebab-case 英文 | ❌ 没人做，**只能工具或手工** |
| 归类（分类必填、标签去重） | ❌ 没人做，**只能工具或手工** |

而且构建层做的比工具做**更好**：转换只发生在内存 AST 里，`.md` 文件永远是 Obsidian 原样，作者不用维护两份不同写法的稿子。

> **结论**：工具的活儿从「五道转换关卡」缩到「起名 + 归类」，但同时又多出一件构建层管不了的事 —— **体检**（见第六节）。这个缩水是好消息，意味着工具更小、更不容易死。

## 二、上次为什么失败

删除时的核查结论（`文件改动记录/2026-10-30.md`）：四类功能里**真正在用的只有「双击启停 dev」**。
正文从来走 Obsidian（ADR-008）、分类标签手写一行就够、改名要文章多了才有意义。

失败原因不是「做得不好用」，是 **功能比真实需求多太多**。5600 行里约 95% 是摆设。

所以本文只守两条原则：

| 原则 | 含义 |
|---|---|
| **按「每次发文必经的动作」定功能** | 不按「后台通常该有什么」定功能 |
| **做不到「每天都会点」的功能就不做** | 宁可少做，不要做一堆供着 |

第二条直接决定：**不做在线写正文**（正文走 Obsidian）、**不做图片上传**（走 PicGo）、**不做主题/配置管理**（改文件就行）。

## 三、定位

| 它不是 | 因为 |
|---|---|
| ❌ 网站后台 / CMS | 静态站没有服务器、没有数据库（ADR-003），不存在「网页点发布就上线」 |
| ❌ 格式转换器 | 格式转换已归构建层的 remark 插件，工具再去改文件会造成「两份写法」 |
| ❌ 博客的一部分 | 删掉这个文件夹，网站照常跑。它是「使用者」，不是「被使用者」 |

**它是什么**：一个只服务一个人的**本地文章管家**，负责构建层管不了的那些判断性、管理性动作 ——
起名字（决定 URL）、归分类、改错了要能改、发出去之前先体检。

## 四、三块功能

| # | 功能 | 频率 | 解决什么 |
|---|---|---|---|
| 1 | **入库** | 每篇 1 次 | 把 Obsidian 的稿子放进 `posts/`，起好英文名、归好分类 |
| 2 | **管理** | 偶尔 | 文章列表、改元数据/正文、删除（带备份）、改名（带重定向）、草稿开关 |
| 3 | **体检** | 每篇入库时 + 手动全站跑 | 报出构建层默默处理、或处理不了的角落 |

## 五、入库（核心流程）

### 5.1 流程

```text
把 .md 拖进页面（或点「选择文件」）
     ↓
① 诊断：拆 frontmatter / 扫正文，列出「这篇会发生什么」
     ↓
② 起名：中文标题 → 英文 kebab 候选，**可改**，撞名即拒绝
     ↓
③ 归类：选分类（必填，可新增）、选标签（与分类重名的提示去掉）
     ↓
④ 写入：先写临时文件再 rename，落盘后提示 git 状态
     ↓
构建时由 remark 插件把 == 和 h1 处理好，页面直接可看
```

### 5.2 诊断清单（工具最该说人话的地方）

拖进来的那一刻，界面直接告诉你会发生什么，不用你自己去数：

| 诊断项 | 输出示例 | 为什么要说 |
|---|---|---|
| 标题来源 | 「从 `title` 取到」/「从首个 h1 取到」 | 让你知道它认的是哪个 |
| 必填字段 | 「缺 `description`，构建会失败」 | 别名只兜 `date`/`explain`，不兜缺字段 |
| h1 数量 | 「3 个 h1 → 构建时整体降一级」 | 让你确认插件按预期工作 |
| 跳级标题 | 「有 `#` 直接跟 `####`，降级后是 `#####`，目录收不到」 | **构建层救不了的角落** |
| 高亮对数 | 「5 处 `==` 会转成高亮；代码块内 12 处已免疫」 | 让你确信没误伤运算符 |
| 字数/代码块 | 「4200 字，9 个代码块，预计阅读 11 分钟」 | 顺便给你个手感 |

### 5.3 界面

三栏，只在一个页面里完成：

| 左栏 | 中栏 | 右栏 |
|---|---|---|
| 原文（等宽只读） | 诊断清单，逐条打勾，可单条关掉 | 将写入的 frontmatter |
| 语法高亮 | 底部三项：文件名 / 分类 / 标签 | 文件名与撞名检查结果 |

不做渲染预览：你要核对的是「标记对不对」，源码对照最直接；视觉效果在站点上看真的。

## 六、体检（本次新增，也是旧工具没有的）

构建层的自动转换是好事，但它**默默处理**——你不会知道它处理了什么、哪里没兜住。
体检就是把「默默」变成「看得见」。

| 检查项 | 严重度 | 说明 |
|---|---|---|
| 缺必填字段 | 🔴 阻断构建 | `title` / `description` / `pubDate` / `categories` |
| 文件名含中文或大写 | 🟠 会变编码 URL | URL 走文件名（ADR-006） |
| 分类不存在于其他文章 | 🟡 可能是拼错 | 会造出一个只有 1 篇文章的孤儿分类页 |
| 标签与分类重名 | 🟡 冗余 | 标签页和分类页重复收录 |
| 标题跳级（`#` 接 `####`） | 🟡 降级后仍进不了目录 | 构建层管不了 |
| 正文 `==` 未配对 | 🟡 会原样露出等号 | 插件会原样吐回，不吞内容但难看 |
| 重定向表 key 指向现存文件 | 🔴 会顶掉真文章 | 踩过，BUG-014，且只 WARN 不报错 |

**一键全站跑**，输出一张表。这是工具唯一能防止站点「慢慢烂掉」的功能。

## 七、五条硬边界

| 边界 | 理由 |
|---|---|
| **绝不写 Obsidian vault** | 源文件只读。有 bug 时最坏是不产出，不会毁掉笔记 |
| **重名拒绝覆盖** | 撞名报错，不悄悄改成 `-1` |
| **先写临时文件再 rename** | 中途失败不留半截文章 |
| **删除前先备份到 `.workbuddy/tmp/deleted-posts/`** | 唯一不可逆的动作，必须留退路 |
| **改名必须显式确认，默认不跟随标题变** | 改名 = 换 URL = 死链（ADR-011）。工具只能问，不能自己决定 |

## 八、技术选型与复用

### 8.1 选型（全部沿用上次验证过的）

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node 内置模块，**零新依赖** | 踩过 npm 装依赖挂 23 分钟（BUG-002） |
| 界面 | 原生 HTML/CSS/JS | 不引框架，改样式刷新即可 |
| 端口 | `127.0.0.1:5678` | 只给自己用；用 127.0.0.1 而非 localhost（BUG-007 地址族） |
| 配色 | 直接抄 `UI.md` 的设计令牌 | 跟博客同一套米白+墨绿，不用重新配 |

> 说清楚一件反直觉的事：**代码量比上次删除时还多一点**。
> 因为上次那 5600 行里，「启停进程」这块（`blog-server.mjs` 556 行）被砍了、换成更简单的跳转，
> 而新增了「入库 + 体检」两块真正每天用的。**行数不是成本，没人用的功能才是成本。**

### 8.3 分类清单改成动态扫描的理由

旧 `config.mjs` 硬编码 8 个分类，是 2026-09 的起步主题。现在站点实际只有 `数据结构` 一个分类。
硬编码清单每加一个分类都要改代码，而且会和现实悄悄脱节。

改成**扫描 `posts/` 里所有文章的 `categories` 汇总去重**：分类页本来就是构建时从 frontmatter 算的
（`架构设计.md`），工具跟着这个思路走，永远和站点一致。新增分类时表单里手填一个即可。

## 九、分期与验收

| 批次 | 内容 | 验收标准 |
|---|---|---|
| **P1 骨架** | 恢复旧代码 → 跑通列表 + 编辑 + 保存 | 打开 5678 能看到现有文章；改个标签保存成功；dev 热更新生效 |
| **P2 入库** | 诊断 + 起名 + 归类 + 写入 | 把 `tmp-obsidian-test.md` 拖进去，诊断结果与实际相符；写入后文章正常渲染 |
| **P3 体检** | 规则 + 全站跑 | 7 条规则各有对应用例；故意造一份坏文件能被拦住 |
| **P4 危险操作** | 删除（备份）、改名（重定向） | 删除后备份可复原；改名后旧地址 200 跳转、`redirects.json` 正确追加 |
| **P5 收尾** | 使用说明、文档同步、提交 | 记录按项目规范补齐；`npm run build` exit=0 |

P1 和 P2 之间要**先提交一次**，避免再出现「做完一堆没提交」的状态。

## 十、风险与已知限制

| 风险 | 应对 |
|---|---|
| 又是「功能多、用不上」 | 分 5 批交付，每批都要能独立用；P4 的危险操作放最后 |
| 6200 行的维护负担 | 复用部分已过 109 项测试（54+46+19），新增部分只碰 `ingest.mjs` / `lint.mjs` 两个文件 |
| 工具与 `预览.bat` 职责重叠 | 工具只做「打开博客」跳转，进程启停仍归 bat，不重复实现 |
| frontmatter 手写解析的边界 | 沿用旧实现（扁平字段，不引 YAML 库），代价是嵌套结构不支持——目前 frontmatter 没有嵌套 |
| 构建时转换与工具显示不一致 | 工具的「诊断」只预测、不修改；真正结果以站点渲染为准 |
| `.md` 被工具外改动 | 每次操作前重新读磁盘，不缓存（旧版已有此设计） |
