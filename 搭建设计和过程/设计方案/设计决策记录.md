# 设计决策记录（ADR）

> 每个"定了的事"写一条。**重点记被否决的方案和否决理由** —— 半年后你会需要它。
>
> **门槛**：只有「难反转」或「反直觉」的决定才单开一条 ADR。像"frontmatter 要哪些字段"
> 这种改起来便宜的，记在 `架构设计.md` 的决策表里就够了，不必单开。

## 模板

```text
### ADR-XXX 标题

- 日期：
- 状态：已采纳 / 已废弃 / 待定
- 背景：为什么需要做这个决定
- 备选方案：
  - A：
  - B：
- 决定：选了哪个
- 理由：
- 代价 / 遗留问题：
```

### ADR-001 用「搭建设计和过程」文件夹管理项目文档

- 日期：2026-09-19
- 状态：**已部分废弃**（同日由 ADR-005 推翻其中「主记录各用一个文件」一项，其余仍有效）
- 背景：博客从零搭建，需要一套机制记录设计方案、每次改动、每个 bug 与反思，避免半年后想不起来当时为什么这么做
- 备选方案：
  - A：不专门记录，靠脑子记
  - B：每个改动 / 每个 bug 单独开一个文件
  - C：主记录各用一个文件（CHANGELOG / BUGLOG），跨 bug 的提炼另开一个文件
- 决定：C —— 其中「主记录各用一个文件」已于同日被 **ADR-005** 推翻（改为一天一个文件）；「跨 bug 的提炼独立成文件」（`经验教训.md`）仍然有效
- 理由：单文件便于回看和检索，也不会变成几百个小文件；改动/反思与对应条目是强绑定的，拆成多文件会导致两边都要维护，很快对不上；只有跨 bug 的通用规律才值得独立成文件
- 代价 / 遗留问题：主文件会随时间变长，靠「按日期分组 + 倒序」缓解（**此代价后被 ADR-005 证明为「只是缓解、不解决」，并据此推翻**）；「自动记录」实际依赖 AI 在对话中主动落笔，用户离线自行改文件时不会被记录

### ADR-002 启用 Git 记录文件改动，与 CHANGELOG 分工互补

- 日期：2026-09-19
- 状态：已采纳
- 背景：ADR-001 建立的 CHANGELOG 依赖人工 / AI 主动落笔，存在漏记风险；用户自行改文件时更是完全无法察觉。需要一层不依赖自觉的记录
- 备选方案：
  - A：只保留 CHANGELOG，不加版本控制
  - B：加 Git，Git 与 CHANGELOG 二选一（认为 CHANGELOG 多余）
  - C：加 Git，两者分工互补 —— Git 记「事实」（哪些文件、哪些行变了），CHANGELOG 记「意图」（为什么改），用提交号双向索引
- 决定：C
- 理由：Git 是文件系统级的自动留痕，不会漏、成本近零，且 `git status` 能在 CHANGELOG 漏记时兜底；但纯 diff 不讲人话，半年后自己都看不懂，所以「为什么」这部分仍然只能由 CHANGELOG 承担。两者用提交号互相索引后可双向查询
- 代价 / 遗留问题：每次改动多一步提交动作（由 AI 自动完成，用户无感）；仓库体积会持续增长，但本项目以纯文本为主，可忽略。另外把 `.workbuddy/`（工具内部数据）排除出仓库，以免日后仓库公开时泄露私人笔记

### ADR-003 用静态站点生成器，不用动态博客、不自己写

- 日期：2026-09-19
- 状态：已采纳
- 背景：`需求与目标.md` 已定稿（v1.0），需要确定实现方式。需求里有几条硬约束：不做后台管理、不自己运维、发文章 = 加一个文件
- 备选方案：
  - A：动态博客（WordPress 一类）—— 有现成后台，能装插件
  - B：自己写前端 + 后端
  - C：静态站点生成器（SSG）
  - D：直接用知乎 / 掘金 / CSDN 等平台
- 决定：C
- 理由：
  1. **决定性的巧合**：静态站做不了的典型功能，恰好是需求里已被明确砍掉的（评论、访问统计 —— 两者都需要服务端存数据）。**「被砍的」与「做不了的」完全重合，所以选静态方案零损失**
  2. 违背「不做后台」「不自己运维」的方案（A）直接出局
  3. B 会让项目变成「一直在做站、零篇文章」，与「成功标准第 5 条：半年后还愿意写」直接冲突
  4. D 内容不归自己、样式不能改，与「搭自己的博客」目标不符
  5. 附带白送：零服务器、零数据库、免费托管、无后台可被攻击、访问速度极快
- 代价 / 遗留问题：
  - 没有服务端 → 将来若想加评论 / 访问统计 / 服务端搜索，需接第三方服务或更换方案
  - 站内搜索只能用客户端方案（如 Pagefind 这类在浏览器里跑的全文搜索）
  - 内容更新必须经过「生成」这一步才能看到成品（用本地预览命令解决，成本很低）

### ADR-004 在候选生成器中选定 Astro（否决 Hugo 与 Hexo）

- 日期：2026-09-19
- 状态：已采纳
- 背景：ADR-003 确定用静态生成器后，需要在 Hugo / Hexo / Astro 中选一个。用户对 Hugo 与 Astro「都感觉挺好」，要求细讲区别
- 备选方案：
  - A：Hugo（Go 写的，单个 exe，零依赖，构建极快）
  - B：Hexo（Node 生态，中文教程最多）
  - C：Astro（Node 生态，模板即 HTML + JS）
- 决定：C —— **Astro**
- 理由：
  1. **决定性理由来自用户的自我定位**。当我问「你希望三年后这个博客是什么样」时，用户选了「**一个你亲手改造过的个人网站**」（而非「一个稳定更新的技术文章站」）。既然确定会长期动手改造它，那么**改造时学到的东西能否迁移**就成了首要标准：Astro 的模板是 HTML / JS，学到的在前端通用；Hugo 的 Go 模板只对 Hugo 自己有用
  2. Astro 的内容集合（Content Collections）带 schema 校验，**frontmatter 写错会直接报错并指出哪一行**；Hugo 在这种情况下常常**静默失败**（不报错，值就是不显示）。frontmatter 写错是新手最高频的错误，这个差别在学习阶段的实际影响大于构建速度
  3. Astro 内置 Shiki 代码高亮，技术内容的观感更好
  4. Hexo 退出：其唯一强项「中文教程最多、卡住能自救」被「AI 全程在场」抵消，而短板（依赖多、构建慢）仍在
- 代价 / 遗留问题（**诚实列出，不粉饰**）：
  - **放弃了 Hugo 最大的优势**：Hugo 是单个 exe、零依赖，「放半年回来照样能跑」，这一点其实直接对着「半年后还愿意写」那一条。选 Astro 等于用这份确定性换取了可迁移的技能与更强的改造能力
  - 依赖多一层不确定性：Node 版本升级、`node_modules` 被误删等情况可能需要重装依赖
  - 起步比 Hugo 多几步（装 Node 依赖）
  - 本机 Node 为 v24.15.0，属较新版本，与 Astro 的兼容性需实测验证（安装时验证，结果记录在 `技术选型.md`）
- 补充说明：**这不是一次定终身的选择**。文章都是 Markdown，换工具时文章能原样带走；但主题配置与 URL 结构需重做。所以切换成本是「配置重做」而非「内容重写」—— 这也是敢于先选一个用起来的原因

### ADR-006 文章 URL 不带分类

- 日期：2026-09-20
- 状态：已采纳
- 背景：`架构设计.md` 需要确定 URL 结构。这是需求文档中点名的**唯一「以后改起来贵」**的东西 —— 一旦公开，别人的收藏与分享链接就固定了，改 URL = 制造死链。而当前尚未上线、无人收藏过任何链接，正是把 URL 定死的窗口期
- 备选方案：
  - A：`/posts/<分类>/<文件名>` —— URL 里体现分类层级
  - B：`/posts/<文件名>` —— 扁平结构，分类不进 URL
  - C：`/<年>/<月>/<文件名>` —— 按时间分目录（很多 Hexo 博客的默认做法）
- 决定：B
- 理由：
  1. **与「分类体系还在试错期」直接配套**。需求文档已写明「起步主题清单不是定稿、前期鼓励频繁调整，攒到二十来篇再固化」。URL 带分类意味着**每调整一次分类就产生一批死链**；不带分类则分类可以随便改，链接纹丝不动
  2. 分类是**列表页的职责**，不是文章 URL 的职责。单看 URL 不知道主题归属，这个信息在导航栏和列表页里有
  3. C 被否决：日期目录几乎不提供导航价值（读者不按日期找文章），却让 URL 变长，且与「文章可能有重要更新」矛盾
- 代价 / 遗留问题：
  - 读者从 URL 看不出文章主题
  - 若将来强烈想要带分类的 URL，需做**重定向**而非直接改（但正因为现在没上线，这个代价目前是 0）
  - 好处是「以后加分类页」不会冲突：可以**新增** `/categories/<主题>` 这类列表页，不必改动文章 URL

### ADR-007 暂不装第三方主题，先自建最小可用版本

- 日期：2026-09-20
- 状态：已采纳
- 背景：用户看到有人用 Butterfly 主题，提出讨论。经调研发现 **Butterfly（jerryc127 出品）是 Hexo 的招牌主题，没有官方 Astro 版**；受它启发的 Astro 主题有两个：Astrofly（活跃维护，基于 Astro v6）与 HsuBlog（最后提交 2023-08，停更三年）
- 备选方案：
  - A：装 **Astrofly**（受 hexo-butterfly 启发的 Astro 主题，2026-09-15 仍有提交）
  - B：装 **HsuBlog**（另一个 butterfly 风 Astro 主题）
  - C：**放弃 Astro，改用 Hexo + 官方 Butterfly**
  - D：**不装主题**，用当前 `minimal` 空底板自建最小可用版本
- 决定：D
- 理由：
  1. **主题不是插件，是整个项目**。它自带自己的 `src/pages`、`src/content/config.ts`、`astro.config`、`tailwind.config`。装主题 = 换掉全部骨架，并被迫按它的 frontmatter 字段改已定的规范（`架构设计.md` 第五节）
  2. **版本不匹配的风险**：Astrofly 基于 Astro **v6**，本项目是 **v7.3.3**，兼容性**未经验证**。在还没有一篇真实文章的情况下承担这个不确定性不划算
  3. **内容优先于外观**。主题是纯外观层，**改它不碰 URL、不影响已发文章**，是随时能改的东西。而反过来，「有没有内容」才是这个博客成败的关键（成功标准第 5 条：半年后还愿意写）。**先写内容，主题排后**
  4. B 直接排除：**停更三年**的主题 = 一次性用品，Astro 三年间迭代多次，装上去大概率跑不起来且无人维护
  5. C 直接排除：需要推翻 ADR-004（选 Astro），而选 Astro 的决定性理由（改造技能可迁移）依然成立，不因主题问题动摇
- 代价 / 遗留问题：
  - 初期站点外观朴素，需要自己写样式
  - 放弃了 Astrofly 已经做好的功能（Pagefind 搜索、PWA、深色模式）—— 这些要自己做，但需求里它们本就属「想要有」而非「必须有」
  - **回头条件**：攒够 3-5 篇真实文章后再评估。到那时才知道文章多长、公式表格多不多、哪里难看 —— **主题是为内容服务的，没有内容时挑主题就是纸上看房**
  - 需要提醒用户一个事实：**Butterfly 是 Hexo 主题，不存在官方的 Astro 版**。若日后仍想要 Butterfly 的观感，选项是 Astrofly 或手写仿制，而不是「装个 Butterfly」

### ADR-009 索引下放到各文件夹，上级 README 只做总览

- 日期：2026-09-20
- 状态：已采纳
- 背景：用户提出「给文件改动记录写一个目录，里面连接每天的改动」，并追问能否像 Obsidian 那样**自动**生成索引。此时日期列表是放在上级 `搭建设计和过程/README.md` 的「索引」一节里
- 备选方案：
  - A：维持现状（日期表只在上级 README）
  - B：**在每个记录文件夹内放自己的 `README.md` 作索引**，上级 README 的日期表删掉，改为链接
  - C：文件夹内索引的同时，上级 README 也保留一份日期表
  - D：写脚本/工具自动生成索引
- 决定：B
- 理由：
  1. **职责分层**：上级 README 该回答「有哪些文件夹」，文件夹内索引该回答「有哪些天」。原方案让两个问题挤在一个文件里，且日期表随天数增长会淹没总览
  2. **进文件夹就能看到索引**：原方案下打开 `文件改动记录/` 只看到一堆日期文件，得退到上级才找得到目录
  3. **避免双处维护**：C 方案要维护两份日期表，迟早对不上 —— 这正是原方案的真实痛点
  4. **`README.md` 是通用惯例**：GitHub 点进任何文件夹会自动显示该文件夹的 `README.md`。用它做索引**不是我们发明的规矩**，学习成本为零，且将来上线/公开后别人也能直接看懂
- 代价 / 遗留问题：
  - **新建日期文件后要补索引**：`文件改动记录/` 补 1 处，`bug修复记录/` 补 2 处（索引 + bug 一览表）。已在各文件夹 `模板.md` 顶部注明，并在文件夹 `README.md` 的「维护提醒」一节重复
  - 上级 README 少一层信息：在根目录时需再点一次才能看到日期。这是 B 换来的收益的对价，可接受

> **关于 D（自动生成索引）为何被否决** —— 用户明确问起这个（参考 Obsidian 的 Dataview），
> 结论值得单独记住：
>
> **Dataview 是 Obsidian 插件，不是 Markdown 功能。** 它的原理是"打开笔记时扫描整个 vault、实时计算、
> 渲染结果"。本项目**不在 Obsidian vault 内**，也没有任何程序会去运行它 → 语法在这个项目里**完全无效**。
> 换言之，它不是"能不能配"的问题，而是**前提不存在**。
>
> 至于"在 Astro 构建时自动扫描文件夹生成索引"——技术上完全可行（Astro 本就擅长读文件生成页面），
> 但**用错了地方**：这套记录是给作者自己在编辑器里看的，不参与网站运行；
> 而 Astro 的自动化只在"构建博客"时触发，与这个需求不在同一个执行环境里。
> 为一个连构建都不参与的手写索引搭一套生成机制，**投入产出不成比例**。
>
> 另外手写有个自动化给不了的好处：**可以写「备注」列**（如"这天主要在改文档体系"），
> 自动生成的只有干巴巴的链接。
>
> **触发重新考虑的条件**：记录多到「每次补索引都觉得烦」时，再上脚本生成。这是优化，不是必需品。

### ADR-008 写作流程：Obsidian 写好 → 整篇复制到站点

- 日期：2026-09-20
- 状态：已采纳
- 背景：用户已有成熟的 Obsidian 工作流（模板、双链、PicGo 图床插件）。需要决定文章如何进入站点。备选中最省事的是让 Astro 直接读 Obsidian 文件夹，实现"零复制"
- 备选方案：
  - A：**让 Astro 直接读 Obsidian 文件夹**（改配置指向 `Obsidian Vault\学习\学校笔记\` 或某个白名单文件夹）
  - B：在站点目录里直接用 Obsidian 打开 `site/src/content/`
  - C：**在 Obsidian 写好，整篇复制到 `site/src/content/`**
- 决定：C
- 理由：
  1. **A 的核心风险是"误发私人内容"**。用户的 vault 里有日记、饮食记录、考研决策记录、私人备忘 —— 让博客直读 vault 等于**把「哪些能公开」的判断权交给目录结构**，而不是交给用户的明确动作
  2. **A 的白名单变体仍不够好**：即便只指向一个专用文件夹，也要求用户写作时始终记得"这篇是公开的"。这份持续的心智负担与「半年后还愿意写」（成功标准第 5 条）冲突
  3. **C 的边界最简单**：「我复制过去的 = 公开的」。一步复制换来确定性，值得
  4. B 被否决：无法复用用户已有的 vault 工作流（模板、图床插件、双链、笔记间链接）；且会让私人笔记与公开文章混在同一结构里
- 代价 / 遗留问题：
  - **发文章多一步手动复制**（这是自觉接受的成本）
  - 站点与 vault 之间存在**内容副本**，两边可能不一致 → 约定**站点内的版本是权威版本**，改文章在站点内改，不再回改 vault（避免双向同步带来的混乱）
  - 图片问题已被用户的既有配置解决：Obsidian 插件 `obsidian-image-auto-upload-plugin` 在粘贴时**自动上传 PicGo 并替换为网络链接**（2026-09-20 读取插件 `data.json` 确认：`uploadByClipSwitch` / `applyImage` 均为 true），因此复制过去链接天然可用
  - 新增外部依赖：图片存 GitHub 图床，若图床失效则图片全裂。这是用「仓库体积小」换来的取舍

### ADR-010 记录改为卡片形式，不再用表格

- 日期：2026-09-20
- 状态：已采纳
- 背景：`文件改动记录` 原用 6 列表格（时间 / 类型 / 涉及文件 / 改了什么 / 为什么 / 提交）。用户使用后反馈「**不要用表格的形式，这不方便我看**」
- 备选方案：
  - A：**卡片式** —— 每条一个小标题 + 分行字段（**改了什么** / **为什么** / **提交**）
  - B：清单式 —— 每条一个自然段落，不固定字段
  - C：列表式 —— 一条一行，最短
  - D：维持表格
- 决定：A
- 理由：
  1. **表格的横向宽度是真实痛点**：6 列在编辑器里要左右拖动才能看完一行，阅读时需要频繁横向移动视线，累
  2. **卡片纵向展开**，每条各占一小块，从上往下读即可，不用横拖
  3. **A 保留了结构**（三个固定字段），比 B 的纯段落更容易"扫一眼就知道哪部分是为什么"；比 C 的一行挤一句更耐读
  4. D 被否决即用户的直接反馈
- 代价 / 遗留问题：
  - **文件变长**：同样内容，卡片比表格占更多行。但这是「可读性换紧凑度」的自觉取舍 —— 记录本来就少，不是问题
  - **跨条对比变难**：表格适合横向比较（比如"哪几次是重构"），卡片不适合。鉴于本项目不做统计式回顾，可接受
- 附带处理（**不留新旧混排**）：
  - 已存在的 `2026-09-19.md`、`2026-09-20.md` **整体转为卡片**，避免新旧格式混在仓库里更难读
  - 两个文件夹的 `README.md` 索引同步由表格改为列表
  - `模板.md` 重写为卡片格式
  - ⚠️ **`bug修复记录` 的卡片本来就是分行形式**（不是表格），用户对它的可读性没有异议 ——
    说明"分行优于表格"这个判断在 `bug修复记录` 上早已被实践验证过

> **为什么给一次纯格式调整单开 ADR**：它违反直觉 —— 格式改起来不是"很便宜"吗？
> 但这里有个反直觉之处值得记：**记录格式决定"半年后你还愿不愿意记"**（成功标准第 5 条）。
> 用户主动提出"不方便看"，说明格式已经在阻碍记录行为本身。
> 这类"影响长期习惯"的决定，即使技术成本低，也值得留痕说明为什么改。

### ADR-011 改名与 URL 的关系：改名是显式操作，重定向留到上线时

- 日期：2026-09-20
- 状态：已采纳
- 背景：设计博客管理工具时，用户提出「**改标题不会自动改文件名，那能不能实现 URL 的自动定位**」。这个问题触及 ADR-006（URL 不带分类）的同一条底线 —— **URL 是唯一"以后改起来贵"的东西**。需要为「改标题时 URL 怎么办」定一条长期规则
- 备选方案：
  - A：**改标题时自动重命名文件**（URL 自动跟着标题走）
  - B：**改标题绝不动文件名**，也不提供改名功能
  - C：**改标题时显式询问，默认不改**；改名后**本期不做**重定向，留到上线时再加
  - D：C + 现在就把重定向机制做出来
- 决定：**C**
- 理由：
  1. **A 被否决的核心是"无感知"**：改标题是高频动作。若它自动换 URL，则**上线后某次不经意的改标题就会制造死链** —— 别人的收藏、外站引用静默失效，而用户不会察觉。**风险不在于"改 URL"，在于"改 URL 这件事没经过决策"**
  2. **B 被否决**：确实存在正当需求 —— 文章写歪了、方向变了，URL 里的旧词已完全不搭。此时用户**主动**改名是对的。工具不该替用户否决，只该保证"不会悄悄发生"
  3. **C 的关键设计是默认值**：弹窗存在（你知道有条路），但**默认按钮是"不改"**（你不会被推着走）。这与 5.5.2 的设计一致：**把选择权交给用户，但不让变化偷偷发生**
  4. **D 被否决 —— 依据是需求文档里的一个硬数字**：`需求与目标.md` 写明「**第 3 类读者当前数量为 0**（博客还没上线）」。**没人访问过 = 没人收藏过任何链接 = 现在改 URL 的死链代价是 0**。此时做重定向，等于「为一批不存在的访问者建立档案」。这正是需求里点名的「**免费改错权**」窗口期，不该浪费在防御一个还不存在的风险上
- 代价 / 遗留问题：
  - **上线后欠一笔债**：需要在工具里补上"改名时自动生成跳转页"的逻辑。**触发条件明确** —— 博客一上线就该做（届时会把此条转为待办）
  - **重定向方案已预先选定 A（生成跳转页）并存入 `博客管理工具/技术架构.md` 5.5.2**，避免上线时从头再想。选 A 而非托管商 `_redirects` 配置的理由：**本项目托管商尚未决定，选不绑托管商的方案才不会让"换托管"变成"重做重定向"** —— 与 ADR-004 选 Astro 的理由同源
  - **A 方案自带一项永久成本**：每改一次标题就多留一个跳转页，且只要可能有人访问过老链接就不能删。**所以上线后仍应尽量少改名**，改名是例外而非常态
  - 本条规则**主体不在工具，而属于整个博客项目的 URL 纪律** —— 所以写在 `设计决策记录.md`（全项目级）而非只写进工具文档

> **为什么这条够格单开 ADR**：按 ADR 门槛（「难反转」或「反直觉」），它两条都占 ——
> ① URL 一旦公开就难反转（ADR-006 已确认这是全项目唯一"改起来贵"的东西）；
> ② 直觉上"标题变了 URL 该跟着变"，而正确答案恰恰相反。
> 用户这次主动追问「能不能自动定位」，说明这个直觉冲突是真实的、不是假想的 —— 半年后大概率会再问一次，故留痕。

### ADR-012 提交信息改英文短句，并取消「提交号回填」

- 日期：2026-09-20
- 状态：已采纳
- 背景：仓库已同步到 GitHub 私有仓库。用户发现提交信息**写得过细**，提出两点：
  ①「有的东西需要保护隐私」；②「只需要用 GitHub 标准的 commit 写法来就行了」。
  此前本项目用的是**中文提交信息 + 提交号回填**机制（改动记录卡片末尾写 git 短 hash）。
- 备选方案：
  - A：保持现状（中文详细描述 + 回填提交号）
  - B：**改用英文 Conventional Commits（`type: description`），并取消提交号回填**
  - C：改成英文但保留回填机制
- 决定：**B**
- 理由：
  1. **隐私是直接动因**：仓库已推到 GitHub。中文提交信息容易夹带内部细节
     （如「回填提交号 xxxxxxx」这类流水账、具体文件路径与措辞中的私人线索）。
     英文短句只描述动作，天然不泄露过程
  2. **回填机制本身的成本一直高于收益**：它要求**每个改动跟一个记账提交**，
     而记账提交又产生新提交号，又要回填 —— 文档里原话就是「否则会无限套娃」。
     40 个提交里有**一半以上**是这种纯记账提交，等于把提交历史灌成了流水账
  3. **回填的收益还会被重写历史一笔勾销**：本次整理历史后所有提交号都变了，
     卡片里写的号全部失效 —— 硬链到会变的东西上，本身就是脆弱设计
  4. **业界惯例**：Conventional Commits 是 GitHub 社区标准，以后接 CI、
     自动生成 changelog、换协作工具都能直接用
- 代价 / 遗留问题：
  - **历史已重写**：40 个提交信息全部改为英文，提交号全部改变（本地与远程都是）。
    旧号只存在于 `backup-before-rewrite` 备份分支中
  - **改动记录里的提交号已统一移除**，改为固定文案「本次改动已提交」。
    想反查用 `git log --oneline` 或 `git log -S "关键词"`
  - **提交信息不再承载「为什么」**：这个职责完全落到文件改动记录。
    两边分工更清楚 —— 提交信息回答「做了什么」，改动记录回答「为什么做」
  - 用户是中文使用者，**英文提交信息由 AI 全权代写**，用户不需要自己写（符合
    「用户不敲命令」的既有约定）

> **为什么这条够格单开 ADR**：按门槛，「难反转」成立 —— 它**改变了提交历史的形态**
> （重写了全部 40 个提交），且**取消了已写入文档体系的一条机制**（回填），
> 涉及 `模板.md`、两份 README、版本控制约定等多处。改回来要再重写一次历史，成本很高。
