# 设计决策记录（ADR）

> 每个"定了的事"写一条。**重点记被否决的方案和否决理由** —— 半年后你会需要它。

## 模板

```text
### ADR-XXX 标题

- 日期：
- 状态：已采纳 / 已废弃 / 待定
- 背景：为什么需要做这个决定
- 备选方案：
  - A：
  - B：
- 决定：选了哪个
- 理由：
- 代价 / 遗留问题：
```

### ADR-001 用「搭建设计和过程」文件夹管理项目文档

- 日期：2026-09-19
- 状态：已采纳
- 背景：博客从零搭建，需要一套机制记录设计方案、每次改动、每个 bug 与反思，避免半年后想不起来当时为什么这么做
- 备选方案：
  - A：不专门记录，靠脑子记
  - B：每个改动 / 每个 bug 单独开一个文件
  - C：主记录各用一个文件（CHANGELOG / BUGLOG），跨 bug 的提炼另开一个文件
- 决定：C
- 理由：单文件便于回看和检索，也不会变成几百个小文件；改动/反思与对应条目是强绑定的，拆成多文件会导致两边都要维护，很快对不上；只有跨 bug 的通用规律才值得独立成文件
- 代价 / 遗留问题：主文件会随时间变长，靠「按日期分组 + 倒序」缓解；「自动记录」实际依赖 AI 在对话中主动落笔，用户离线自行改文件时不会被记录

### ADR-002 启用 Git 记录文件改动，与 CHANGELOG 分工互补

- 日期：2026-09-19
- 状态：已采纳
- 背景：ADR-001 建立的 CHANGELOG 依赖人工 / AI 主动落笔，存在漏记风险；用户自行改文件时更是完全无法察觉。需要一层不依赖自觉的记录
- 备选方案：
  - A：只保留 CHANGELOG，不加版本控制
  - B：加 Git，Git 与 CHANGELOG 二选一（认为 CHANGELOG 多余）
  - C：加 Git，两者分工互补 —— Git 记「事实」（哪些文件、哪些行变了），CHANGELOG 记「意图」（为什么改），用提交号双向索引
- 决定：C
- 理由：Git 是文件系统级的自动留痕，不会漏、成本近零，且 `git status` 能在 CHANGELOG 漏记时兜底；但纯 diff 不讲人话，半年后自己都看不懂，所以「为什么」这部分仍然只能由 CHANGELOG 承担。两者用提交号互相索引后可双向查询
- 代价 / 遗留问题：每次改动多一步提交动作（由 AI 自动完成，用户无感）；仓库体积会持续增长，但本项目以纯文本为主，可忽略。另外把 `.workbuddy/`（工具内部数据）排除出仓库，以免日后仓库公开时泄露私人笔记

### ADR-003 用静态站点生成器，不用动态博客、不自己写

- 日期：2026-09-19
- 状态：已采纳
- 背景：`需求与目标.md` 已定稿（v1.0），需要确定实现方式。需求里有几条硬约束：不做后台管理、不自己运维、发文章 = 加一个文件
- 备选方案：
  - A：动态博客（WordPress 一类）—— 有现成后台，能装插件
  - B：自己写前端 + 后端
  - C：静态站点生成器（SSG）
  - D：直接用知乎 / 掘金 / CSDN 等平台
- 决定：C
- 理由：
  1. **决定性的巧合**：静态站做不了的典型功能，恰好是需求里已被明确砍掉的（评论、访问统计 —— 两者都需要服务端存数据）。**「被砍的」与「做不了的」完全重合，所以选静态方案零损失**
  2. 违背「不做后台」「不自己运维」的方案（A）直接出局
  3. B 会让项目变成「一直在做站、零篇文章」，与「成功标准第 5 条：半年后还愿意写」直接冲突
  4. D 内容不归自己、样式不能改，与「搭自己的博客」目标不符
  5. 附带白送：零服务器、零数据库、免费托管、无后台可被攻击、访问速度极快
- 代价 / 遗留问题：
  - 没有服务端 → 将来若想加评论 / 访问统计 / 服务端搜索，需接第三方服务或更换方案
  - 站内搜索只能用客户端方案（如 Pagefind 这类在浏览器里跑的全文搜索）
  - 内容更新必须经过「生成」这一步才能看到成品（用本地预览命令解决，成本很低）

### ADR-004 在候选生成器中选定 Astro（否决 Hugo 与 Hexo）

- 日期：2026-09-19
- 状态：已采纳
- 背景：ADR-003 确定用静态生成器后，需要在 Hugo / Hexo / Astro 中选一个。用户对 Hugo 与 Astro「都感觉挺好」，要求细讲区别
- 备选方案：
  - A：Hugo（Go 写的，单个 exe，零依赖，构建极快）
  - B：Hexo（Node 生态，中文教程最多）
  - C：Astro（Node 生态，模板即 HTML + JS）
- 决定：C —— **Astro**
- 理由：
  1. **决定性理由来自用户的自我定位**。当我问「你希望三年后这个博客是什么样」时，用户选了「**一个你亲手改造过的个人网站**」（而非「一个稳定更新的技术文章站」）。既然确定会长期动手改造它，那么**改造时学到的东西能否迁移**就成了首要标准：Astro 的模板是 HTML / JS，学到的在前端通用；Hugo 的 Go 模板只对 Hugo 自己有用
  2. Astro 的内容集合（Content Collections）带 schema 校验，**frontmatter 写错会直接报错并指出哪一行**；Hugo 在这种情况下常常**静默失败**（不报错，值就是不显示）。frontmatter 写错是新手最高频的错误，这个差别在学习阶段的实际影响大于构建速度
  3. Astro 内置 Shiki 代码高亮，技术内容的观感更好
  4. Hexo 退出：其唯一强项「中文教程最多、卡住能自救」被「AI 全程在场」抵消，而短板（依赖多、构建慢）仍在
- 代价 / 遗留问题（**诚实列出，不粉饰**）：
  - **放弃了 Hugo 最大的优势**：Hugo 是单个 exe、零依赖，「放半年回来照样能跑」，这一点其实直接对着「半年后还愿意写」那一条。选 Astro 等于用这份确定性换取了可迁移的技能与更强的改造能力
  - 依赖多一层不确定性：Node 版本升级、`node_modules` 被误删等情况可能需要重装依赖
  - 起步比 Hugo 多几步（装 Node 依赖）
  - 本机 Node 为 v24.15.0，属较新版本，与 Astro 的兼容性需实测验证（安装时验证，结果记录在 `技术选型.md`）
- 补充说明：**这不是一次定终身的选择**。文章都是 Markdown，换工具时文章能原样带走；但主题配置与 URL 结构需重做。所以切换成本是「配置重做」而非「内容重写」—— 这也是敢于先选一个用起来的原因
