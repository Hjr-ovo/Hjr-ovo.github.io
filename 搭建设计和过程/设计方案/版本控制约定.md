## 一、Git 为什么和「文件改动记录」不冲突

很多人第一次会以为这两个是重复的。**不是替代关系，是互补关系** —— 它们记的是两件不同的事：

| | Git | 文件改动记录 |
|---|---|---|
| 记什么 | **事实**：改了哪些文件、每一行怎么变的 | **意图**：为什么改、当时怎么想 |
| 谁来写 | 工具自动生成，不用手写 | 需要人 / AI 用文字总结 |
| 精度 | **行级，不会漏** | 靠自觉，**可能漏** |
| 可读性 | 要会看 diff，比较枯燥 | 大白话，一眼看懂 |
| 能否篡改 | 改历史会留痕 | 改了没人知道 |

**关键：Git 是兜底。** 改动记录漏记了，`git status` / `git diff` 立刻能看出哪些文件变了，
能补回来。这解决了「自动记录其实不完全自动」这个硬伤 —— 记录这件事不再依赖谁的记性。

## 四、哪些东西不进仓库

| 忽略项 | 为什么 |
|---|---|
| `.workbuddy/` | AI 的记忆数据，不是博客内容。避免仓库日后公开时把私人笔记一起发出去 |
| `node_modules/`、`dist/`、`.cache/` | 依赖与构建产物，体积大且能重新生成 |
| `.env`、`*.key`、`*.pem` | 密钥密码，**绝对不能提交** |
| `Thumbs.db`、`.DS_Store`、`*.log` | 系统垃圾与日志 |
| `/_*.txt`、`/_*.log` | 仓库根目录下划线开头的临时文件（用**通配符**而非点名，见 L-001） |

完整规则见根目录 `.gitignore`，每条都有中文注释。

> ⚠️ **例外，必须记住**：**`site/public/` 是源码不是产物**，要进仓库。
> 它放的是 favicon 等"原样拷到网站根目录"的资源。这跟很多生成器的习惯相反，
> 已在 `.gitignore` 里重点标注。

## 五、提交信息规范（2026-09-20 定稿：英文类型 + 中文描述）

格式：**`type: 中文描述`** —— 类型用 Conventional Commits 的标准英文词，描述用中文。

| type | 什么时候用 |
|---|---|
| `feat` | 加了新文件 / 新功能 |
| `fix` | 修了 bug |
| `docs` | 只改文档，不动代码 |
| `refactor` | 结构大改，功能不变 |
| `style` | 只改外观、配色、排版（不影响逻辑） |
| `chore` | 杂务：配置、依赖、构建脚本等 |

示例：

```
feat: 站点最小可用页面跑通
fix: 修复弹窗被 CSS 的 display 顶穿
docs: 架构设计定稿并补写 ADR-006 至 ADR-008
refactor: 改动记录改为卡片形式
chore: 忽略博客管理工具的运行时日志
```

需要解释「为什么」时，空一行再写正文（**空一行**很重要，`type:` 那一行会被当成标题）：

```
fix: 修复弹窗被 CSS 的 display 顶穿

hidden 属性只是浏览器默认样式，优先级很低，
被作者样式里的 display:flex 盖过就失效了。
```

### 为什么这么定（ADR-012）

1. **类型用英文**：`feat` / `fix` 这类是工具链能识别的标准词，以后接 CI、
   自动生成 changelog 都能直接用。换成中文（如「新增」）这些工具就不认了
2. **描述用中文**：这是给自己看的私有仓库，中文读起来最快，
   也方便在 `git log` 里扫一眼就知道每次干了什么
3. **只写一句话**：**提交信息只回答「做了什么」，「为什么」写在文件改动记录里**。
   两边职责分开，就不用为了写清楚而把细节堆进 commit

> ⚠️ **提交信息里不写**：提交号本身（`回填提交号 xxx` 这类流水账）、私人信息、详细的过程描述。
> 一句话说清做了什么即可。

> 📌 **一段插曲（2026-09-20）**：曾一度把提交信息全改成英文（当时考虑仓库要同步到 GitHub、
> 担心中文夹带隐私）。实际用下来中文更顺手，且仓库是**私有**的，隐私顾虑很小，
> 所以当天又改回中文。ADR-012 的**核心决定（取消提交号回填）不变**，
> 只有「描述用什么语言」这一条调整为中文。

## 六、日常怎么用

**你不需要敲任何命令。**

每次改动完成后 AI 自动提交，按上面的规范写提交信息，同时往**当天**的
`文件改动记录/YYYY-MM-DD.md` 追加一张卡片。

**唯一的例外**：如果你**自己手动改了文件**，跟我说一声改了啥就行。
我会先 `git status` 对比出真实差异，再补记和提交 —— **不靠你描述，靠 git 看事实**。

## 七、和文件改动记录的分工（2026-09-20 调整）

| | Git 提交信息 | 文件改动记录 |
|---|---|---|
| 记什么 | **做了什么**（一句话） | **为什么做**、当时的判断依据 |
| 详细程度 | 一句话 | 可以很长，写透 |
| 谁看 | 想在历史里扫一眼 | 半年后想回忆当时的想法 |

**两者不再用提交号互链**（ADR-012 取消）。原因：

- 回填提交号需要**每个改动跟一个记账提交**，而记账提交本身又产生新提交号，
  永远追不上 —— 上一版文档里专门写的「否则会无限套娃」就是这个
- 重写历史（如本次整理）会让所有提交号失效，硬链进去反而变成错误信息

**想找某次改动对应哪个提交**：

```bash
git log --oneline          # 按时间扫一眼
git log -S "关键词"         # 按内容搜：哪次提交增删了这个字符串
git log --since="2026-09-20"   # 按日期范围
```

## 八、想自己看一眼历史（可选）

```bash
git log --oneline          # 一行一条，看全部提交
git status                 # 看当前有哪些改动还没提交
git diff                   # 看具体改了哪些行（还没提交的）
git show <提交号>           # 看某次提交的完整改动
```

> 本机 Bash 环境有问题，建议用 PowerShell 执行。

## 九、备份策略

### 远程仓库：已接 GitHub（2026-09-20 变更）

2026-09-19 曾决定「暂不接远程」，2026-09-20 用户接了 GitHub 私有仓库，**该决定已作废**。

```text
origin  https://github.com/Hjr-ovo/myblogweb.git
可见性  私有
```

> ⚠️ **一个容易踩的坑：改了历史之后必须强推。**
> 本地重写历史（如批量改提交信息）后，远程那份还是旧的，普通 `git push` 会被拒绝。
> 正确做法是用 `git push --force-with-lease` —— 它比 `--force` 安全，
> 如果远程有别人推的新提交会拒绝执行，避免覆盖掉别人的工作。
>
> **只有一个人的私有仓库**，强推是安全的。

### 仍然建议保留的本地备份

远程同步不是万能的（账号丢了、仓库误删、网络不通时都用不了），
**再复制一份到另一块盘**仍是便宜的保险：

- 定期把整个 `D:\file\myblogweb`（**不含 `node_modules/` 和 `dist/`**，这两个能重新生成）
  复制到移动硬盘或另一块盘
- 纯文本文档很小，几百 MB 都不到，复制很快

> ⚠️ **别只存在同一块盘的不同文件夹里 —— 那不叫备份。** 硬盘坏掉时它们一起没。
