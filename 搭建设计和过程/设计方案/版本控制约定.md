## 一、Git 为什么和「文件改动记录」不冲突

很多人第一次会以为这两个是重复的。**不是替代关系，是互补关系** —— 它们记的是两件不同的事：

| | Git | 文件改动记录 |
|---|---|---|
| 记什么 | **事实**：改了哪些文件、每一行怎么变的 | **意图**：为什么改、当时怎么想 |
| 谁来写 | 工具自动生成，不用手写 | 需要人 / AI 用文字总结 |
| 精度 | **行级，不会漏** | 靠自觉，**可能漏** |
| 可读性 | 要会看 diff，比较枯燥 | 大白话，一眼看懂 |
| 能否篡改 | 改历史会留痕 | 改了没人知道 |

**关键：Git 是兜底。** 改动记录漏记了，`git status` / `git diff` 立刻能看出哪些文件变了，
能补回来。这解决了「自动记录其实不完全自动」这个硬伤 —— 记录这件事不再依赖谁的记性。

## 三、已做的配置

| 配置项 | 值 | 作用 |
|---|---|---|
| `core.quotepath` | `false` | 中文文件名正常显示，不显示成 `\346\226\207` 这种转义码 |
| `core.autocrlf` | `true` | Windows 换行符自动转换（本地 CRLF ↔ 仓库 LF），避免凭空多出"整文件都改了"的差异 |

> 全局身份（user.name / user.email）在系统级已配置，本仓库不需要重复设置。

## 四、哪些东西不进仓库

| 忽略项 | 为什么 |
|---|---|
| `.workbuddy/` | AI 的记忆数据，不是博客内容。避免仓库日后公开时把私人笔记一起发出去 |
| `node_modules/`、`dist/`、`.cache/` | 依赖与构建产物，体积大且能重新生成 |
| `.env`、`*.key`、`*.pem` | 密钥密码，**绝对不能提交** |
| `Thumbs.db`、`.DS_Store`、`*.log` | 系统垃圾与日志 |
| `/_*.txt`、`/_*.log` | 仓库根目录下划线开头的临时文件（用**通配符**而非点名，见 L-001） |

完整规则见根目录 `.gitignore`，每条都有中文注释。

> ⚠️ **例外，必须记住**：**`site/public/` 是源码不是产物**，要进仓库。
> 它放的是 favicon 等"原样拷到网站根目录"的资源。这跟很多生成器的习惯相反，
> 已在 `.gitignore` 里重点标注。

## 五、提交信息规范

格式：**`类型: 一句话描述`**

类型固定 5 个词，**与文件改动记录完全一致**：

| 类型 | 什么时候用 |
|---|---|
| 新增 | 加了新文件 / 新功能 |
| 修改 | 改了已有内容 |
| 删除 | 删掉文件或功能 |
| 重构 | 结构大改，功能不变 |
| 样式 | 只改外观、配色、排版 |

示例：

```
新增: 首页骨架
修改: 导航栏配色改浅
样式: 文章卡片圆角调到 8px
```

需要解释「为什么」时，空一行再写正文：

```
修改: 导航栏配色改浅

原色在深色屏上对比度不够，看起来发灰。
```

> **为什么要求写「为什么」**：diff 能告诉你改了哪一行，但永远不告诉你为什么。
> 半年后你自己看到一行改动，只有正文里的这句话能救你。

## 六、日常怎么用

**你不需要敲任何命令。**

每次改动完成后 AI 自动提交，按上面的规范写提交信息，同时往**当天**的
`文件改动记录/YYYY-MM-DD.md` 追加一张卡片并回填本次提交号。

**唯一的例外**：如果你**自己手动改了文件**，跟我说一声改了啥就行。
我会先 `git status` 对比出真实差异，再补记和提交 —— **不靠你描述，靠 git 看事实**。

## 七、和文件改动记录的联动

`文件改动记录/YYYY-MM-DD.md` 里每张卡片末尾是本次改动对应的提交号（短 hash，如 `b2cbb6e`）。

| 想知道 | 怎么做 |
|---|---|
| 某次改动具体动了哪些行 | `git show b2cbb6e` |
| 某行代码当时为什么改 | 在 `文件改动记录/` 里搜这个号 |

**两个方向都能走通**，这是这套结构最实用的地方。

### 提交号怎么填（重要）

提交号得**提交完才知道**，所以填不进正在提交的那个文件里。规则是：

1. 写新卡片时，**顺手回填上一张卡片的提交号**
2. 最新那张暂时标 `——`
3. 每次收工前补全

**回填以卡片所在的那个日期文件为准**，跨天也不影响。

**纯记账性提交不单独占一张卡片**（比如回填提交号、改错别字），否则会无限套娃 ——
回填动作本身又产生一个新提交号，又要回填，永远追不上。

## 八、想自己看一眼历史（可选）

```bash
git log --oneline          # 一行一条，看全部提交
git status                 # 看当前有哪些改动还没提交
git diff                   # 看具体改了哪些行（还没提交的）
git show b2cbb6e           # 看某次提交的完整改动
```

> 本机 Bash 环境有问题，建议在 Git Bash 或用 PowerShell 执行。

## 九、备份策略

### 远程仓库：暂不接（2026-09-19 决定，2026-09-20 复核仍有效）

现阶段只在本地建仓库，不接 GitHub / Gitee。

> **代价必须讲清楚**：本地 git 只防「改错了想回退」，**防不了硬盘坏掉**。
> 目前整个仓库只有**一份物理副本**，这块盘挂了就全没了 —— 远程上不会有一份。

**退而求其次的做法（成本最低）**：定期把整个 `D:\file\myblogweb` 文件夹
复制到**另一块盘**或移动硬盘。纯文本文档很小，复制起来很快。

> ⚠️ **别只存在同一块盘的不同文件夹里 —— 那不叫备份。** 硬盘坏掉时它们一起没。

### 什么时候该回头接远程仓库

| 触发条件 | 为什么 |
|---|---|
| 博客要上线部署 | 主流免费托管都靠远程仓库自动部署 |
| 想换台电脑 / 用手机接着写 | 远程仓库是天然的同步点 |
| 硬盘只剩一块、没有备份盘 | 这是最后一道保险 |

只改文档、纯本地练习的话，可以一直不接。
**满足任一条件时，AI 应主动提醒用户回头处理这件事。**
