## 一句话定位

**把学到的技术知识、踩过的坑、动手做出来的东西，沉淀成一个能长期积累的技术站。**

以学习为起点，但不止于学习。内容重心是**技术**：原理理解、工具使用、项目实践，以及真实踩过的坑。

> 先本地写，结构上按公开站设计，随时可上线（见「上线策略」）。

## 目标读者

| 优先级 | 是谁 | 他们来干什么 | 对内容的要求 |
|---|---|---|---|
| 1 | **我自己** | 复习、翻之前记过的知识点或踩过的坑 | 分类 + 搜索必须好用，否则自己都找不到 |
| 2 | **遇到同样问题的开发者 / 同学** | 搜到一个具体问题，想找能照着做的解法 | **必须交代环境、版本、前提**。否则照做不成功，文章等于白写 |
| 3 | 搜索引擎搜到的人（泛访客） | 顺着关键词点进来 | 标题要能被关键词命中，不能叫「随笔」「记录」这种模糊名字 |

> **第 3 类读者当前数量为 0**（博客还没上线），但页面结构要**为它们设计** ——
> 标题写法、URL 结构、页面描述都要按"将来会被搜到"来做。这是「按公开设计」的具体含义。
> 上线后这一行自动生效，不用改任何东西。

## 定位变更说明（学习笔记 → 技术内容）

这不是「内容变多了」，是**三条标准同时上调**。半年后回看这里，能想起为什么这么定：

| 维度 | 学习笔记站 | 技术站（现在的定位） |
|---|---|---|
| **读者** | 同专业的人，共享课程背景 | 全网遇到同样问题的人，**没有共享背景** |
| **内容标准** | 我自己看懂就行 | **陌生人照着做要能成功** → 必须写清环境、版本、前提、失败情况 |
| **时间属性** | 课本知识几乎不过期 | **工具、版本、命令会过时** → 需要日期，也需要判断什么内容值得写 |

反过来，这也给了内容一个明确的取舍标准：

> **泛泛的「XX 入门」全网都是，别人为什么看你的？**
> 真正有人搜、有人看的，是你**真实踩过的具体坑** —— 因为你写的失败过程，
> 恰好就是别人正在搜的那句话。这是唯一别人抄不走的素材。

## 上线策略（已定 · 2026-09-19）

用户决定：**先按公开站设计，暂不上线。**

| 现在就要做 | 现在不用做 |
|---|---|
| 内容结构与 URL 按公开站设计（避免以后返工） | 域名、备案、托管账号 |
| 本地能一条命令起服务、随时预览 | 访问速度优化、CDN 配置 |
| 把分类体系试出来（还没人看过，改了也没有代价） | 正式上线与对外分享 |

> **这一节里唯一「以后改起来贵」的东西是 URL 结构。**
> 一旦公开，别人收藏和分享的链接就固定了，改 URL = 制造死链。
> 而现在没人收藏过任何链接 —— **这个还没上线的窗口，正是把 URL 定死的最好时机**。
> 换句话说：延迟上线买到的是「免费改错权」，别把它浪费掉，该定的结构现在就定。

## 必须有（核心功能）

- [ ] **文章列表页** —— 按时间倒序列出所有文章
- [ ] **文章详情页** —— 能正常阅读，支持 Markdown 的标题 / 列表 / 引用 / 表格
- [ ] **代码块高亮** —— 技术内容的硬门槛，没有它文章没法看
- [ ] **数学公式** —— 计算机和数学课里公式不少
- [ ] **分类 / 标签（按主题）** —— 主题为一级分类，课程与来源作标签
- [ ] **文章日期 + 最后更新时间** —— 技术内容会过时，读者需要知道这条是什么时候写的。
      生成式站点（Hugo / Astro 等）自带此字段，**成本为零**，所以放进「必须有」
- [ ] **本地一条命令起服务** —— 「暂不上线」期间这是主要的阅读方式，必须够简单
- [ ] **随时可上线** —— 结构具备上线条件，需要时不返工（见「上线策略」）
- [ ] **我能自己发布文章** —— 不改代码，只加文件就能发

## 分类体系（方向已定，清单待确认）

**已定：按主题分类，课程与来源作标签。**

理由：技术内容天然跨课程；项目实践、工具踩坑不属于任何一门课。按课程分会让非课程内容无处可放。

起步主题清单（**不是定稿，前期可随便改** —— 见下方窗口期说明）：

| 主题 | 收什么 |
|---|---|
| 计算机网络 | 协议、HTTP、TCP/IP、抓包实践 |
| 操作系统 | 进程、内存、文件系统、Linux 命令 |
| 计算机组成 | 存储层次、指令、CPU |
| 数据结构与算法 | 结构、算法、刷题总结 |
| 数据库 | SQL、索引、事务 |
| 编程语言 | C / Python 等语法与陷阱 |
| 开发工具 | Git、编辑器、环境配置、踩坑 |
| 项目实践 | 动手做过的东西（含本站本身） |

标签示例：`计网课` `408` `考研` `Windows` `本站搭建`

> **窗口期说明**：现在文章还少、也没人访问过，改主题清单的代价接近零。
> 等上线后分类再动就麻烦了（会影响已有 URL 和外部链接）。所以**前期鼓励频繁调整**，
> 攒到二十来篇时再回头固化一次。

## 想要有（次要功能）

- [ ] 站内搜索
- [ ] 深色模式
- [ ] 文章目录导航（长文必备）
- [ ] 阅读时长显示
- [ ] 文章底部「相关文章」推荐（技术站里很实用：一个人踩过的坑往往连着好几个坑）

## 明确不做（范围边界）

> 这一栏和「必须有」一样重要 —— 不写清楚，需求会无限膨胀。

- ❌ 不做用户注册 / 登录（没有多用户需求）
- ❌ 不做后台管理界面（内容用 Markdown 文件管，不搞数据库）
- ❌ 不做手机 App（响应式网页够用）
- ❌ 不做多语言
- ❌ **不做评论 / 留言**（2026-09-19 定）—— 需接第三方服务，且要处理垃圾评论，
      与「半年后还愿意维护」直接冲突
- ❌ **不做访问统计**（含第三方统计脚本，2026-09-19 定）—— 涉及第三方脚本与隐私，且与「不接广告」一致
- ❌ 不接广告
- ❌ 不自己租服务器做运维（用免费托管）
- ❌ **不写强时效的内容**（如「某软件某版本的界面操作截图」）—— 半年就作废，
      维护成本高于价值。要写就写原理和可迁移的方法，写「怎么做」而不是「点了哪个按钮」
- ⏸ **本期不做生活随笔 / 日记 / 考研心路**（用户 2026-09-19 定：先不放，以后想加再说）

> **关于最后一条，有个结构上的好消息**：「按主题分类」这套结构天然支持以后加生活内容 ——
> **加生活随笔 = 新增一个主题，不需要改任何代码结构**。
> 所以「先不放」不是一个需要将来返工的决定，随时可以低成本扩。
>
> **关于评论被删掉**：第 1～3 版它一直挂在「想要有」里，第 4 版删除了。删除的依据是
> 它与「不做后台」「不自己运维」互相矛盾 —— 评论必须有服务端才能存数据。
> 这也顺带印证了静态方案对本项目是零损失（见 `技术选型.md`）。

## 成功标准

怎么算做成了？按重要性排序：

1. **本地能跑起来、随时能预览** —— 一条命令起服务，电脑手机都能看
2. **随时能上线，且上线不返工** —— URL 结构、分类、页面元素都按公开站设计好了
3. **发一篇文章 = 写一个 Markdown 文件** —— 不需要任何人帮忙改代码
4. **内容找得到** —— 能按主题分类，能搜索
5. **半年后我自己还愿意往里写**

> 第 5 条最难，也最真。**一个没人维护的博客等于失败。**
> 所以「写起来省事」的优先级，要高于「功能多」—— 这一点会在技术选型时反复用到。
