# 别人的博客后台是怎么做的（调研笔记）

> 2026-10-31 18:55 起调研，素材以 2026 年 10 月的现状为准。
> 目的不是「抄一个」，而是回答三个问题：**该不该做、做成哪一类、哪些交互值得抄**。

---

## 一、先说结论

| 问题 | 结论 |
|---|---|
| 该不该做 | **该**，但只做「入库 + 列表 + 编辑」，其余一律后置 |
| 做成哪一类 | **本地编辑器型**（本机起服务、127.0.0.1、直接读写磁盘）—— 这正好是唯一对单人静态博客成立的一类 |
| 最值得抄的 | ① 原文整份写回、不重排注释；② 草稿就是「提交了但不渲染」；③ 图片地址必须绝对；④ 告警宁可进待审也不误杀 |
| 最该放弃的 | 一切云端方案（OAuth、GitHub App、在线 `/admin`），理由见第四节 |
| 一盆冷水 | 半年发不到 6 篇的站，做完整 CMS 是自嗨（第五节） |

---

## 二、市场上的四类做法

### 流派 A：云端 Git CMS（最常见的「静态站后台」）

浏览器里打开一个后台 → 表单编辑 → 保存时把文件 commit 到你仓库 → 触发重建。

| 代表 | 特点 | 谁在用 |
|---|---|---|
| **Decap CMS**（原 Netlify CMS） | 一个 `config.yml` 就能跑，支持 GitHub/GitLab/Gitea 等最多后端；2026 年仍在发版（3.16.x），但积压 594 个 issue | 团队协作、非技术编辑者 |
| **Sveltia CMS** | Decap 的重写版，兼容其配置，更快更轻；仍是 0.x，单人维护 | 想从 Decap 迁走的人 |
| **Keystatic** | TypeScript 写 schema，**local 模式直接读写本机文件**，github 模式走 OAuth | Astro/Next 项目，开发者自己维护 |
| **Pages CMS** | 一个 `.pages.yml`，只支持 GitHub，托管版免费 | 「今天下午就要能编辑」的小站 |
| **TinaCMS** | 能在真实页面上「点哪改哪」的可视化编辑 | 有非技术编辑者的团队 |

**共同代价**（这篇调研文里最重要的一句）：

> 所有客户端 git CMS 都需要一个 **OAuth broker**（替浏览器换取 Git 令牌的中间服务）。
> 这是这类工具部署失败最常见的原因，也是「塞一个 script 标签就能用」这句话最大的误导。

对阿然而言：私有仓库 + 单人 + 不想折腾服务器 → 这一整类都排除。

### 流派 B：给静态站配的「在线后台」

| 代表 | 做法 | 为什么不适合 |
|---|---|---|
| **Qexo**（~2000 星，Django） | 部署到 Vercel 等平台，网页里管文章/图片/页面，通过 GitHub/GitLab 或本地推回仓库；支持 Hexo / Hugo / Valaxy | 要在云上跑一个 Python 服务、要连你的仓库、要账号体系；且不认 Astro 的内容集合 |
| **hexo-admin**（线上模式） | 装成 Hexo 插件，`/admin/` 里写文章 | 只服务 Hexo；作者自己都写着「GitHub Pages 这类纯静态托管**不能**在线上跑 admin」 |

> ⚠️ 这条对我们的直接含义：**上线到 GitHub Pages 之后，「在网站里管理文章」这条路本身就是堵死的**。
> 后台只能永远跑在你自己的电脑上。设计时不要留「以后上线了就能在网页上改」的幻想。

### 流派 C：本地编辑器型（和我们要做的是同一类）

| 代表 | 形态 | 与本项目的对照 |
|---|---|---|
| **hexo-admin**（本地模式） | `hexo server` 起服务，打开 `/admin/`，Ghost 风格界面，直接改 `source/_posts/` | **结构完全同构**：本地服务 + 直接读写 md。差别只在它绑死 Hexo |
| **Keystatic local 模式** | `npm run dev` 后访问 `localhost:4321/keystatic`，表单界面直接写本地文件，**不需要 GitHub 登录** | 现成的「表单型后台」，但要把 React + Markdoc 装进项目，见第六节 |

### 流派 D：脚本 + 编辑器插件（没有后台界面）

这几年 GitHub 上冒出的一批「小工具」路线，核心就一句话：**别做界面，做一条命令**。

| 代表 | 做法 |
|---|---|
| `obsidian-publish.mjs` + 一个 100 行的 Obsidian 插件（破仑的博客） | 插件里点一下 → 跑脚本 → 转语法、拷图片、`git commit + push` |
| **Blog Bridge**（Obsidian 插件） | 选中笔记 → 同步到仓库对应目录，自动按框架预设路径，本地图片一起提交 |
| Markdown Blogger | 把当前笔记推到指定文件夹 |

这条路线对我们最有启发的是它的**设计哲学**，不是工具本身：

> 「Obsidian 是内容的唯一真源，博客仓库里的 Markdown 只是发布产物。
> 这意味着：改文章必须回 Obsidian 改，然后重新发布。」

## 三、值得直接抄的 6 个交互

来源主要是一篇写得很细的中文实践（Hugo + Cloudflare 那套「zero-stack」后台），它的很多取舍是踩过坑之后的结论。

### 1. 保存分两步：先存本地，再提交

它把编辑器里的「保存」拆成两件事：

- **保存本地** → 只写进浏览器缓存，切文章、关后台都不丢
- **保存到 Git** → 才真正提交，会把攒着的几篇一次推上去

**为什么值得抄**：写作时频繁保存，但不希望每存一次就触发一次构建（它那边一次构建 = 一次部署）。
**我们用不用**：用一半 —— 我们的「保存」直接写磁盘（不产生构建），所以不需要缓存层；
但**批量入库**（一次拖 3 个文件）值得做成「确认后一起写」，而不是写一个等三秒。

### 2. 配置文件「整份原样写回」，注释、空行、顺序都不重排

它有一页「主题配置文件」，就是把仓库里那份 `params.toml` 的原文摊在文本框里，
改完整份写回去 —— **不解析、不重组、不排序**。作者原话是「注释、空行、顺序都不重排」。

**为什么值得抄**：这是**最小 diff** 原则。任何「解析成对象再序列化」的做法都会把文件重排一遍，
于是 git 里每次保存都是一整块 diff，看不出你到底改了什么，diff 就失去了审查价值。

**这条直接改我们的设计**：v2 里 F3「重建 frontmatter」是错的做法，要改成「只替换改动的那几行」。

### 3. 草稿是真的草稿

勾了草稿的文章**照样提交进仓库**，只是构建时不渲染它 —— 前台列表、RSS、sitemap 里都没有。
不是「存在数据库里没发布」，也不是「存在浏览器里没保存」。

**我们已经是这样**（`draft: true` → `getCollection` 过滤），继续保持，不用改。

### 4. 写进 Markdown 的图片地址必须是绝对地址

它的硬规矩，原因是站点和 API 不同源：相对路径 `/api/media/...` 到了站点那一侧就是站点的 404，
表现是「后台填的封面和正文图片前台全都不显示」。

**对我们的含义**：阿然用 PicGo 图床，本来就是绝对 URL，天然满足。
但要防另一种情况 —— **Obsidian 里拖进去的本地图片**，复制到站点后路径是 `![](./img/a.png)`，
站点上必裂。这正是我们体检规则 L10 要拦的，**优先级从「🟠 一般」提到「必须拦」**。

### 5. 编辑器左边是仓库目录树

它的文章编辑器：左边一列是 `content/zh/posts/` 的目录树，点开一层层；右边结构化字段；
下面才是 Markdown 正文框。

**为什么值得抄**：一眼知道「我在整个结构里的哪一层」，也能直接切到别的文章。
我们文章少（1 篇），目录树没意义，但**左侧「文章列表常驻」**这个布局值同样值钱 ——
改完一篇不用退回列表页再点下一篇。

### 6. 告警阈值「宁可进待审，也不误杀」

它的评论审核：命中规则打分 ≥ 60 就进「待审」，而不是直接删。作者理由：
「宁可进待审也不误杀作者」。

**对我们的含义**：体检的严重度设计要克制 —— **只有真的会让构建失败或让页面裂掉的才标红**
（缺必填字段、本地图片、重定向撞车），风格类问题一律标黄，且默认不拦入库。

## 四、一条必须先想清楚的原则：谁是唯一真源

这是整个方案的地基。三种模式只有一种能长期成立：

| 模式 | 代表 | 好处 | 致命问题 |
|---|---|---|---|
| **Obsidian 为源**（仓库里的是产物） | 破仑的博客、Blog Bridge | 改文章永远回 Obsidian，不会「两边都改过」 | 站点里手改的内容会在下次发布时被覆盖；工具必须做双向 diff 或强覆盖 |
| **站点为源**（Obsidian 只是写作器） | **本项目（ADR-008）** | 站点里的 md 是权威版本，改了就生效，没有中间层 | Obsidian 里那份会慢慢变旧，可能造成「我明明改了啊」 |
| **双向同步** | 无成熟案例 | 听起来最方便 | 冲突无解，必须做版本合并，单人项目不值得 |

**本项目的选择：站点为源。** 因此有三条结论：

1. 工具**绝不回写 Obsidian vault**（v2 的硬边界第 1 条，继续保留）；
2. 入库是**单向复制**，之后所有修改都在站点这一侧做，不提供「同步回 vault」；
3. 但要在入库成功页**明确提示一句**：「源文件留在 Obsidian 里，之后请改站点这一份」——
   否则半年后一定出现「我到底改的是哪份」。

> 顺带一条反直觉的观察：破仑那套「Obsidian 为源」之所以成立，是因为他把**历史文章也全部搬进 vault**，
> 且从不手改仓库里的 md。只要我们做不到「全部搬进去 + 从不手改」，就不该学他。

## 五、一盆冷水：什么时候不该做 CMS

有篇给客户做 Astro 迁移的实录写得很难听但很实在，它给的阈值是：

| 你的内容变更频率 | 建议 |
|---|---|
| 每月 **少于 1 次** | **不要建 CMS**。发邮件给懂的人改，或者直接用 GitHub 网页编辑器改 md |
| 每月 **1–4 次** | git-based CMS 或 Google Sheets 这类轻方案 |
| **每周**，或者有第二个人在写 | 才值得上真 CMS（带预览、带权限） |

它还补了一句：他把三个客户的站迁完之后发现，其中两个**一个月都改不到一次**，
「为了改个电话号码去搭一套 CMS、培训、维护、付订阅费，是我在解决自己的不舒服，不是他们的问题」。

**套到阿然身上**：

- 现在站里 **1 篇文章**；考研期间（到 2027 年 12 月）真实产出大概 **每月 1–2 篇**；
- 所以按这张表，正好卡在「1–4 次」那一档 —— **轻方案成立，重后台不成立**；
- 更关键的是：他每次发文的痛点不是「文章太多管不过来」，而是**每篇都要重复 5 道手工动作**。

**这个区别决定了方案的形状**：要优化的是**单篇成本**，不是**吞吐量**。
所以「入库向导 + 一个能改元数据的列表」就够；「分类合并、图床巡检、访问统计」这些是给写了 100 篇的人用的。

## 六、对现有设计的 7 处修正

| # | v2 设计里的 | 改成 | 依据 |
|---|---|---|---|
| 1 | F3 保存时「**重建** frontmatter 为规范 7 字段」 | **最小改动**：只替换变更的那几行，新增字段追加到末尾，其余字节（含注释、空行、字段顺序）原样不动 | 流派 C 的「整份原样写回、注释不重排」；最小 diff 才可审查 |
| 2 | 入库后没提「以后改哪一份」 | 成功页加一句「源文件留在 Obsidian，之后请改站点这一份」 | 第四节「站点为源」的必然要求 |
| 3 | 起名「查不到就退化成拼音首字母 + 日期」 | 改为 **术语词表 + 记忆**：维护 `slug-glossary.json`（哈希→hash、线性探测→linear-probing…），用过的自动记住，越用越准；生成 3 个候选让人选 | 拼音首字母生成 `hsyfc` 这种名字比中文名还糟；术语表是可积累资产 |
| 4 | 体检 L10（本地图片）标 🟠 | 提到 **🔴 阻断入库**（除非明确选「先这么放着」） | 「后台填的图前台全不显示」是这类工具第一大坑 |
| 5 | 打算自研 schema 校验（L1/L2） | 优先**直接跑项目自己的构建**（`astro build` 或 `astro check`）并解析报错，自研规则只补构建管不到的（跳级、`==` 未配对、重定向撞车） | 构建器才是权威，自研校验永远慢半拍 |
| 6 | 上线后「在网页上管理」的想象 | 文档里明确写死：**GitHub Pages 跑不了 Node 服务，后台只能本地跑**（且要说明这是行业通例，不是我们偷懒） | hexo-admin 官方说明 + Keystatic 生产需要 adapter |
| 7 | 没评估现成方案 | 附上「为什么不直接用 Keystatic」的说明，见下 | 避免「你为啥不直接用现成的」这个必然会被问到的问题 |

## 六之二、为什么不直接用 Keystatic（现成的那个）

它是这次调研里唯一「几乎能用」的现成方案：`storage: { kind: 'local' }` 下，
`npm run dev` 就能在 `localhost:4321/keystatic` 用表单改本地 md，不需要任何登录。

**但代价对我们偏重**：

| 代价 | 具体 |
|---|---|
| 依赖 | 要装 `@keystatic/core`、`@keystatic/astro`、`@astrojs/react`、`@astrojs/markdoc` 四个包，**把 React 引进一个纯 Astro 站**（本项目有「装依赖挂 23 分钟」的前科，BUG-002） |
| 正文格式 | 它用 Markdoc 存正文，字段类型是 `fields.markdoc`（存 `.mdoc`）。我们的 `==高亮==`、`cpp+tab` 是自研 remark 语法，编辑一次正文有被重写序列化的风险 —— **而我们对正文的要求是逐字节不变** |
| 双份 schema | `keystatic.config.ts` 和 `content.config.ts` 各描述一遍字段，永远要手动同步 |
| 稳定性 | 仍是 0.x / experimental，官方 README 自己标了 |
| 只能管内容 | 我们要的「体检、重定向、起名字」它一个都不管 |

**结论**：如果哪天需求缩到「只要一个表单改 frontmatter」，Keystatic 是首选现成方案；
但按现在的范围（入库 + 体检 + 重定向），自研一个本地小服务反而更小、更可控。

## 七、摆三个方案，你挑一个

| | A 完整后台（v2 原方案） | B 最小后台（推荐） | C 零界面脚本 |
|---|---|---|---|
| 形态 | 本地服务 + 6 个页面 | 本地服务 + **2 个页面**（列表 / 入库） | 一个 `发文章.bat`：拖 md 进去 → 自动起名、补 frontmatter、跑构建 |
| 能干什么 | 列表、入库、编辑、体检、改名、删除、分类合并、git 面板 | 列表、入库、编辑（含草稿开关）、打开站点 | 只管「扔进去 → 变成文章」，改内容得回编辑器 |
| 代码量 | ~6000 行 | **~1800 行** | ~200 行 |
| 第一次能用要多久 | 5 批交付 | **2 批** | 1 天 |
| 适不适合「每月 1–2 篇」 | ❌ 过度 | ✅ 正好 | ✅ 也行，但改元数据要开编辑器 |
| 风险 | 又变成 95% 没人用 | 小 | 用两次就嫌不够，回头还是要做 B |

**我的建议：B。** 理由是第五节那张阈值表 —— 每月 1–2 篇的人需要的是「少点手工」，
不是「一个完整后台」。B 做完如果发现真缺什么（比如改名、体检），再按 P3 往上加，
**而且加的时候接口是现成的**。
