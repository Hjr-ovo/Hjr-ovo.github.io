# 搭建设计和过程

博客项目（myblogweb）的全部设计文档与过程记录。**本文件是总览与索引。**

> 这个文件夹**不参与网站运行**，纯文档。删掉它网站照样跑。

## 文件夹

| 文件夹 | 记什么 | 怎么分文件 |
|---|---|---|
| `设计方案/` | 项目定下来的所有技术、架构决定 | 一个主题一个文件 |
| `文件改动记录/` | 每次改动后记一条 | **一天一个文件** —— `YYYY-MM-DD.md` |
| `bug修复记录/` | 每个 bug 一张卡片，含反思 | **一天一个文件** —— `YYYY-MM-DD.md` |

两个记录文件夹各带一份 `模板.md`（空白骨架 + 完整规则），新建当天文件时复制它即可。
它们的日期文件**同名成对** —— 同一天的「改了什么」和「出了什么问题」能对着看。

另外，**仓库根目录的 Git** 也在承担记录职责，规则见 `设计方案/版本控制约定.md`。

## 规则速览

**文件改动记录** —— 一次操作 = 一行，倒序排列（最新在最上面）；类型只用 5 个词：新增 / 修改 / 删除 / 重构 / 样式。

**bug 修复记录** —— 一个 bug 一张卡片，编号 `BUG-001` 起**全局递增**；**根因** = 这次为什么错，**反思** = 下次怎么不错，两者必须分开写。只有「多个 bug 反复踩同一个坑」才提升成通用规律，写进 `经验教训.md`。

**设计方案** —— 定了的事写进去，**被否决的方案和否决理由也要写**（半年后你会需要它）。

**版本控制（Git）** —— Git 记「事实」（哪些文件、哪些行变了），改动记录记「意图」（为什么改），用提交号双向索引。规则见 `设计方案/版本控制约定.md`。

**文档内引用** —— 一律用**相对路径 + 正斜杠 `/`**，例如 `[查看](文件改动记录/2026-09-19.md)`。不用反斜杠（Markdown 里是转义符）、不用绝对路径（换设备就断）、不用 Obsidian 双链（本项目不在 vault 内，在 GitHub 上不可点）。详见 `设计方案/目录与命名规范.md`。

## 维护约定

| 时机 | 动作 |
|---|---|
| 每次改完文件 | 往 `文件改动记录/YYYY-MM-DD.md` 追加一行；当天文件不存在，就从 `模板.md` 复制一份新建 |
| 发现 bug | 往 `bug修复记录/YYYY-MM-DD.md`（**发现日期**）追加一张卡片，编号接上一个递增 |
| 出现跨 bug 的通用规律 | 追加到 `bug修复记录/经验教训.md` |
| 每次提交后 | 把提交号回填到对应条目（顺手回填上一条，最新那条先标 `——`） |
| 新建了日期文件 | 在下面「索引」里补一行链接 |
